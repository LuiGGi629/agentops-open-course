## Two green checkmarks, one of them load-bearing

It is 16:40 on a Friday and the release decision is yours. Two things on your screen are green. The test suite passed. Last night's evaluation scored 14 of 15. One of those licenses you to say the release is safe; the other one does not, and if you cannot say which is which by the end of this page, you will eventually find out at 02:00 instead.

So this course keeps two words apart, everywhere, on purpose.

A **gate** is deterministic: same input, same verdict, every time, on your machine and in CI. `mise run check` is one. A schema validator is one. So is the test showing that a mutation and its audit row commit together. When a gate is green, the thing it checks is true — not likely, not usually. True.

An **observation** measures something that varies: an evaluation pass rate, a judge's agreement number, a latency figure. When an observation is good, you have learned something real about one run, on one machine, against one model, at one moment. That is worth having. It is not the same currency.

## The report that shows what a gate actually promises

Here is a gate being specific about its own promise. `mise run test` inside `agents/go` runs the suite under the race detector, then checks the coverage profile it just wrote, package by package. Below is the tail of that run — the test results scroll past first — with one line per package trimmed to six of the twenty, plus the verdict:

```bash
cd agents/go
mise run test
```

```text
  ok      84.2%  agents/go/a2aserver
  ok      91.7%  agents/go/compose
  ok      99.4%  agents/go/domain
  ok     100.0%  agents/go/internal/safefile
  ok      90.9%  agents/go/policy
  ok      82.7%  agents/go/state
agents/go meets the 80% per-package coverage floor
```

Before you read on, look at the `100.0%` row and decide what it entitles you to say about `internal/safefile`.

Here is what it entitles you to say: every statement in that package ran at least once while the tests executed. That is all. It says nothing about whether the assertions around those statements checked anything worth checking — a test that calls a function and confirms it did not panic raises coverage and settles nothing. Coverage measures reach. Correctness is decided by what the tests assert, which is why the question you want in a review is "which test fails if I break this", never "what percentage is that package at".

The floor's scope is narrower than it looks, too. Two Go modules carry it: `agents/go`, the code the course teaches from, and `evals`, the harness that measures it. `cmd/` packages are excluded by kind in both, because their behavior is exercised through subprocess tests that Go attributes to the test binary rather than to the package under test. The repository's own tooling module carries no floor at all, and says so in a comment rather than leaving you to infer it.

## Where the two get confused

**Temperature zero is not determinism.** Setting temperature to `0` narrows a model's output distribution; it does not make a run reproducible. The same prompt against the same model can still take a different route through the tools, and it certainly will after a model update, a context change, or a different machine's floating-point behavior. That is why `mise run eval` samples every case three times instead of once: repeats do not remove variance, they let you see it.

A simulation is not production either, and the local stack is unusually honest about being one. The k3d cluster and the seeded incident database are real software doing real work — against a fixed dataset, with no noisy neighbours, no contention, and no traffic you did not send. That tells you the mechanism is correct. It cannot touch how the mechanism behaves at your scale, with your data, under your failure modes.

The subtlest one is silence. A green offline suite says nothing about whether the agent answered well, because it never called a model; a passing conventions check says nothing about whether this page teaches you anything. That kind of false claim is almost never stated out loud — it arrives as a green tick left standing next to a question nobody asked. So this course names the command behind anything it calls proved, and says plainly when there is none.

## How to read the rest of the course

Every later page states its point plainly and, where a caveat matters, links back here instead of restating it. That is a deliberate trade: repeating a warning on forty pages trains you to skip it, and a warning you skip is worse than none at all, because it lets everyone believe the risk was communicated.

So take a passed gate literally, notice what varied in a reported observation, and treat any claim with no command behind it as the page's opinion — including this one.

## What you can do now

- You can say what a gate proves and what an observation suggests, and why the difference decides whether that Friday release ships.
- You can read a coverage percentage as reach rather than correctness, and name the two modules the 80% floor actually covers.
- You can name the three ways a green tick overreaches: variance the repeats reveal, a simulation standing in for production, and silence read as approval.

An hour ago a green checkmark was a green checkmark. You can now take any claim — on these pages or in your own release channel — and ask the one question that settles it: which command would have to fail for this to be false? When no command would, you are holding an opinion. Telling those apart at 16:40 on a Friday is the whole skill.
