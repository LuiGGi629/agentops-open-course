## One question, one tool declaration, nothing else in the room

In 2.1 the agent called `list_incidents` and you read the rows that came back. Something decided to make that call, and it is worth being exact about what. Not the tool layer, not ADK, and not the instruction — those shaped the request. The decision arrived over a TCP connection from a process listening on port 11434, in a JSON field you can go and look at.

So look at it. Predict first: you are about to send one question and one tool declaration to that process directly, with no agent, no instruction, and no session. Does it answer in prose, or does it ask for the tool?

```bash
curl --fail-with-body http://127.0.0.1:11434/v1/responses \
  -H 'Authorization: Bearer local-ollama' \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "qwen3:4b-instruct",
    "input": "What is the status of checkout?",
    "tools": [{
      "type": "function",
      "name": "get_service_status",
      "description": "Return one service status",
      "parameters": {
        "type": "object",
        "properties": {"name": {"type": "string"}},
        "required": ["name"],
        "additionalProperties": false
      }
    }]
  }'
```

Here is the reply. It arrived with thirty-one top-level fields and three of them are shown, each one whole — nested ids and sub-fields included, because those turn out to matter. The twenty-eight left out are the echoed tool list, every sampling setting, the response id, the timestamps, and a long tail of nulls.

```json
{
  "status": "completed",
  "output": [
    {
      "id": "fc_resp_329409_0",
      "type": "function_call",
      "status": "completed",
      "call_id": "be1ATCAFE9C8w5JhEnIdTSUbM1Tlg3vz",
      "name": "get_service_status",
      "arguments": "{\"name\":\"checkout\"}"
    }
  ],
  "usage": {
    "input_tokens": 152,
    "output_tokens": 21,
    "total_tokens": 173,
    "input_tokens_details": { "cached_tokens": 0 },
    "output_tokens_details": { "reasoning_tokens": 0 }
  }
}
```

No prose. Given a question it could not answer and a tool that could, the model emitted a request for the tool — the same move you watched inside the agent in 2.1, here with the whole repository taken out of the room.

Three details are worth carrying forward. The route is `/v1/responses`, the OpenAI Responses API, and an offline test in `agents/go/model/openai_test.go` asserts that exact path so a silent route change fails in CI rather than during an incident. The `arguments` field is a **string** containing JSON, produced by a model that guessed at your schema — which is why nothing downstream trusts it: ADK decodes the shape, then the agent parses identifiers and validates domain rules before any read or write runs. And `usage` is where every token count in this course ultimately comes from. One sentence plus one tool declaration cost 152 input tokens, which is a useful calibration for what a full instruction and the agent's entire tool list will cost on every single turn.

**You just talked to the model layer directly. Every "the AI decided to" sentence you will ever read now decomposes into this: a JSON request in, a function-call proposal out, and typed code that decides what happens next.**

### Tokens, context, and parameters

A language model predicts the next **token** — a chunk of text of a few characters — from the context supplied for one request. Two properties follow, and both shape everything in this course. Generation is **probabilistic**: the same request can produce different valid-looking output. And it is **stateless**: the weights do not remember the previous turn, so the session service rebuilds the relevant history into every request.

The **context window** is the token budget shared by the instruction, the history, the tool schemas, the tool results, and the answer being generated. It is not free real estate. More context means more latency, and on priced providers more money, which is why the policy plugin carries a budget guard and a compaction callback that bound the envelope before a request is sent.

**Parameters** are the learned numbers in the model artifact. They are not current facts about your platform, and they are not memory. That distinction is the whole reason `get_service_status` exists: what is true right now comes from tool reads and explicit stores, never from weights. Notice how thin the model's contribution was above — it picked a tool and filled in one string. Everything that made the string mean something came from somewhere else.

Two more words that get used loosely. An **instruction-tuned** model has been trained to follow conversational instructions and emit tool-call conventions; a base model only continues token sequences and is not a supported agent boundary here without further tuning and measurement. And **open weights** is not **open source**: the default Qwen weights are Apache-2.0 licensed and runnable locally, but the training data and training code needed to reproduce them are not published. This course says the precise thing rather than the flattering one.

## The model is a value, not a name

You answered Ana's page on a laptop — slowly, and for free. A team that runs this for real puts the model on a box with a GPU, behind a gateway that records every request, and sooner or later the same agent has to run there instead. In most agent codebases that move is a refactor, because the provider SDK is stitched through the tool layer. Here it is a URL.

That is possible because ADK keeps its portability seam comically small. A model is anything with two methods:

```go
// simplified: the installed ADK interface also carries package documentation.
type LLM interface {
	Name() string
	GenerateContent(ctx context.Context, req *LLMRequest, stream bool) iter.Seq2[*LLMResponse, error]
}
```

`Name` identifies the implementation; `GenerateContent` takes a typed request and yields responses or errors, the last of which carries the usage metadata you just read off the wire. The agent composes against that interface and never against a vendor client, which is also why tests can replace the model with a scripted one while ADK, the plugins, the tools, the sessions, and the state stay entirely real.

One consequence trips people up: ADK takes a model _instance_, not a model name. Nothing in the framework turns the string `qwen3:4b-instruct` into a client. The factory does that, once, at startup:

{{< include path="agents/go/model/model.go" region="build-model" lang="go" >}}

Set `AGENT_MODEL_FALLBACK` and `Build` wraps the primary so a dead primary fails over to a second model on the same provider, endpoint, deadline, and connection pool. That is continuity inside one trust perimeter — not multi-provider failover, and not a way to smuggle a hosted model into an account-free run.

## Four settings, one of which moves you to a gateway

Every field a run needs is parsed and cross-checked once, at startup, and here is the block they live in. Read past the first line: `AGENT_ENTRYPOINT` chooses which composition gets built, which is [2.5. Dev Loop]({{< relref "/2. Agents/2.5. Dev Loop.md" >}})'s subject rather than this page's. The rest is the model.

{{< include path="agents/go/config/config.go" region="settings-provider-fields" lang="go" >}}

The stable surface is four of them:

| Setting                | What it decides                                        |
| ---------------------- | ------------------------------------------------------ |
| `AGENT_MODEL_PROVIDER` | Which ADK adapter family builds the client             |
| `AGENT_MODEL`          | Which model artifact that adapter asks for             |
| `OPENAI_BASE_URL`      | Direct Ollama, or agentgateway in front of it          |
| `OPENAI_API_KEY`       | The adapter credential, or the local non-secret marker |

The move from your laptop to that governed endpoint is the third row and nothing else: `http://127.0.0.1:11434/v1` becomes `http://127.0.0.1:4000/v1`, and the composition, the tools, the instruction, and the tests are untouched. That is the payoff for constructing the model explicitly instead of letting an SDK read the ambient environment — endpoint, credential, deadline, and sampling all arrive from validated configuration, so nothing about a run depends on what your shell happened to export.

Native Gemini is available and optional: an AI Studio API key, or enterprise mode through Application Default Credentials with an explicit project and location. Both need an account and can cost money, so they are comparisons rather than prerequisites.

The whole wire-and-factory story checks out offline, in under a second, with no endpoint running:

cd agents/go
go test ./model -run 'TestOpenAICompatible|TestBuild' -count=1

## Your turn: change one number and watch the answer move

Comparing two models honestly means holding everything else still: same code, same dataset, same prompt, same decoding settings, same transport. Then you change one thing and run more than once, because a single sample of a probabilistic system is an anecdote.

Predict first: `AGENT_MODEL_TEMPERATURE=0` asks for greedy decoding. Will two runs of the same question then be word-for-word identical?

- **Mode**: `inspect` — the variable goes on the command line, the agent only reads, and no file on disk changes.
- **Goal**: see for yourself how much of a turn's wording is the model's freedom and how much is the rows underneath it.
- **Files to touch**: none. In particular, do not put the variable into `.env`, and do not run `data:reset` — it is `rm -rf .state` and would throw away the conversation you built in 2.1 for no benefit here.
- **Preflight**: `mise run doctor:model` reports the model ready.
- **Steps**: from `agents/go`, run `AGENT_MODEL_TEMPERATURE=0 mise run run` and ask `List the three open incidents.`. Exit with `Ctrl-D`, launch the identical command again, and ask the identical question. Then do it a third time with the variable left off entirely. Each console launch opens a fresh session, so the three runs do not contaminate each other.
- **Gate that proves completion**: you can say which parts of the two temperature-zero answers matched exactly and which did not, and whether the incident identifiers changed across any of the three runs.
- **Final state**: no tracked file changed. Your `.state` directory has gained three short sessions and nothing else.

Whatever your runs show, hold on to the shape of the result: temperature zero narrows the distribution, it does not make a run reproducible, and the identifiers should be stable for a reason that has nothing to do with sampling — they came from a tool. When you compare candidate models seriously, this is the same discipline scaled up: run the same evalset repeatedly and report pass rate, variance, tokens, model calls, latency, and failures rather than one impressive transcript. [0.2. Evidence]({{< relref "/0. Overview/0.2. Evidence.md" >}}) is blunt about how little a single green run tells you.

- You sent a raw request to the model and read the function-call proposal and token usage it returned.

The model has stopped being a brand name and become a value your code constructs: reachable with `curl`, answering on a documented route, and sending back a bill of tokens with every reply.
