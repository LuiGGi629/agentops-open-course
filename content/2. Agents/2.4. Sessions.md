## The conversation has to outlive the process {#what-is-a-session}

It is 03:40 and Ana's laptop has gone to sleep with the agent halfway through INC-002. She wakes it, the server has been restarted by a colleague's deploy, and she types the question that decides how the rest of her night goes: _so what did we already rule out?_ Either the agent still knows, or she is re-establishing twenty minutes of context at four in the morning while inventory is still returning 503s.

That is what a **session** is for. An ADK session is the conversation state for one application, one user, and one session identifier: the ordered events of the turns so far, plus the application state carried alongside them. The reference agent stores sessions in SQLite through ADK's database session service, which is the difference between "the process remembers" and "the conversation exists".

Start the deployed surface and see for yourself:

```bash
cd agents/go
mise run a2a
```

That blocks and serves on `:8080`. From a second terminal, ask it two different questions:

```bash
curl -s http://127.0.0.1:8080/livez
curl -s http://127.0.0.1:8080/healthz
```

```text
{"status":"alive"}
{"status":"ready"}
```

The two look alike and mean different things, which is exactly why there are two. Liveness answers _is this process still looping_ — a restart fixes a failure here. Readiness answers _can this process serve a turn_: it opens both state databases and checks their schemas, and confirms the state directory still accepts writes. Readiness never migrates or publishes state, for a reason worth carrying forward — a probe that changed the generation on disk would be a probe that changes the thing it is measuring. It does write exactly one thing, a `.readiness-*` file it creates and immediately unlinks, because "can I still write here" is not a question you can answer by reading.

**You are now running the same server the Kubernetes chapters deploy, on your own machine, and you can tell the difference between a process that is alive and one that is ready.**

## A task is not a session

Submit work over A2A and a second object appears. An **A2A task** is protocol-visible work with its own id, a context id, a status, messages, artifacts, and a cancellation lifecycle. It is what a remote caller polls, cancels, and resumes. The session is the conversation; the task is one unit of work inside it.

They live in different databases, and you can watch them line up. Send the server one turn — a single JSON-RPC `message/send` post to `http://127.0.0.1:8080/`, which is the one step on this page that calls the model:

```bash
curl -s -X POST http://127.0.0.1:8080/ -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"message/send","params":{"message":{"role":"user","parts":[{"kind":"text","text":"What is the status of INC-002?"}],"messageId":"m-1","kind":"message"}}}'
```

That one post is the only command on this page that spends inference, so it takes as long as a model turn does on your hardware — seconds on a GPU, minutes on a CPU-only laptop. Once it returns, read the task store directly, from the repository root:

```bash
sqlite3 -header -column agents/go/.state/tasks.db \
  "select id, context_id, state from tasks order by last_updated_ns desc limit 2;"
```

```text
                 id                                context_id                     state
------------------------------------  ------------------------------------  ------------------
019fecf4-8b2d-78d9-8fe6-72618f58aa56  019fecf4-8b2d-79bd-a466-02db764bc2a0  TASK_STATE_WORKING
019fecf3-7a1e-7a2a-8266-f1b5261da423  019fecf3-7a1e-7ac4-9d6b-b9bef64a04f5  TASK_STATE_WORKING
```

Those `context_id` values are not task ids. Ask the other database what they are:

```bash
sqlite3 -header -column agents/go/.state/runtime.db \
  "select id, app_name from sessions order by rowid desc limit 2;"
```

```text
                 id                      app_name
------------------------------------  --------------
019fecf4-8b2d-79bd-a466-02db764bc2a0  agentops-agent
019fecf3-7a1e-7ac4-9d6b-b9bef64a04f5  agentops-agent
```

There is the join, and you did not have to take it on trust: each task's context id is the id of the ADK session that owns the conversation it belongs to. Two databases, two vocabularies, one identifier carried across both. And a task that is still thinking is already durable — `TASK_STATE_WORKING` is on disk, not in a goroutine's memory, so a client that reconnects after a restart can still ask what happened to it.

Four files end up in `agents/go/.state/` once you have run a turn, and keeping them straight saves an hour later: `runtime.db` holds ADK's sessions and events, `tasks.db` holds the A2A task store, `incidents.db` is the writable copy of the committed seed, and `vectors.db` is the derived retrieval index. A fifth, `memory.db`, joins them the first time the agent saves a note. All of them are disposable. Writes to each are serialized rather than merely hoped about — the session pool holds one connection, the task store opens every write with `BEGIN IMMEDIATE`, and a per-session lock stops two turns in the same conversation from interleaving their event appends while unrelated sessions keep running concurrently.

SQLite is the right choice for one replica and the wrong one for several: a second replica writing the same file needs a shared database, not a bigger disk. That is a setting rather than a rewrite — [6.9. Scale Out]({{< relref "/6. Platform/6.9. Scale Out.md" >}}) moves exactly these sessions onto PostgreSQL, runs one conversation across two processes to prove it, and names the state that deliberately stays here.

## Kill it mid-restore and it comes back clean

Now the part that sounds like it cannot be true. Run a restore, `kill -9` the process halfway through, and restart it. It comes back clean — either fully on the old generation or fully on the new one, never on a mixture.

That is not luck. Every restore runs under a process lock and walks a three-phase journal: `prepared` while the new generation is staged and the old one is being moved aside, `rolling_back` if anything goes wrong, `committed` once the new generation is live. The journal is fsynced to disk before the first rename happens, so whatever the next start finds on disk is enough to decide what to finish. Recovery rolls a committed transaction forward and rolls anything else back to the byte-exact old generation, verified by SHA-256 rather than by filename.

The suite does exactly that, on purpose, at real seams. Each scenario re-executes the test binary, replaces the rename call with one that calls `os.Exit` at a chosen point, and then asserts what the surviving parent can rebuild from what the dead child left behind:

```bash
cd agents/go
go test ./state -run 'TestRestoreRecoversByteIdentical|TestRestorePreservesCommitted' -v -count=1
```

```text
=== RUN   TestRestoreRecoversByteIdenticalOldGenerationAfterProcessExitOnFirstReplacement
    crash_test.go:242: after-quarantine child exited 71:
--- PASS: TestRestoreRecoversByteIdenticalOldGenerationAfterProcessExitOnFirstReplacement (0.49s)
=== RUN   TestRestorePreservesCommittedNewGenerationAfterProcessExitBeforeCleanup
    crash_test.go:264: before-cleanup child exited 72:
--- PASS: TestRestorePreservesCommittedNewGenerationAfterProcessExitBeforeCleanup (0.38s)
PASS
ok  	github.com/MLOps-Courses/agentops-open-course-go/agents/go/state	0.878s
```

Exit code 71 is a process that died immediately after the old generation's first file was moved aside; 72 is one that died after committing but before cleaning up. Both parents recovered. The dot-prefixed `.restore-*` files you may find in `.state/` afterwards — the journal, its write-ahead temporary, a staging directory, a quarantine directory — are that mechanism's crash notes, and recovery reads them to decide what to do. Deleting them by hand is the one reliable way to break a guarantee these tests otherwise keep, because it removes the only record of which generation was real.

For everyday resets, stop every writer first and then throw the runtime state away:

```bash
cd agents/go
mise run data:reset
```

None of this needs a model to verify. The whole persistence story — schemas, lifecycle, restore, recovery — is decidable offline with `cd agents/go && go test ./a2aserver ./state ./cmd/agent`.

## Your turn: corrupt the journal and watch it refuse

Predict before you run this: you are about to leave a syntactically valid but incomplete restore journal in the state directory and start the server. Does it start and log a warning, start and ignore the file, or refuse to start at all — and which of those three would you want at 03:40?

- **Mode**: `temporary experiment`.
- **Goal**: watch an unexplained restore journal fail closed rather than being guessed at, and confirm that removing it lets startup proceed.
- **Files to touch**: only `agents/go/.state/.restore-journal.json`, which you create and then delete. The committed seed under `agents/data/` is never touched.
- **Preflight**: stop the A2A server with `Ctrl-C`, then confirm no journal is already present with `test ! -e agents/go/.state/.restore-journal.json`.
- **Steps**: from `agents/go`, write a bogus journal with `printf '{"phase":"prepared"}' > .state/.restore-journal.json`, then run `mise run a2a` and read the failure.
- **Gate that proves completion**: `mise run a2a` exits non-zero with `Restore journal is incomplete or has unsupported fields.`, and starts normally again once the file is gone.
- **Final state**: run `rm -- .state/.restore-journal.json` from `agents/go`; the server then starts and `curl -s http://127.0.0.1:8080/healthz` reports ready.

The refusal reads like this, in full:

```text
[a2a] $ go run ./cmd/agent a2a
agent: recovering an interrupted state restore: state snapshot failed: Restore journal is incomplete or has unsupported fields.
exit status 1
[a2a] ERROR task failed
```

Startup order is what makes that refusal possible, and the order is the guarantee rather than a style choice:

{{< include path="agents/go/a2aserver/serve.go" region="a2a-lifespan" lang="go" >}}

Recovery runs first, before the state directory is even created, because until it has run a half-published generation is indistinguishable from a healthy one. Only then does startup publish the writable dataset, prepare the session and task schemas, and build the HTTP surface — the first moment a request could be served at all. Moving the recovery later would not be a refactor; it would be a process that cheerfully serves a conversation reconstructed from two different generations.

## What you can do now

- You started the persistent A2A server and can say what readiness checks that liveness does not.
- You read a live task out of `tasks.db`, then read `runtime.db` and found its `context_id` sitting there as a session id.
- You left an unexplained restore journal in the state directory and watched startup fail closed rather than guess.
- The focused lifecycle, persistence, and crash-recovery tests pass on your machine without a model.

Three files now hold what "the agent remembers" means: one for the conversation, one for the work, and a journal that decides which copy of both is real after a crash. Which of the three survives a second replica is the question [6.9. Scale Out]({{< relref "/6. Platform/6.9. Scale Out.md" >}}) answers.
