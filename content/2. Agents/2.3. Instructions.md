## What belongs in a system instruction?

An instruction should state purpose, evidence procedure, tool-use discipline, stopping conditions, and answer style. It should not pretend prose is authorization.

Open the source and its focused tests:

```bash
sed -n '1,90p' agents/go/compose/composition.go
cd agents/go
go test ./compose -run Instruction -count=1
```

The test proves the committed instruction contract is present. It does not prove a model follows it.

## What operating contract does the agent use?

The exact instruction is included from the composition root:

{{< include path="agents/go/compose/composition.go" region="instruction" lang="go" >}}

Its central loop is evidence first: recall context, read the incident, reuse returned identifiers, inspect unfiltered logs, load the named runbook or skill, then recommend or propose an action.

For multi-step work it requires an observable plan and a stopping or escalation condition. After an approved action it requires fresh reads before claiming recovery.

## Which rules are advice and which are enforced?

| Rule                                      | Runtime enforcement or evidence                     |
| ----------------------------------------- | --------------------------------------------------- |
| Use typed tools and valid identifiers     | Tool schemas plus domain parsers                    |
| Treat tool output as untrusted data       | Policy output hardening                             |
| Do not mutate before approval             | ADK confirmation plus action validation             |
| Attribute a write                         | Required caller, session, invocation, and rationale |
| Keep mutation and audit together          | One SQLite transaction                              |
| Stay inside token budget                  | Before-model budget guard                           |
| Call tools in the required sequence       | Model-backed trajectory scorer                      |
| Cite evidence and avoid invented entities | Groundedness scorer and review                      |
| Be concise                                | Instruction only; no hard runtime limit             |

An instruction can improve model behavior. A guard makes some behavior impossible or causes a deterministic refusal. Keep the distinction explicit.

## Why plan and verify?

A plan makes the target, next checks, expected recovery evidence, and stop condition observable before the loop spends more calls.

Verification after a write prevents the action response from being mistaken for recovery. A successful restart request is not evidence that the service became healthy.

The bounded workflow encodes plan, investigate, evidence review, and recommendation structurally when stronger orchestration is needed.

## Why ground answers in tools?

The model's weights do not contain the current fictional incident database. Tool calls supply the only authorized operational facts.

Grounding also makes evaluation possible: a scorer can compare claimed incident, severity, service, and runbook entities against the question and captured tool evidence.

Entity overlap is narrower than truth. A green grounding score does not certify every causal statement.

## Why name logs, runbooks, skills, and memory separately?

They have different authority:

- Logs are untrusted operational evidence.
- Runbooks are incident-specific remediation data.
- Skills are locally reviewed reusable instructions loaded by a concrete trusted tool type.
- Long-term notes are user-scoped durable context and are redacted before persistence.

Collapsing them into “use context” would hide which boundary, policy, and evaluation owns each one.

## Why is approval not a prompt rule?

The instruction tells the model when to propose a guarded tool call. ADK and the tool implementation decide whether it can run.

A confirmed execution still requires identity, session, invocation, rationale, valid target, enabled writes, and a transaction. A sentence such as “I restarted it” changes nothing.

Human approval is necessary but not sufficient; the runtime validates the complete action context.

## When should output be structured?

Use a schema when another program consumes the answer. The triage report agent emits one strict JSON object whose fields are derived from a typed Go report.

The black-box evaluator refuses unknown fields, trailing JSON, invalid identifiers, empty evidence, and invalid runbook slugs. Free prose remains better when a human is the only consumer and the shape would add no contract value.

## Why does instruction length cost every turn?

The instruction is part of every model request. Repetition consumes context, tokens, latency, and attention before the current question appears.

Keep purpose and load-bearing procedure in the root instruction. Put detailed reusable procedures in skills and incident-specific material in runbooks so the agent loads them only when needed.

Measure token effects with the per-case usage the evaluation run records before adding another long rule.

## How is the instruction versioned?

The instruction is committed source. The exact Git commit identifies its text, composition, policies, and tool schemas together.

Evaluation artifacts record `source_commit` and the evalset digest. Container builds carry the same commit in the OCI revision label and process environment.

Do not introduce a mutable prompt alias as a second authority. Compare instruction candidates as separate git-pinned revisions.

## How should you review an instruction change?

Use a bounded sequence:

1. State the behavior the change should affect.
1. Add or update the smallest deterministic contract test.
1. Add a representative eval case when model choice is involved.
1. Run the compose and policy packages offline.
1. Run `eval:validate` and the eval module tests.
1. Capture model-backed evidence on the exact candidate only when a model is available.
1. Compare tokens, required trajectories, groundedness, and failures before promotion.

Avoid tuning the wording against one visible case until it merely memorizes the set.

## Your turn: which case catches a deleted rule?

Run a temporary red-green experiment against the direct skill-loading rule.

- **Mode**: `temporary experiment`.
- **Goal**: weaken one load-bearing instruction, observe its deterministic contract fail, restore it, and connect it to the named model-backed case.
- **Files to touch**: temporarily edit only `agents/go/compose/composition.go`; keep the existing regression test unchanged.
- **Preflight**: require `git diff --quiet -- agents/go/compose/composition.go` and save the current `TestRootInstructionPromptContract` green result.
- **Gate that proves completion**: `cd agents/go && go test ./compose -run TestRootInstructionPromptContract -count=1` goes red after the edit and green after the restore.
- **Final state**: run `git restore -- agents/go/compose/composition.go`; then `git diff --exit-code -- agents/go/compose/composition.go` is empty and the focused test is green.

Temporarily weaken the sentence that requires direct exact-name `load_skill`, run the focused test, and retain the failing test output as regression evidence outside the repository. Restore the source immediately and rerun the test.

Then inspect `remediation-loads-skill` in `evals/ops.evalset.json`: its required trajectory is the model-backed owner of the same behavior. A live before/after run is optional and stochastic; never promise that one weakened-prompt sample must fail, and never weaken the case or scorer to manufacture red.

**You are done when:**

- The instruction and policy tests pass offline.
- The evalset and scorer assets validate without a model.
- You can classify every instruction rule as enforced, behavior-scored, structurally pinned, or advisory.
- You can point to the runtime confirmation boundary rather than treating prompt text as authorization.
- You can explain why the source commit is the instruction version.
- The temporary instruction edit made `TestRootInstructionPromptContract` fail, the restored tree is clean, and you can name the `remediation-loads-skill` model-backed case.
