## How does online evaluation differ from offline evaluation?

Offline evaluation runs fixed, versioned cases before release. Online evaluation samples real traffic after an answer has already reached a user.

Offline evidence asks whether a candidate regressed known behaviors. Online evidence asks whether real inputs and outcomes are drifting beyond what the fixed set anticipated.

Online scoring cannot block an answer retroactively. Request-time policy owns prevention; an asynchronous scorer can only detect and route a finding.

## How do you inspect a bounded trace sample?

Open Grafana at `http://localhost:3002`, choose the Tempo datasource, and filter the `agentops-agent` service over a stated recent window.

Read metadata first: operation, model, duration, status, tool names, and errors. Open detailed spans only for authorized investigation.

Confirm Tempo itself is ready and one selected trace exists:

```bash
curl --fail http://localhost:3200/ready
curl -sS -o /dev/null -w '%{http_code}\n' \
  'http://localhost:3200/api/traces/<trace-id-from-grafana>'
```

A `200` proves that trace is stored. It does not prove its answer was correct.

## How are runtime and evaluation populations separated?

The evaluator exports only when `EVAL_OTEL_EXPORTER_OTLP_ENDPOINT` is set explicitly. It also forces child-agent telemetry off.

Runtime traffic uses the agent's own OTLP configuration. Evaluation runs use `service.name=agentops-evals` and stable `agentops.eval.*` signals.

Never estimate user drift from a population mixed with committed eval prompts. Check the service and run attributes before sampling.

## What evaluation does the course ship?

The standalone `evals` Go module drives isolated ADK REST or A2A processes from committed evalsets. It folds captured events into a typed turn and applies deterministic trajectory, cost, groundedness, and schema scorers, plus an optional calibrated gateway judge.

It writes sanitized result artifacts and optional run/case/score OTel evidence. It does not read stored runtime traces and does not score production traffic.

This separation is architectural, not a naming convention.

## Does the course ship an online evaluator?

No. It ships runtime telemetry, offline model evaluation, and a process for promoting sanitized review findings into committed regression cases.

It does not ship sampling, consent, an online judge scheduler, reviewer access control, assessment storage, alert thresholds, or incident routing for answer quality.

Do not claim drift detection or automatic feedback collection is active.

## Why can metadata-only traces not prove answer quality?

Content capture defaults to false. Runtime traces keep operation, model, tool, token, latency, status, and correlation metadata while excluding prompts, responses, and tool payloads.

Without the answer and evidence, a later job cannot decide whether the answer was correct or grounded. It can score coarse properties such as tool-name order, status, latency, or model selection.

Enabling content capture duplicates user data into a durable store and changes privacy, access, and retention obligations. There is no path that gets answer correctness from content-free telemetry for free.

## Which shipped signals can reveal coarse drift?

Use bounded runtime proxies:

- Request rate, latency, and error ratio by operation and model.
- Guardrail injection-neutralization and gateway rejection counts.
- Structured-report schema failures.
- Model-call and token distributions.
- Circuit openings and dependency errors.

A changed proxy says something moved. It does not identify answer correctness.

## How should you detect drift honestly?

Choose a baseline window, candidate window, minimum sample, and bounded dimensions. Compare distributions only after confirming source and model identity for both windows.

Sparse lab traffic is noisy. Require a sustained difference larger than expected sampling noise before acting.

The absence of a quality metric is not evidence of stable quality. State that no online correctness trend exists when content is not scored.

## What would a safe online scorer require?

A production design needs:

1. A representative rate-limited inclusion rule.
1. Consent, minimization, and retention for every field read.
1. Redaction before any external model call.
1. Versioned scorer and judge identities.
1. Cost, timeout, and error budgets.
1. Deduplicated verdict storage linked to the source trace without mutating it.
1. Sustained thresholds and accountable incident owners.
1. A path that promotes sanitized failures into offline cases.

Run the job outside the request path so scorer latency or outage cannot harm users.

## What should your design say?

Write one page that fills these fields:

1. Included and excluded traces.
1. Metadata or content fields read.
1. Redaction and retention.
1. Scorer version and cost cap.
1. Baseline, threshold, window, and minimum sample.
1. Verdict store and trace-link key.
1. Owner, alert route, and rollback action.

State whether the scorer can assess answer correctness. If it needs content, name the privacy cost explicitly.
