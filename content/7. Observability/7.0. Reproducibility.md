{{% admonition abstract "In one glance" %}}

- **You will:** Capture the inputs that decide an agent run and reject comparisons that mix source, model, data, state, or transport.
- **You need:** The offline Go modules installed; a local model only for the optional model-backed capture.
- **Time:** about 30 minutes, hands-on. {{% /admonition %}}

## What must be recorded to reproduce a run?

An agent release is a tuple, not only a commit:

```bash
go -C tools run ./cmd/source-identity --root .. --mode development | jq
```

| Input                     | Authority                                      |
| ------------------------- | ---------------------------------------------- |
| Source and instruction    | Typed source identity, revision, and tree hash |
| Go dependency graphs      | Module manifests and checksums                 |
| Build and CLI tools       | `mise.toml` and `mise.lock`                    |
| Container bytes           | Image digest and OCI revision label            |
| Provider, model, endpoint | Validated configuration                        |
| Model artifact            | Provider identity or local model digest        |
| Tool schemas and policy   | Source identity and compiled binary            |
| Seed and eval cases       | Source identity plus evalset digest            |
| Runtime state             | Isolated state generation or reviewed snapshot |
| Transport                 | ADK REST or A2A                                |
| Sampling                  | Temperature and repeat count                   |

Any one can change behavior. Record every value before comparing candidates.

## Why does Git own the instruction version?

The root instruction is committed source and its contract tests pin its exact content. The compiled binary and OCI revision therefore identify the instruction and tool wiring together.

That is stronger than a mutable registry alias: the same commit can be reviewed, built, evaluated, and rolled back without a second version namespace.

Do not identify a prompt merely as “current.” Use the binary's validated source tuple.

## How do you capture the source identity?

Inspect development work without pretending it is a release:

```bash
go -C tools run ./cmd/source-identity --root .. --mode development | jq
```

Clean output keeps the full revision and a tree digest. Dirty output uses a visible `unknown+dirty.<digest>` identity, omits the revision claim, and still records a deterministic tree digest.

Require a clean release identity before collecting release-bearing evidence:

```bash
go -C tools run ./cmd/source-identity --root .. --mode release | jq
```

That mode rejects tracked changes, untracked source, missing Git metadata, and a caller-supplied identity that disagrees. Image tasks pass the same validated identity, revision, tree digest, mode, and dirty bit to the binary and OCI labels.

## How do you capture model identity?

Print the validated configuration with secrets masked:

```bash
cd agents/go
mise run config:check
```

Record provider, model name, base URL class, temperature, and optional fallback. For local Ollama, also retain the resolved model artifact identity from the model catalog.

An endpoint URL can contain infrastructure details, so sanitized release artifacts record provider, name, and optional digest rather than the URL.

## How does evaluation bind the tuple?

The Go harness writes a content-free run artifact containing:

- Source mode, identity, revision, tree digest, and dirty state.
- Sanitized platform identity.
- Sanitized model identity.
- Evalset id and SHA-256 digest.
- Transport and timestamps.
- Per-case sample, scores, pass state, token usage, and model calls.
- Repository release-policy version and digest for release-bearing runs.
- Pass rate, policy-derived minimum pass rate, and required-case status.

The core artifact is `evals/eval-results.json`. Its existence is not a pass; a qualifier matches its policy identity and verdict to the reviewed `evals/release-policy.json` as well as every other required field.

## How does OpenTelemetry reinforce the artifact?

An explicitly configured eval exporter creates one `agentops.eval.run` trace with case and score children. Bounded metrics carry the same run, source tuple, platform, model, evalset, transport, case, and outcome identities.

JSON is the release handoff. Tempo, Prometheus, and Grafana are runtime evidence and comparison views. Neither store replaces source-controlled evalsets or immutable release attachments.

The harness never exports child-agent telemetry into the evaluator's stream, which prevents one model call from appearing as both runtime and evaluation evidence.

## How do you reset state for comparison?

Each evaluation case starts the agent with isolated temporary state and tears it down afterward. Manual comparisons reset host state explicitly:

```bash
cd agents/go
mise run data:reset
```

Never mutate `agents/data/incidents.db`. If two candidates read different runtime generations, label the comparison invalid unless state itself is the variable under test.

## What remains nondeterministic?

Model selection, serving kernels, concurrency, sampling, and upstream behavior can vary even when temperature is zero. Network latency and tool availability also change run timing.

Reduce variance by pinning inputs, isolating state, using stable transport, and repeating important cases. Report mixed samples rather than averaging away a load-bearing failure.

Deterministic Go tests prove parsers, policies, scorers, and wire folds. They do not make the model deterministic.

## Which comparisons are invalid?

Reject a comparison when candidates differ in more than the declared variable:

- Different source identities without a reviewed source diff.
- Different evalset digests or sample counts.
- Different seed or runtime state.
- Different provider, model artifact, endpoint class, or temperature.
- REST on one side and A2A on the other unless transport is the variable.
- Different cost context or serving version.
- One artifact missing positive usage or required cases.
- One run exported evaluator evidence and the other did not, then compared dashboard presence as quality.

The comparison command refuses incompatible evalset digests and samples, but human review still owns the rest of the tuple.

## How do you compare two prompt revisions?

Capture one sanitized result from each clean Git-pinned instruction revision with the same model and evalset. Separate worktrees prevent one candidate binary from serving both runs.

Export reviewed `BASELINE_SHA` and `CANDIDATE_SHA` values, then run from the repository root:

```bash
git worktree add ../agentops-baseline "$BASELINE_SHA"
git worktree add ../agentops-candidate "$CANDIDATE_SHA"
mise run --cd ../agentops-baseline/agents/go build
mise run --cd ../agentops-baseline/evals eval:policy-trial
mise run --cd ../agentops-candidate/agents/go build
mise run --cd ../agentops-candidate/evals eval:policy-trial
mise run --cd evals eval:ab -- \
  --baseline ../../agentops-baseline/evals/policy-trial-results.json \
  --candidate ../../agentops-candidate/evals/policy-trial-results.json
```

Give both worktrees the same exported model settings or equivalent gitignored root `.env` files. The command requires distinct clean revisions and identical model, platform, transport, evalset, and samples. Policy trials support comparison while release thresholds remain unapproved; they do not qualify either candidate.

Review the source diff before attributing the delta to instructions. The command compares deterministic scores and pass rate, but it cannot prove that the commits differ only in prompt text.

Roll back by validated source revision and exact image digest, not by editing a mutable prompt in place.

## How do you capture the release tuple in one pass?

Run offline validation first, then a model-backed task only when a model is intentionally available:

```bash
go -C tools run ./cmd/source-identity --root .. --mode release | jq
mise run --cd agents/go config:check
mise run --cd evals eval:validate
mise run --cd evals test
mise run --cd agents/go build
AGENT_MODEL_TEMPERATURE=0 mise run --cd evals eval:policy-trial
```

Only the policy trial is model-backed; building remains offline after dependencies are installed. Preserve the resulting sanitized artifact and its full source tuple. Once the reviewed policy is approved, replace the trial task with canonical `eval` to request qualification.

If the observability stack is intentionally running, set `EVAL_OTEL_EXPORTER_OTLP_ENDPOINT` explicitly before the eval and confirm the matching run trace. Do not start the stack solely to satisfy an offline claim.

## What proves this page worked?

Fill this checklist from current evidence:

1. Source mode, identity, revision, tree digest, and clean-tree status.
1. Agent, evaluator, and tool module checksums.
1. Provider, model, optional digest, and temperature.
1. Evalset id and digest.
1. Transport and repeat count.
1. Image digest and revision when a container was used.
1. Result run id, pass rate, minimum pass rate, and required-case status.
1. OTel run trace id only when an explicit collector stored it.

**You are done when:**

- Every checklist line has a value or an explicit “not used” boundary.
- The offline eval validation and tests pass.
- A model-backed artifact, if produced, identifies the same clean source tuple and evalset digest.
- You can explain why Git owns instruction versioning and why a dirty tree breaks that claim.
- You refuse to combine evidence from different candidate source identities.

Continue to [7.1. Tracing]({{< relref "/7. Observability/7.1. Tracing.md" >}}) when one run can be attributed without a mutable alias or hidden state assumption.
