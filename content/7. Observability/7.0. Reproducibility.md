## "It passed on my machine on Tuesday"

The evaluation was green on Tuesday. On Thursday the same command, on what everyone agrees is the same code, comes back red — and the argument starts. Ana says the prompt changed under them. Her colleague says it is just the model being stochastic. Neither can prove it, because nobody wrote down what Tuesday actually was.

An agent run is decided by more than a commit. It is decided by the source, the model artifact behind a model _name_, the seed data, the runtime state left over from the last run, the transport, the temperature, and the number of samples. Change any one silently and you have not run the experiment you think you ran. So before this chapter measures anything, it teaches you to pin what you are measuring.

## Ask the checkout what it is

One command answers, and it never guesses:

```bash
go -C tools run ./cmd/source-identity --root .. --mode development | jq
```

Predict the answer first. Your working tree almost certainly has uncommitted edits right now. Should this command print the commit you are sitting on?

It does not, and that refusal is the whole design:

```json
{
  "mode": "development",
  "display": "unknown+dirty.066737d90d99",
  "tree_digest": "sha256:066737d90d99404dabb8009400b1bcaa42484f434deecf98483135170a55cb19",
  "dirty": true,
  "shallow": false
}
```

There is no `revision` field at all. A dirty tree is not the commit it sits on, so it never claims one — it gets a visible `unknown+dirty.<digest>` name instead, plus a deterministic digest of the tree as it actually is. Your digest will differ from the one above; that is the point of a digest.

Now ask the same tree for a release identity:

```bash
go -C tools run ./cmd/source-identity --root .. --mode release | jq
```

```text
source-identity: release source is dirty; tracked and untracked inputs must match HEAD
exit status 1
```

Release mode refuses, non-zero, before producing anything a downstream artifact could quote. It reads `git status` with untracked files included, so a stray scratch file counts as dirt exactly like an edited one — because a build that compiled a file nobody committed is not reproducible from the commit. On a clean checkout the same command prints the full revision, the tree digest, and `"dirty": false`, and the image tasks stamp that same validated identity into the binary and the OCI labels.

**You can now tell, in one command and without trusting anyone's memory, whether the thing in front of you is a release candidate or somebody's afternoon.**

That is also why Git owns the instruction version here. The root instruction is committed source with contract tests pinning its content, so the binary and its OCI revision identify the instruction and the tool wiring together. There is no mutable prompt alias to drift out from under a review — and a rollback is a revision plus an image digest, not an edit to a live prompt.

## The tuple that decides a run

Source identity is one line of a longer receipt. Record every line below before you compare two candidates, because any one of them can move an answer:

| Input                     | Authority                                      |
| ------------------------- | ---------------------------------------------- |
| Source and instruction    | Typed source identity, revision, and tree hash |
| Go dependency graphs      | Module manifests and checksums                 |
| Build and CLI tools       | `mise.toml` and `mise.lock`                    |
| Container bytes           | Image digest and OCI revision label            |
| Provider, model, endpoint | Validated configuration                        |
| Model artifact            | Provider identity or local model digest        |
| Tool schemas and policy   | Source identity and compiled binary            |
| Seed and eval cases       | Source identity plus evalset digest            |
| Runtime state             | Isolated state generation or reviewed snapshot |
| Transport                 | ADK REST or A2A                                |
| Sampling                  | Temperature and repeat count                   |

The model half of that table has its own command, which prints the resolved configuration with secrets masked:

```bash
cd agents/go
mise run config:check
```

It prints every setting in one alphabetical list. Here is the run's header plus the five consecutive `AGENT_MODEL*` lines out of the middle of it:

```text
[config:check] $ go run ./cmd/agent config:check
Agent configuration is valid. Resolved settings (secrets masked):
...
- AGENT_MODEL = qwen3:4b-instruct
- AGENT_MODEL_FALLBACK = (unset)
- AGENT_MODEL_PROVIDER = openai-compatible
- AGENT_MODEL_TEMPERATURE = (unset)
- AGENT_MODEL_TIMEOUT_S = 60
...
```

The `...` marks are mine — the real run prints 45 settings with nothing elided, and yours will differ wherever your `.env` does. Record the provider, the model name, the base-URL _class_ rather than the URL, the temperature, and any fallback. An endpoint URL can carry infrastructure detail, so sanitized artifacts record provider, name, and optional digest instead. For local Ollama, also keep the model artifact digest the catalog resolved — `qwen3:4b-instruct` is a label, and labels get re-pointed.

State is the line people forget. Each evaluation case starts the agent on isolated temporary state and tears it down afterwards, but a manual comparison you run by hand inherits whatever the last run left behind:

```bash
cd agents/go
mise run data:reset
```

Never mutate the committed seed at `agents/data/incidents.db`. If two candidates read different runtime generations, the comparison is invalid unless state itself is the variable you are testing.

### What the evaluation artifact pins for you

The harness writes most of that receipt so you do not have to. `mise run eval` runs three samples per case against a 0.33 minimum pass rate with four required safety cases, and writes a content-free artifact to `results.json`: the run id, the source revision and dirty flag, the sanitized model identity, the evalset id and SHA-256 digest, the transport and timestamps, per-case scores, pass state and token usage, and a summary carrying `pass_rate`, `minimum_pass_rate`, and `required_cases_passed`.

The file existing is not a pass. Read those three summary fields together, then check that `source.revision` is the candidate you meant to measure — a dirty run reports no revision at all, which is the artifact telling you it cannot be attributed.

With an evaluation exporter explicitly configured through `EVAL_OTEL_EXPORTER_OTLP_ENDPOINT`, the same run also emits one `agentops.eval.run` span tree with case and score children, and bounded metrics carrying the run, source revision, model, evalset, transport, case, and outcome. JSON stays the release handoff; Tempo and Prometheus are the comparison view. The harness forces the child agent's exporter off, so one captured case can never be counted twice — once as an evaluation result and once as production traffic.

A comparison is invalid the moment two candidates differ in more than the declared variable. Reject one when the source identities differ without a reviewed diff, when the evalset digest or sample count differs, when the seed or runtime state differs, when the provider, model artifact, endpoint class, or temperature differs, when one side ran REST and the other A2A, or when one run exported evaluator telemetry and the other did not and someone read dashboard presence as quality. `mise run eval:ab` refuses mismatched evalset digests, sample counts, and non-distinct revisions, and recomputes pass rates from the per-case records rather than trusting either summary — but the rest of the tuple is still yours to check.

{{% collapsible note "Deeper: comparing two prompt revisions without cross-contamination" %}}

Separate worktrees stop one candidate binary from serving both runs. With reviewed `BASELINE_SHA` and `CANDIDATE_SHA` exported, from the repository root:

```bash
git worktree add ../agentops-baseline "$BASELINE_SHA"
git worktree add ../agentops-candidate "$CANDIDATE_SHA"
mise run --cd ../agentops-baseline/agents/go build
mise run --cd ../agentops-baseline/evals eval
mise run --cd ../agentops-candidate/agents/go build
mise run --cd ../agentops-candidate/evals eval
mise run --cd evals eval:ab -- \
  --baseline ../../agentops-baseline/evals/results.json \
  --candidate ../../agentops-candidate/evals/results.json
```

Give both worktrees the same model settings. Then read the source diff before attributing the delta to the instruction: the command shows only that the scores moved, never that the prompt text was the sole difference. {{% /collapsible %}}

Temperature zero does not buy determinism, only lower variance — model selection, serving kernels, concurrency, and upstream behavior all still move. Deterministic Go tests cover the parsers, policies, scorers, and wire folds around the model; they do not make the model deterministic. Report a mixed sample rather than averaging away the one failure that mattered. The reasoning behind that line lives in [0.2. Evidence]({{< relref "/0. Overview/0.2. Evidence.md" >}}).

## Your turn: make the build refuse to name itself

You have read that release mode fails closed. Now cause it, so you recognise the message when it blocks a pipeline instead of a page.

Predict first: you are about to add one file that nothing imports and nothing reads. Does an untracked file change the tree digest, and should it stop a release identity?

- **Mode**: `temporary experiment`.
- **Goal**: watch one untracked file change the development identity and make release mode exit non-zero, then watch both return to where they started.
- **Files to touch**: only `scratch-identity.txt` at the repository root, which you create and then delete. The committed seed and every tracked file stay untouched.
- **Preflight**: from the repository root, confirm the file is not already there with `test ! -e scratch-identity.txt`, and record today's digest with `go -C tools run ./cmd/source-identity --root .. --mode development | jq -r .tree_digest`.
- **Steps**: create the file with `printf 'scratch\n' > scratch-identity.txt`, then run the development command again and the `--mode release` command after it.
- **Gate that proves completion**: with the file present, the development `tree_digest` differs from the one you recorded, and `--mode release` exits non-zero with `release source is dirty; tracked and untracked inputs must match HEAD`.
- **Final state**: run `rm -- scratch-identity.txt`; the development `tree_digest` matches the value you recorded in the preflight, byte for byte.

Write one sentence explaining to a colleague why an unimported scratch file is allowed to block a release build. If you cannot, the digest is not yet doing the job you think it is.

## What you can do now

- You can name what your checkout is — revision or `unknown+dirty.<digest>` — without asking Git twice or trusting memory.
- You made release mode refuse on purpose and can quote the message it fails with.
- You can list the tuple behind a run, and say which line makes a given comparison invalid.
- You know why a dirty run's `results.json` carries no revision at all, because you just made the same refusal happen by hand.

Thursday's argument now has an answer, and it takes one command rather than three people's memories. That is the whole reason the rest of this chapter's numbers are worth writing down: a measurement you cannot attribute to a specific tree is a number, not evidence.
