{{% admonition abstract "In one glance" %}}

- **You will:** Inspect one approved action, its audit record, and the retention and authority boundaries around that evidence.
- **You need:** A host agent with initialized state; the in-cluster backup proof is optional and needs the Chapter 6 platform.
- **Time:** about 24 minutes, hands-on. {{% /admonition %}}

## What does governance mean for this agent?

Governance means every consequential write has a named authority, a bounded surface, and evidence another person can inspect.

```bash
cd agents/go
go test ./tools ./state
```

The repository implements that statement at four boundaries:

1. Only `restart_service` and `resolve_incident` can change operational state.
1. ADK confirmation must approve the exact action and target before either handler runs.
1. The state change and its audit row commit in one SQLite transaction.
1. Release qualification consumes sanitized, source-scoped evaluation verdicts rather than prompts or responses.

This is a lab-grade governance model. It does not provide public identity, cryptographic log immutability, high availability, or an external retention service.

## Who authorized this change, and can you prove it?

The direct ADK surface carries its local user id into confirmation. On A2A, a synthetic id scopes sessions and memory but cannot authorize a guarded operational write. A trusted gateway must validate the caller and overwrite the configured identity header; the typed subject must then match the invocation owner.

The secured host profile makes that trust chain executable with lab JWTs. The shipped k3d and GKE profiles configure no caller identity provider and set `AGENT_WRITES_DISABLED=true`, so guarded actions refuse independently of confirmation.

On the account-free route, task and context identifiers are only single-user capability handles. They are not tenant credentials and provide no multi-user task-confidentiality claim; keep that route private or add gateway authentication before shared use.

Approval is not a Boolean detached from the work. The handler validates the invocation id, action, target, rationale, and current decision context. Replaying the same invocation, action, and target returns the original audit row without mutating state again; changing any member creates a different request.

This is why the conversational entrypoint keeps write tools in-process. The remote MCP surface publishes only six reads and cannot manufacture an ADK confirmation context.

## How do you inspect action evidence?

Run a host action through `mise run run`, approve it when ADK asks, and retain the returned `audit` object. It contains the same row committed with the state change.

Then inspect the persisted row with the pinned SQLite CLI:

```bash
sqlite3 agents/go/.state/incidents.db \
  'SELECT schema_version, ts, actor, approved_by, action, target, invocation_id FROM audit_log ORDER BY id DESC LIMIT 5;'
```

Do not query the immutable seed at `agents/data/incidents.db`; host writes belong under `agents/go/.state`. The container is distroless and has no diagnostic shell, so in-cluster recovery evidence is verified by the typed `platform-backup` drill from [6.6. Platform Delivery]({{< relref "/6. Platform/6.6. Platform Delivery.md#how-do-you-run-a-restore-drill" >}}), not by installing ad hoc tools in the workload. That drill seeds a mock audit invocation directly and is not proof of an authenticated network write.

## What does an audit row contain?

The schema stores decision evidence, replay identity, and the action outcome together:

{{< include path="agents/data/sql/schema.sql" region="audit-schema" lang="sql" >}}

The important fields answer separate questions:

- `actor` names the executing agent; `approved_by` names the principal that confirmed it.
- `rationale` records why the approver accepted the action after deterministic redaction and length validation.
- `context_summary` captures the service and incident state used at execution time.
- `session_id` and `invocation_id` join the row to the exact decision and enforce idempotent replay.
- `schema_version` lets backup and restore refuse evidence newer code cannot interpret.

The row contains no prompt, model response, raw tool body, credential, endpoint URL, or trace body.

## Is the audit log immutable?

No. It is append-only at the application schema boundary, not cryptographically immutable.

SQLite triggers reject `UPDATE` and `DELETE` against `audit_log`, and the tests prove that the action and row roll back together on failure. An administrator who can replace the database, alter the schema, disable triggers, or restore an older snapshot can still change history.

Use the precise claim: ordinary application writes cannot rewrite or delete an existing audit row. Production-grade immutability would need a separately administered append-only or signed destination with independent access controls and retention.

## How long does each kind of evidence survive?

Retention follows the store that owns each signal; the course configures no universal policy.

| Evidence                   | Store                                        | Shipped retention boundary                                        |
| -------------------------- | -------------------------------------------- | ----------------------------------------------------------------- |
| Runtime traces             | Tempo                                        | the configured local volume and backend settings                  |
| Runtime logs               | Loki                                         | the configured local volume and backend settings                  |
| Runtime and eval metrics   | Prometheus                                   | the configured time-series retention                              |
| Sanitized eval verdicts    | generated JSON artifacts and optional OTLP   | artifact lifecycle or telemetry-backend policy                    |
| Approved action rows       | runtime SQLite state                         | until an authorized state restore or storage lifecycle removes it |
| Release workflow artifacts | GitHub Actions handoff                       | at most seven days                                                |
| Immutable release evidence | release assets and OCI attestations, if made | the release and registry retention policies                       |

Telemetry and generated eval artifacts are content-free by default, but metadata can still be sensitive. A session id, source identity, model name, or incident target can reveal operational context, so access and retention still matter.

## How do you answer a data-subject request?

Start from a verified subject key, not a text search over every store.

This course has no customer identity directory and therefore ships no automated subject-access or erasure workflow. The available identifiers have different authority:

| Store                   | Search key available here                         | Erasure mechanism shipped?                     |
| ----------------------- | ------------------------------------------------- | ---------------------------------------------- |
| Session SQLite          | application, user, and session ids                | no end-user API                                |
| Audit SQLite            | approved principal, session, invocation, target   | none; application triggers reject row deletion |
| Tempo and Loki          | trace, span, service, and bounded resource fields | no subject-indexed workflow                    |
| Prometheus              | low-cardinality service and eval dimensions       | no subject-indexed workflow                    |
| Sanitized eval artifact | run, source, model, evalset, case, and score ids  | delete the generated artifact by policy        |

Do not promise erasure you cannot perform. An operator must authenticate the requester, map that identity to repository identifiers, identify legal retention constraints, and apply the backend owner's deletion process. The course gives you evidence boundaries, not a compliance certification.

## Who can still alter the evidence, and what stops them?

Authority is separated by component, but a local lab operator ultimately controls the machine.

- An authenticated host agent can append guarded audit rows, but its normal handlers cannot update or delete them.
- The shipped Kubernetes agent freezes guarded writes at startup because its gateways provide no verified caller identity.
- The read-only MCP pod cannot write the shared state claim.
- The evaluation harness cannot import the agent module and exports only through its own explicit OTLP endpoint.
- The collector can route telemetry but does not receive model prompts or answers by default.
- A cluster or storage administrator can replace state and telemetry; independent production evidence needs a stronger administrative boundary.

The defense is layered least privilege, not an assertion that administrators are powerless.

## How is cloud authority separated?

The optional GKE path uses Workload Identity Federation rather than mounted service-account keys.

OpenTofu plans the project resources, kagent controls the BYO workload, the gateway obtains only the identity required for its Vertex backend, and the agent service account has no cloud credential file. Cloud apply and destroy remain explicit owner actions because they create cost and mutate an external project.

Workload Identity Federation authenticates the gateway to Google Cloud, not a human or A2A client to the gateway. It cannot establish task tenancy or authorize operational writes.

The authenticated host path needs no cloud account and proves application-level audit behavior. Local Kubernetes remains write-frozen until a caller identity substrate exists.

## What evidence belongs in a release decision?

A release decision needs one clean source identity and evidence scoped to its revision and tree digest.

The sanitized evaluation contract supplies:

- `eval-results.json`, including typed source and platform identity, model identity, evalset digest, release-policy version and digest, policy-derived minimum, required-case verdict, and deterministic scores;
- `judge-calibration-results.json`, including the same source/policy tuple, typed judge provider/name/digest, calibration digest, policy-owned agreement floor, and per-case match verdicts;
- `cost-observed.json`, when a reviewed model run records positive token and model-call usage;
- OpenTelemetry spans and metrics named `agentops.eval.*`, when an explicit evaluation exporter is configured;
- the later image digest, scan, smoke result, and attestation for the exact artifact considered for deployment.

Prompts, answers, tool arguments, tool responses, judge rationales, provider errors, endpoints, and credentials are forbidden from the release artifacts. A green offline suite proves the harness and assets; it does not prove a model-backed run, deployed image, hosted workflow, or public release.

**You are done when:**

- You can join an approved action to its actor, approver, rationale, session, invocation, and target.
- You distinguish the authenticated host write path from the account-free, write-frozen Kubernetes profiles and from seeded backup evidence.
- You describe the SQLite trail as application append-only, never immutable.
- You can name the retention owner and erasure limitation for each evidence store.
- You can list the release verdict fields without exposing model or tool content.
