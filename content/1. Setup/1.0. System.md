{{% admonition abstract "In one glance" %}}

- **You will:** Install mise, trust this checkout's task files by name, and run a clean clone all the way to a green offline suite.
- **You need:** Git, a Unix-like shell, and permission to install tools into your own user account. No model, no container engine, no cluster, no cloud project.
- **Time:** about 20 minutes, hands-on. {{% /admonition %}}

## The toolchain is the bug nobody can see

You push a one-line change. The reviewer's machine goes red on a lint rule yours never mentioned, the diff is empty, and half a day later somebody notices that their `golangci-lint` is two minor versions behind yours. Nothing was wrong with the code. Two machines were simply never running the same program, and no test could have caught that, because the tests themselves were the thing that differed.

This repository answers that by pinning every command-line tool it shells out to — the Go toolchain, the linters and formatters, the documentation builder, the SQLite CLI — in one table in the root `mise.toml`, and by shipping one command whose entire job is to compare that table against your machine.

You will run it yourself two sections from now, as soon as mise itself is on your machine:

```bash
mise run doctor
```

Here is what it says before anything is installed. Every line names a tool and the remedy for it, and the run exits non-zero. This is a real run with `PATH` stripped down to the few shell utilities the script itself calls, so nineteen tools come back missing; these are its first four lines:

```text
missing: go                       remedy: mise run install
missing: hugo                     remedy: mise run install
missing: golangci-lint            remedy: mise run install
missing: gotestsum                remedy: mise run install
```

Nine more mise-managed tools follow with that same remedy. Then come six the repository does not own — `git`, `curl`, `cc`, `install`, `make`, and `tar` — and each of those points at a reviewed host package source instead, because no repository installer can conjure a C compiler. The run closes by telling you to re-run the doctor for the profile you asked about.

That is the whole contract of this page: nothing here fails with a bare `command not found` from four levels down a task chain.

{{% collapsible note "Deeper: which hosts are exercised, and which are best-effort" %}}

The doctor reads your tools. It has no opinion about your operating system, and the course's answer there is a matrix rather than a yes.

| Host                        | Status          | What that means here                                                        |
| --------------------------- | --------------- | --------------------------------------------------------------------------- |
| Linux x86_64 with cgroup v2 | Fully supported | Offline checks, containers, k3d, and host observability are exercised here. |
| Linux arm64                 | Best-effort     | Go builds are portable; pinned third-party images and tools may differ.     |
| macOS                       | Best-effort     | Offline Go and docs work; container networking follows the desktop runtime. |
| WSL2                        | Best-effort     | File permissions, cgroups, and host networking depend on the WSL setup.     |

Everything on the required path — the offline checks, the local model, the agent itself — works on all four. What is only exercised on the first row is the heavier optional half: containers, the local cluster, and host observability. `SUPPORT.md` owns this matrix and its deprecation policy. {{% /collapsible %}}

## Install mise, then trust five files by name

Get the source first. Every command on this page resolves against a path inside the checkout, so there is nothing to trust until one exists:

```bash
git clone https://github.com/MLOps-Courses/agentops-open-course-go.git
cd agentops-open-course-go
```

Install [mise](https://mise.jdx.dev/) from its official instructions and activate it in your shell. Then tell it, file by file, which task definitions in this checkout you are willing to execute:

```bash
mise --version
mise trust mise.toml
mise trust agents/go/mise.toml
mise trust agents/data/mise.toml
mise trust evals/mise.toml
mise trust tools/mise.toml
```

Five commands where one would do, and the one is the problem. Trusting everything at once — the `--all` form of that command — walks parent directories and unrelated nested configurations, so on a laptop with several checkouts under one directory it can quietly approve task files you have never read. Naming each file is slower to type and impossible to get wrong. Mise can also share trust between linked Git worktrees, which is another reason to look at what you are approving.

If `mise --version` prints a version but a later task still runs the wrong tool, mise is installed without being activated: restart the shell and check again.

## Four commands take a clean clone to green

One of them builds SQLite from source, so the C toolchain the doctor named has to be there first. Install it from a reviewed host package source, the line that matches your system:

```bash
sudo apt install build-essential   # Debian and Ubuntu
sudo dnf group install development-tools   # Fedora
xcode-select --install   # macOS
```

Then run these in this order, from the repository root:

```bash
mise run install
mise run doctor
mise run check:core
mise run test
```

`install` resolves the three Go modules, materializes the Hextra documentation theme, rebuilds the SQLite CLI from a checksum-verified upstream archive, and connects the Git hooks to the same tasks you just ran. `doctor` reports the base profile. The last two are the interesting ones, and neither makes a model call, opens a network connection to a provider, or reads your `.env`.

Predict before you run them: how long should a repository that contains an AI agent, an evaluation harness, and a documentation site take to check itself?

`check:core` takes a couple of minutes and is noisier than you expect, because it lints the shell scripts, parses every inline mise task body under its configured shell, and security-reviews the GitHub Actions workflows. These are its last three lines:

```text
[check:shell] GKE model smoke context, payload, retrieval, and fail-closed checks passed
[check:shell] Finished in 147.17s
Finished in 147.91s
```

`mise run test` then runs all three module suites. The agent's own suite ends with a per-package coverage report rather than one flattering total:

```text
DONE 1815 tests, 1 skipped in 4.826s
[test] $ ../../scripts/check-coverage.sh coverage.out 80 agents/go
  ok      84.2%  agents/go/a2aserver
  ok      91.7%  agents/go/compose
  ok      91.0%  agents/go/config
  ok     100.0%  agents/go/model
  ok      98.5%  agents/go/tools
agents/go meets the 80% per-package coverage floor
```

That is one real run, trimmed: twenty packages are reported and five survive here, and the timing is a warm cache — a first run compiles everything and takes minutes rather than seconds.

The one skip is deliberate, not a broken machine. `a2aserver`'s `TestPostgresSessionProbeAgainstARealServer` needs a live PostgreSQL, so it skips whenever `AGENT_TEST_SESSION_DSN` is unset and prints the `docker run` command that would un-skip it. Everything the account-free path promises is in the 1,814 that ran.

**You have just verified an agent's composition, configuration, persistence, and policy plane on your own machine, offline, in about three minutes.** What that green run cannot tell you is whether the agent reasons well, because nothing in it called a model; [0.2. Evidence]({{< relref "/0. Overview/0.2. Evidence.md" >}}) owns that distinction and every later page links there rather than repeating it.

Formatting is a separate verb on purpose. `mise run format:core` rewrites files, so run it deliberately and read the diff; `mise run build:docs` renders the site into `site/` and fails on any warning.

## Each doctor profile checks one tier and stops

There are five profiles, and the tool lists they compare against live in the script rather than in this page:

{{< include path="scripts/doctor.sh" region="doctor-tool-tiers" lang="bash" >}}

The base doctor checks mise-managed `actionlint`, `dprint`, Go, `golangci-lint`, `gotestsum`, Hugo, `jq`, `lychee`, `shellcheck`, `shfmt`, `sqlite3`, `trivy`, and Zizmor, plus the six host prerequisites named above. Each heavier profile adds its own tier on top:

- **model** adds Ollama and the configured local model.
- **gateway** adds Docker, OpenSSL, and mise-managed `yq` plus the pinned host gateway wrapper.
- **platform** checks `age-keygen`, `agentgateway`, `helm`, `helmfile`, `k3d`, `kube-linter`, `kubeconform`, `kubectl`, `promtool`, `rg`, `skaffold`, `sops`, plus the gateway tier.
- **gcp** checks `gcloud`, `gke-gcloud-auth-plugin`, `helm`, `helmfile`, `kubeconform`, `kubectl`, `rg`, `skaffold`, `tflint`, and `tofu` plus the gateway tier.

Run only the profile the page in front of you names. `mise run install:platform` provides the platform tier; the repository deliberately installs no Google Cloud CLI components, so `gcloud` and `gke-gcloud-auth-plugin` come from the same reviewed Cloud SDK or host package source as the rest of your system, and `mise run doctor:gcp` then verifies the whole live path.

A doctor result says the prerequisites are present, and nothing else. It does not claim the application works, the model answers well, a deployment is healthy, or a release is fit to ship.

## Your turn: read the list the doctor is checking against

The doctor prints failures, not its reasoning. There is a flag that prints the reasoning, and reading it once tells you exactly which parts of your machine this course owns and which parts it merely requires.

Predict first: of the tools the base profile needs, how many can `mise run install` provide, and what is the C compiler for?

- **Mode**: `inspect` — the flag only prints; it installs and checks nothing.
- **Goal**: separate the tools this repository pins from the prerequisites your host owns, and explain why the split exists.
- **Files to touch**: none.
- **Preflight**: `mise run doctor` exits zero.
- **Steps**: from the repository root run `./scripts/doctor.sh --requirements base`, then `./scripts/doctor.sh --requirements platform`, and compare the two lists. Each line is a tool and its remedy, separated by a tab.
- **Gate that proves completion**: you can name the six tools whose remedy is a host package source rather than a repository task, and say which install step needs `cc`, `make`, and `tar`. Read `scripts/install-sqlite.sh` if the answer is not obvious — it downloads one upstream SQLite archive, verifies its SHA-256, compiles it, and asserts the resulting binary's version.
- **Final state**: no files changed, no tools installed.

The answer matters beyond trivia: a repository that compiled its own SQLite from a moving plugin would be trusting bytes nobody reviewed, and a repository that trusted whatever `sqlite3` your distribution shipped could not promise that `agents/data/incidents.db` is reproducible. Both promises cost you one C compiler.

## What you can do now

- `mise run doctor` reports the base profile ready, and you can read its failure output as a tool-and-remedy list rather than as noise.
- `mise run check:core` and `mise run test` both pass on your machine, with no model, no container engine, and no network.
- You trusted five named task files instead of broadening the operation to everything under your home directory.
- You can say which doctor profile a later page needs, and why a green one never implies the next.

An hour ago this was an unfamiliar checkout. It is now a machine where every tool that decides a verdict is pinned, and where the difference between "the code is wrong" and "your toolchain is different" is one command away.
