## Documentation rots quietly, so this repository checks it

A tutorial tells you to open a Go file. The file was renamed eleven months ago. Nothing failed, nobody noticed, and the only cost was a reader's afternoon — which is exactly why prose drift is the most durable form of technical debt in a teaching repository.

So the course pages are checked like source. Here is what happens when a page names a file that does not exist; the offending sentence was appended to this very page, and the checker was run from the repository root:

```bash
tools/bin/conventions docs
```

```text
content/1. Setup/1.5. Workspace.md: line 105: literal repository path does not exist: agents/go/nope.go
```

Line 105 is two past the last line of this page as it ships, which is where an appended sentence lands. Delete it, run the same command, and the checker goes quiet and exits zero.

That checker is not a spell-checker with ambitions. It reads every page against the actual repository: file paths must exist, `mise run` tasks must be declared in a manifest, quoted tool versions must equal the pins, included source regions must exist with one start and one end marker, and every Mermaid diagram must have a prose alternative beside it. When a maintainer renames a task, the page that documented it fails before the rename is committed.

**You have just watched documentation get treated as something that can be wrong, rather than as something that is merely old.**

## Source is authority; everything else is disposable

The workspace has exactly one rule underneath all of the others: a small set of files decide what is true, and everything a command produces is a record of one moment rather than a fact about the project.

Authority lives in `mise.toml` for task names and pinned tools; in `agents/go/go.mod`, `evals/go.mod`, and `tools/go.mod` for declared dependencies, with their `go.sum` files owning exact resolution; in `AGENTS.md` for repository invariants and operating limits; and in `dprint.json` plus the three `.golangci.yml` files for mechanical style. Use whatever editor you like, as long as it can run `gopls` and you let the repository's own formatters have the last word — `mise run format` is the arbiter, not your editor's plugin.

Everything in this list is generated, ignored by Git, and safe to delete — and none of it should ever be cited as a source of truth:

- `agents/go/.state/` holds the writable runtime databases and crash-recovery journals.
- `site/` holds the rendered documentation site.
- `coverage.out` and its reports are local measurements.
- `results.json` and any artifact named by an `--output` flag record one run and nothing more.
- `.env` and local credentials are private configuration.

One exception hides inside the first bullet, and it is worth a sentence now so it does not surprise you in Chapter 2. A dot-prefixed `.restore-*` file in the state directory is not stray litter to be tidied away because a status command is noisy: it is the journal a half-finished state restore left behind, and it records which copy of the data was real. Read one before you remove it. [2.4. Sessions]({{< relref "/2. Agents/2.4. Sessions.md" >}}) has you plant one on purpose, watch startup refuse to guess at it, and then delete it deliberately — which is the difference between clearing an artifact you understand and clearing one you do not.

The repository holds three independent Go modules for a related reason: the black-box evaluation harness must reach the agent over the wire, so it is kept unable to import agent internals at all. And when you do change a fact, change its owning source, its test, and its public contract together — never copy a dependency version into prose when you can link to the lock that owns it.

## The hooks run the tasks you already ran

Local hooks are a second implementation of CI in most repositories, which is why they drift and then get bypassed. Here they are thin: lefthook only calls `mise run` tasks, so a hook and a workflow cannot disagree about what "checked" means.

**pre-commit** formats staged Go, Markdown, and configuration, then runs path-scoped checks and a staged secret scan. **pre-push** runs the model-, container-, cluster-, and cloud-free core check plus the full test suite. Both are fast local guards: bypassing a hook relaxes nothing, it only moves the failure later. Hosted CI prepares the same deterministic surface with `mise run install:validation`, which installs the account-free validation CLIs and starts no model or platform service.

Choose the smallest check that honestly settles what you changed:

| Moment                | Command                                           | What it decides                                           |
| --------------------- | ------------------------------------------------- | --------------------------------------------------------- |
| While editing Go      | module-local `mise run check` and `mise run test` | Formatting, lint, race-tested behavior, measured coverage |
| While editing docs    | `mise run check:docs` and `mise run check:links`  | Page contracts, the rendered site, and local links        |
| Before pushing        | `mise run check:core` and `mise run test`         | The whole deterministic repository                        |
| Maintainer validation | `mise run check`                                  | Core plus infrastructure, licences, and security profiles |
| Release candidate     | configured `eval:*` and platform smoke tasks      | Model and runtime behavior tied to one source commit      |

`mise run test` enforces the 80% per-package line-coverage floor in `agents/go` and `evals`; `tools/` is maintainer scaffolding and sits outside it deliberately. Report a measured percentage next to the floor it cleared, and remember that neither number says the tested behavior is right — [0.2. Evidence]({{< relref "/0. Overview/0.2. Evidence.md" >}}) explains why that distinction is the one this course refuses to blur.

One more habit, and it costs nothing: run `git status --short` before you start and after you finish. A dirty worktree you did not create is not a failure, it is someone else's work — scope your formatting and your restores to the files you actually own.

## Your turn: break a different rule and predict which checker names it

You have seen the checker catch a path. Now find out how specific it gets about something a human eye would slide straight past.

Predict first: this course's Markdown style requires every ordered-list item to be written `1.`, so the numbering stays dynamic when the list is edited. If you write `2.` instead, does the checker ignore it, reformat it, or refuse?

- **Mode**: `temporary experiment`.
- **Goal**: watch the documentation checker name a file, a line, and the exact rule, then restore the page and watch it go quiet.
- **Files to touch**: only this page. The Go modules, the seed data, and your `.env` are untouched.
- **Preflight**: confirm the page is unmodified with `git diff --quiet -- "content/1. Setup/1.5. Workspace.md"`, which prints nothing and exits zero when it is clean.
- **Steps**: from the repository root, append a bogus list item with `printf '\n2. A renumbered list item.\n' >> "content/1. Setup/1.5. Workspace.md"`, then run `tools/bin/conventions docs` and read the failure.
- **Gate that proves completion**: the checker exits non-zero and names the file, the line, and the rule:

```text
content/1. Setup/1.5. Workspace.md: line 105: ordered Markdown items must use `1.`, not `2.`
```

- **Final state**: restore the page with `git restore -- "content/1. Setup/1.5. Workspace.md"`, then run `tools/bin/conventions docs` again and confirm it prints nothing and exits zero.

The rule itself is minor. What is not minor is where it lives: this is a Go test in `tools/internal/conventions`, run by the same `mise run check:docs` that the hook and CI call, so a documentation contract is enforced by the same machinery as a compiler error. When Chapter 4 asks you to add a rule of your own, that is the seam you will extend.

## What you can do now

- You made the documentation checker fail on a page, read the file, line, and rule out of one message, and restored it to green.
- You can say which files are authority, which are disposable records, and why a `.restore-*` journal is neither.
- You can pick the smallest check that honestly settles the change in front of you, and name what each one leaves open.
- `git status --short` shows only changes you meant to make.

An hour ago "the repository is clean" was a feeling. It is now a checkable claim: a checker that reads your prose against the code, a hook that runs the same tasks you do, and a coverage floor that reports per package instead of hiding behind a total.
