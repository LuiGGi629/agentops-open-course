- **You will:** Verify the workspace contract and understand what local hooks and repository gates enforce.
- **You need:** The base installation from 1.0 and a clean view of your current Git changes.
- **Time:** about 20 minutes, hands-on. {{% /admonition %}}

## What defines the workspace contract?

Source files and lockfiles are authority; generated state is disposable evidence.

- `mise.toml` owns task names and pinned tools.
- `agents/go/go.mod`, `evals/go.mod`, and `tools/go.mod` own declared dependencies.
- Their `go.sum` files own exact module resolution.
- `AGENTS.md` owns repository invariants and safe operating boundaries.
- `.editorconfig`, `dprint.json`, Go formatters, and lint configuration own mechanical style.

The repository contains three independent Go modules so the black-box evaluation harness cannot silently depend on agent internals.

## How do you confirm your workspace is ready?

Inspect before changing anything:

```bash
git status --short
mise current
mise run doctor
```

An existing dirty worktree is not a failure. It is a boundary: preserve changes you did not create, and scope formatting or restoration to files you own.

## What is generated and must never be committed?

Generated output must not become accidental source authority.

- `agents/go/.state/` contains the writable runtime database and recovery evidence.
- `site/` contains the rendered Hugo site.
- `coverage.out` and related reports are local measurements.
- `eval-results.json`, task-specific result artifacts, and `cost-observed.json` are run evidence unless a release workflow explicitly packages them.
- `.env` and local credentials are private configuration.

Never remove unexplained restore journals or another process's state merely to make a status command quiet.

## Which editor should you use?

Use any editor that respects EditorConfig and can run Go language tooling.

Useful integrations provide `gopls`, Go formatting, TOML/YAML schemas, Markdown diagnostics, and an EditorConfig client. The repository formatter remains authoritative when an editor disagrees.

## How should a coding agent use AGENTS.md?

An automated contributor should read the nearest `AGENTS.md` before editing and treat source plus tests as executable authority.

The repository guidance records trust boundaries that formatting cannot reveal: seed versus state, read versus write authority, gateway-only remote tools, content-minimized telemetry, and no live service in deterministic gates.

When a fact changes, update its owning source, test, and public contract together. Do not copy dependency versions into prose; link to the lock authority.

## How do you validate the agent configuration?

Use the typed Go boundary instead of interpreting environment variables by eye:

```bash
mise run config:check
```

The command parses provider, URL, timeout, identity, state, telemetry, and guardrail settings. It masks secrets and exits non-zero on invalid cross-field combinations.

Model-backed tasks may load the repository `.env`; deterministic format, lint, test, docs, and evaluation-asset validation do not.

## What do the Git hooks enforce?

Lefthook delegates to repository tasks so hook behavior does not become a second CI implementation.

- **pre-commit** formats staged Go, Markdown, and configuration, then runs path-scoped checks and staged secret detection.
- **pre-push** runs the model-, container-, cluster-, and cloud-free core gate.

Hooks are a fast local guard, not hosted-CI or release proof. Bypassing a hook does not relax the required gates.

## Why do the hooks use the core gate?

The core gate is repeatable on a contributor machine and has no paid or stateful external dependency.

It checks Go modules, documentation, data, links, skills, shell, workflow syntax, and repository metadata without starting Ollama, Docker, Kubernetes, or cloud resources. Model-backed evaluations and platform smoke tests remain explicit evidence campaigns.

## Which gate runs at which moment?

Choose the smallest gate that honestly proves the boundary you changed.

Hosted CI prepares this deterministic boundary with `mise run install:validation`. That profile installs the account-free platform validation CLIs, but it starts no model or platform service and installs no cloud or release-only tool.

| Moment                | Command                                           | Evidence                                                  |
| --------------------- | ------------------------------------------------- | --------------------------------------------------------- |
| While editing Go      | module-local `mise run check` and `mise run test` | Formatting, lint, race-tested behavior, measured coverage |
| While editing docs    | `mise run check:docs` and `mise run check:links`  | Page contract, render, and local links                    |
| Before pushing        | `mise run check:core` and `mise run test`         | Complete deterministic repository behavior                |
| Maintainer validation | `mise run check`                                  | Core plus infrastructure, licenses, and security profiles |
| Release candidate     | configured `eval:*` and platform evidence tasks   | Model/runtime evidence tied to one source commit          |

No Go coverage threshold is enforced because the owner has not selected one. Report the measured percentage, but do not present it as policy.

## How would you add your own rule to the core gate?

Add one rule at the native repository-tool boundary, prove it with a focused Go test, then expose it through the existing task graph.

Keep the experiment scoped: one contract, one failing fixture, one correction, and no unrelated formatting. Run `cd tools && mise run test` before the root docs or core gate.

Rules that govern public course pages belong in `tools/internal/conventions`; rules that govern runtime behavior belong with the agent package that owns the behavior.

## What proves this page worked?

Run the workspace checks from the repository root:

```bash
mise run config:check
mise run check:format
mise run check:docs
mise run check:skills
git status --short
```

**You are done when:**

- Configuration parsing succeeds with secrets masked.
- Formatting, documentation, and skill checks exit zero.
- You can distinguish source locks, generated state, local measurements, and release artifacts.
- `git status --short` contains only changes you intentionally own.
