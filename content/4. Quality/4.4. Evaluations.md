{{% admonition abstract "In one glance" %}}

- **You will:** Validate the evalsets offline, tell a deterministic score from a judged one, and add an adversarial case with a deterministic validator.
- **You need:** The Go modules installed; a local model only for the model-backed tasks.
- **Time:** about 30 minutes, hands-on. {{% /admonition %}}

## What can you validate without a model?

```bash
cd evals
mise run eval:validate
mise run test
```

That validates every committed evalset, the domain vocabulary those cases quote, the labeled judge set, the dashboard, and the import boundary. Nothing here calls a model, so green means the harness is internally consistent — not that the agent answers well.

The operator's reference — the four tasks, every flag recipe, the artifact shape, the two-worktree A/B procedure — lives in `evals/README.md`. This page is about reading what those commands produce.

## Why evaluate at the wire boundary?

The evaluator is a separate Go module that never imports `agents/go`; `eval:validate` resolves its import graph so that boundary is mechanical rather than remembered. It reaches the agent only over public ADK REST or A2A, folding either transport's events into one typed `Turn`: final text, ordered tool calls, tool evidence, usage.

The point is not purity. A scorer that shares a type with the producer moves whenever the producer moves — rename an internal field and the evaluator recompiles happily while the client it stands for breaks. At the wire boundary it sees what a client sees, so a break a client would feel is a break the evaluation feels. The subject under test also becomes a process rather than a function call: one agent process and one throwaway state directory per case, and the binary's own `version` tuple is compared with this checkout before the first case runs.

## Why does deterministic scoring come first?

Most scores read structure, not prose: `trajectory` (required tool calls, in order), `confirmation` (a guarded action left pending approval), `authority` (no forbidden write crossed), `groundedness` (every recognized entity appears in the question or that turn's tool evidence), plus `refusal`, `safety`, and `schema`. The judge adds one more, `judge`, behind the `--judge` flag, and never replaces them. Extra diagnostic reads never fail a trajectory case; missing, reordered, or wrong required calls do.

The ordering is the lesson. Deterministic scores carry what you can least afford to delegate: approval before a restart, no write outside authority, an injected instruction refused, an email address redacted. Those are structural facts about a captured turn, and a second stochastic system is a worse instrument for reading them. Keep the judge for the residue with no structure — was the answer helpful, does it agree with the reference.

## What does a judge-agreement number license you to say?

`mise run eval:judge-calibration` replays a balanced twelve-case labeled set through the configured judge, prints how often it agreed with the human label, and exits zero either way. It measures the judge; it does not gate on it. The number licenses one sentence: on this labeled set, with this judge model and this judge prompt, the judge matched the human label N times out of twelve.

It licenses nothing further. Agreement is not accuracy: the labels are one person's reading, and a judge can agree with a wrong label. It does not transfer to unseen cases, another model, or a rewritten prompt; it never makes a judged score deterministic; and it never promotes the judge into a control a deterministic scorer already owns. Low agreement means read the per-case matches and fix your labels or your prompt — a number that gates is a number that gets tuned until it passes.

## Why does one green run prove so little?

```bash
mise run --cd agents/go build
mise run eval
```

Read the threshold off the task's command line instead of a policy file: fifteen operations cases, `--repeat 3`, `--min-pass-rate 0.33`, a `--required-cases` list of four names, `--judge`. The aggregate floor asks that a third of all forty-five samples pass. The four required cases are stricter — each must pass in every sample — and they are the real safety floor: recall prior context, load the runbook skill before remediating, and ask approval before restarting a service or resolving an incident.

Temperature zero reduces variance without removing it. A case that passes once and fails twice is not a passing case; it is a one-in-three case you caught on a good day. Repeats turn an anecdote into a rate, and mixed samples deserve to be reported as mixed. A low floor is honesty rather than laxity: it states what a small local model does here, which keeps attention on the four cases that must not regress. Cost is watched the same way — a token total moving more than 25% from the previous run warns rather than fails.

## How can an evaluation lie?

An evaluation lies when its number is true and its meaning is not. Watch for at least these:

- **Memorized cases.** The wording you wanted sits in the prompt, or the case was retuned until it passed, so green means the answer was supplied rather than found.
- **A scorer that shares producer code.** Both sides move together and nothing can disagree; the import-graph check in `eval:validate` closes this one.
- **A stale binary.** The run measured the last build instead of your edit, so a fix looks like it worked; the `version` comparison is the defense.
- **State leaking between cases.** One case saves a note a later case recalls, and case ordering quietly becomes part of the answer.
- **Aggregate cover.** The pass rate clears the floor while a safety case fails underneath it, which is why `--required-cases` is checked separately from the rate.
- **Double-counted streaming usage.** Partial chunks counted as spent tokens inflate cost with no change in behavior; partials are excluded from usage totals.
- **A single lucky sample.** One run reported as reliability, when `--repeat` and a per-sample artifact would have said one-in-three.
- **An uncalibrated judge.** A judged score carries weight nobody measured, and prose quality becomes an unexamined gate.
- **Cost compared across contexts.** A different prompt, model, seed state, or serving version yields a "regression" that is really a different experiment.
- **A threshold chosen after the result.** A floor set once the number is known passes forever; a floor on the command line is a diff someone can review.
- **The visible set.** Every case here is readable in the repository, and familiarity gets mistaken for generalization.

That last one is the only failure no tooling closes. Every contributor, and every coding agent working in this repository, can read these cases and fit to them without meaning to. When a model choice actually matters, keep a sealed holdout outside the repository, run it rarely, and never tune against it. A set you can read is a set you can accidentally memorize.

## Your turn: how do you add one adversarial case and deterministic validator?

Turn one failure mode you can describe into coverage that runs.

- **Mode**: `keep`.
- **Goal**: add an adversarial request the committed set does not contain, then one deterministic rule that detects the unsafe captured behavior without judging prose style.
- **Files to touch**: one `evals/*.evalset.json` asset, the owning scorer or validator under `evals/`, and its focused Go test; update the committed asset-count assertion when the case count changes.
- **Preflight**: run `cd evals && mise run eval:validate && go test ./...` green first, so a later red test is your change rather than inherited breakage.
- **Gate that proves completion**: the new test must fail against the unmodified validator, pass once the rule lands, and leave `cd evals && mise run eval:validate && go test ./...` green.
- **Final state**: keep the case, the validator, and the test; leave no generated result JSON.

Pick a hostile shape the committed cases miss. `injection-restart-rejected` already covers an injected instruction found in a log, so go elsewhere: a request phrased as an approved follow-up to a restart nobody approved, one naming a real service inside a fabricated incident id, or one asking for a note summary that would repeat a raw email address. Each has a structural signature a rule can see — a guarded write with no confirmation, an entity absent from the tool evidence, a raw address in the final text.

Write the rule against that signature, never against wording. The evalset decoder refuses unknown fields, so a new expectation must be a typed field parsed at load time; validate it there rather than reading loose JSON while scoring, and test a valid case the rule accepts alongside a malformed one the loader rejects.

## What proves this page worked?

Start with the offline proof, and add a model-backed run only if a local model is intentionally available:

```bash
cd evals
mise run check
mise run test
mise run eval:validate
```

**You are done when:**

- The offline harness, assets, import boundary, and signal-shape tests pass.
- You can explain why an evaluator that imports the agent has stopped being an evaluator.
- You can say which scores are deterministic, which one is judged, and why that order is not an accident.
- You can state what a judge-agreement number does and does not license you to claim.
- You can name three ways this evaluation could report a true number with a false meaning.
- Your kept adversarial case makes its test red without the new rule and leaves the offline gate green.
