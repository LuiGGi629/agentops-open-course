{{% admonition abstract "In one glance" %}}

- **You will:** Validate the committed evalsets offline, understand the wire-level scorers, and distinguish model-backed evidence from release qualification.
- **You need:** The Go modules installed; a configured local model only for live evaluation tasks.
- **Time:** about 42 minutes, hands-on. {{% /admonition %}}

## What can you validate without a model?

The standalone `evals` module validates schemas, domain references, report examples, the cost case set, dashboard JSON, and its import boundary offline:

```bash
cd evals
mise run eval:validate
mise run test
```

This proves the harness and committed assets are internally consistent. It does not prove that the agent passes a model-backed case.

## Why evaluate at the wire boundary?

The evaluator calls only public ADK REST or A2A endpoints. It does not require or import the agent module, and an import-graph test makes that separation mechanical.

Both transports fold captured protocol events into one typed `Turn` containing final text, ordered tool calls, tool evidence, usage, model-call count, and a provider failure code.

Fixture tests prove equivalent REST and A2A event streams produce equivalent turns. Streaming partials are excluded from token totals so repeated chunks cannot inflate cost evidence.

The wire boundary is the point: it sees what a client sees and cannot share an internal type that changes with the producer.

## Which evalsets ship?

| Asset                              | Purpose                                         | Cases |
| ---------------------------------- | ----------------------------------------------- | ----- |
| `evals/ops.evalset.json`           | Core conversational and guarded-action behavior | 15    |
| `evals/workflow.evalset.json`      | Bounded read-only workflow                      | 3     |
| `evals/triage-report.evalset.json` | Strict structured report                        | 3     |

The evaluator reads incident ids, services, statuses, and runbook slugs from immutable `agents/data`. Expected domain vocabulary never comes from an agent package.

These committed cases are visible development and release cases, not a secret holdout. A green result is evidence about this set only.

## What does trajectory scoring require?

Each invocation can declare required tool calls in order. The scorer checks that sequence as an ordered subset of observed calls.

Extra diagnostic reads do not fail a case merely because the model gathered more evidence. Missing, reordered, or wrong required calls do fail it.

`evals/release-policy.json` classifies every core case. Every safety-critical case, required capability, and case covering approval, write authority, injection, PII, or refusal must be mandatory regardless of aggregate rate. The evaluator rejects a policy whose cases drift from the core evalset.

The policy is currently `calibration-required`: its release pass and judge-agreement floors, repeat floor, and token/model-call budgets remain unset until repeated Go trials are reviewed. That is an explicit release block, not a missing learner exercise.

## How is groundedness checked deterministically?

The groundedness scorer extracts recognized incident ids, severities, services, and runbooks from the answer. Every claimed entity must appear in that turn's question or captured tool evidence.

The implementation lives in `evals/groundedness.go`. It treats ambiguous service words carefully and never looks at another turn's hidden state.

This detects unsupported domain entities. It does not judge every factual relationship or natural-language implication, so passing means “recognized entities are supported,” not “the answer is fully true.”

## How is structured output scored?

The report scorer requires one JSON object, refuses unknown fields and trailing values, then validates incident id, severity, affected services, hypothesis, evidence, runbook, and proposed actions.

Run three samples because a schema that succeeds once and fails twice is not a stable interface:

```bash
cd evals
mise run eval:report
```

This is model-backed. It starts an isolated agent process and state directory for each case, then removes them.

## How does cost scoring avoid silent regressions?

`evals/cost_baseline.json` records positive per-case token and model-call budgets. Cost scoring compares each captured case against its identified budget with a configured tolerance.

The committed baseline was inherited from the last fully attributed behavioral-reference run. It is schema-valid but is not proof of a Go-agent baseline.

Capture fresh Go evidence before proposing a replacement:

```bash
cd evals
mise run eval:cost:observe
```

The task writes `cost-results.json` and `cost-observed.json`. A maintainer must review the source identity, revision and tree digest, model digest, evalset digest, serving version, temperature, prompt selection, and positive usage before changing the baseline.

## What does the optional LLM judge add?

Deterministic scorers cannot reliably judge whether a natural-language answer is helpful, safe, and aligned with a reference. The optional judge sends a bounded prompt through the configured agentgateway model route and parses a strict verdict.

While policy approval is open, collect a balanced labeled observation without manufacturing a release floor:

```bash
cd evals
mise run eval:judge-calibration:trial
```

After approval, `mise run eval:judge-calibration` takes the exact accepted agreement floor from `release-policy.json`; passing `--floor` alongside that policy is rejected. Both governed core tasks use the calibrated judge, while approval, write authority, injection, PII, and refusal remain deterministic control scores. Calibration reduces evaluator drift; it does not make the judge objective or deterministic.

The judge must use the gateway boundary selected for the campaign. No live judge belongs in `check`, `test`, or `eval:validate`.

## Where does evaluation evidence go?

Set `EVAL_OTEL_EXPORTER_OTLP_ENDPOINT` to an explicit HTTP(S) collector endpoint to export evaluation evidence. The harness never inherits the agent's OTLP endpoint, and its child agent runs with telemetry export disabled.

Transport failures retain only repository-owned metadata: an HTTP status, JSON-RPC code, or SSE failure class. Non-success response bodies, SSE error data, JSON-RPC messages, and body-reader errors are discarded because a provider can place prompts, credentials, endpoints, or private diagnostics in them.

Stable spans are:

- `agentops.eval.run`
- `agentops.eval.case`
- `agentops.eval.score`

Stable metrics are:

- `agentops.eval.score`
- `agentops.eval.case.passed`
- `agentops.eval.tokens`
- `agentops.eval.model_calls`
- `agentops.eval.run.passed`

Attributes carry run id, typed source and platform identity, model, evalset, transport, case, sample, score name, and pass state. They do not carry prompts, answers, tool payloads, rationales, URLs, credentials, or provider errors.

Tempo, Prometheus, and Grafana visibility requires an explicitly started observability stack. Offline tests prove signal shape; they cannot prove a collector stored it.

## Which artifacts can qualify a release?

The canonical core task writes `evals/eval-results.json` and the matching `evals/cost-observed.json` from one model run. Judge calibration writes `evals/judge-calibration-results.json`.

Other tasks use distinct files so a scheduled campaign cannot overwrite release evidence:

| Task                              | Result artifact                               |
| --------------------------------- | --------------------------------------------- |
| REST policy-calibration trial     | `policy-trial-results.json`                   |
| A2A policy-calibration trial      | `a2a-policy-trial-results.json`               |
| Workflow                          | `workflow-results.json`                       |
| Structured report                 | `triage-report-results.json`                  |
| Canonical A2A qualification       | `a2a-results.json`                            |
| Cost enforcement                  | `cost-results.json`                           |
| Explicit cost re-baseline capture | `cost-results.json` plus `cost-observed.json` |
| Groundedness                      | `grounded-results.json`                       |
| Retrieval quality                 | `retrieval-results.json`                      |
| Prompt revision A/B               | `prompt-comparison.json`                      |

The run artifact includes schema version, run id, typed source and platform identity, sanitized model identity, evalset id and digest, transport, timestamps, per-case scores and usage, and a summary. A release-bearing run also records the reviewed policy version/digest and requires trajectory, judge, and control-specific scores. The calibration handoff carries the same source and policy plus typed judge provider/name/digest. Provider and artifact usage counters must be non-negative, and every sum is overflow-checked before comparison or budget enforcement.

The summary carries `pass_rate`, `minimum_pass_rate`, and `required_cases_passed`. The repository policy owns those settings; the command and candidate artifact do not. A release qualifier must match the artifact's policy identity and derived verdict against that reviewed source, not infer green from a file's existence.

## How do you run the model-backed campaign?

Build the agent, load the intended model configuration, and select the development task while release calibration remains open:

```bash
mise run --cd agents/go build
cd evals
AGENT_MODEL_TEMPERATURE=0 mise run eval:dev
```

`eval:dev` runs three samples at the visible learner floor of `0.33`; it is development evidence and cannot qualify a release. The canonical `eval`, `eval:a2a`, and judge-calibration tasks load `release-policy.json` and fail closed before inference while its status is `calibration-required`. After review populates the pass and judge-agreement floors, repeat floor, budgets, and `approved` status, the repository policy owns every release setting.

Maintainers collect the missing evidence from one clean candidate without manufacturing a release verdict:

```bash
mise run eval:policy-trial
mise run eval:a2a:policy-trial
mise run eval:judge-calibration:trial
```

Each task records three samples, every policy-mandatory outcome, and matching source and policy identity. An unsuccessful case remains a valid calibration observation, so the trial artifact is still published; only an infrastructure or evidence error stops collection. A green trial still cannot qualify a release.

Temperature zero reduces variance but does not remove it. Repeat stochastic paths when stability matters and report mixed outcomes.

## How do you compare two candidates?

Capture content-free artifacts from two Git-pinned prompt revisions with the same model, transport, evalset digest, and sample count, then run:

```bash
cd evals
BASELINE_ARTIFACT=../../agentops-baseline/evals/eval-results.json
CANDIDATE_ARTIFACT=../../agentops-candidate/evals/eval-results.json
mise run eval:ab -- \
  --baseline "$BASELINE_ARTIFACT" \
  --candidate "$CANDIDATE_ARTIFACT"
```

The prompt comparison requires distinct clean source revisions and matching model, platform, transport, evalset, case samples, and score names per sample. It recomputes pass rates and score means from those cases rather than trusting either artifact's serialized summary. [7.0. Reproducibility]({{< relref "/7. Observability/7.0. Reproducibility.md" >}}) owns the separate-worktree capture procedure.

## How can an evaluation lie?

Watch for at least these failures:

- Cases copied from the instruction or tuned repeatedly until memorized.
- A scorer that shares producer code or domain constants.
- Partial streaming usage counted more than once.
- Aggregate success hiding a failed critical case.
- A judge used without fresh calibration.
- Cost compared across different prompts, state, models, or serving versions.
- One lucky stochastic run presented as reliability.
- Sanitization that drops qualification fields or leaks model content.

Keep a sealed holdout outside the repository when making a high-stakes model choice. The committed sets cannot serve that purpose because every contributor can read them.

## How do you add a case?

Choose the evalset that owns the behavior, use only immutable dataset vocabulary, declare the minimum required trajectory, and avoid putting the desired prose in the prompt.

Then run:

```bash
cd evals
mise run eval:validate
mise run test
```

Run a live task only after offline validation passes. Record failures rather than weakening the case or scorer to fit one model response.

## Your turn: how do you add one adversarial case and deterministic validator?

Keep one new failure mode as executable evaluation coverage.

- **Mode**: `keep`.
- **Goal**: add an unseen adversarial request, then add one deterministic rule that detects the unsafe captured behavior without judging prose style.
- **Files to touch**: one `evals/*.evalset.json` asset, the owning scorer or validator under `evals/`, and focused Go tests; update the committed asset-count assertion when the case count changes.
- **Preflight**: require a clean focused diff and run `cd evals && mise run eval:validate && go test ./...`.
- **Gate that proves completion**: the new focused fixture is red before the validator change, then `cd evals && mise run eval:validate && go test ./...` is green.
- **Final state**: keep the case, validator, and tests; leave no generated result JSON or unrelated baseline change.

Choose a case that uses immutable seed vocabulary but a request the committed set does not already contain. For example, combine an injected log instruction with a read-only request and make the deterministic validator reject any observed guarded-write call. Parse the new external JSON field into a typed Go value at load time, reject unknown fields, and test both cancellation-free valid input and malformed input.

Do not encode the desired final sentence in the scorer. The case should specify observable trajectory or authority, and a later model-backed run remains separate stochastic evidence.

## What proves this page worked?

Start with offline proof:

```bash
cd evals
mise run check
mise run test
mise run eval:validate
```

If you intentionally have a local model running, add one model-backed task and retain its sanitized artifact.

**You are done when:**

- The offline harness, assets, import boundary, and signal-shape tests pass.
- You can explain how REST and A2A fold into the same `Turn` and why partials do not count toward usage.
- You can distinguish trajectory, groundedness, schema, cost, and calibrated-judge claims.
- You can name the three release-evidence artifact paths and the fields a qualifier must check.
- Any live result is tied to one typed source and platform identity, model identity, evalset digest, transport, and recorded minimum pass rate.
- You can state why these committed cases are not general correctness proof or a sealed holdout.
- Your kept adversarial case makes its focused validator test red without the new rule and leaves the complete offline eval gate green.

Continue to [4.5. Guardrails]({{< relref "/4. Quality/4.5. Guardrails.md" >}}) when a green run reads as bounded evidence, not a safety certificate.
