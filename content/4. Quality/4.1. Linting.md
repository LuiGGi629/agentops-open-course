## The error nobody read

Every guarded write in this agent ends the same way: the state change and its audit row commit together, or neither does. That guarantee lives in one transaction helper, and it rests entirely on a single error being checked. Imagine a tired refactor drops that check — `tx.Commit()` on its own line, return `nil`, ship it. It compiles. Every test that only asserts "no error came back" still passes. And from then on, a disk-full or lock-timeout commit failure is reported to Ana as a successful restart.

Make that edit — the exercise at the end of this page walks you through it and puts the file back — and run the analyzers over the package. The machine says it out loud:

```bash
cd agents/go
golangci-lint run ./data/...
```

```text
data/write.go:85:11: Error return value of `tx.Commit` is not checked (errcheck)
	tx.Commit()
	         ^
1 issues:
* errcheck: 1
```

**A correctness bug that compiled, that the focused tests waved through, and that would have told Ana a failed restart succeeded — caught by a machine that reads every line of every diff and never gets tired at 18:00 on a Friday.**

That is the class of defect this page exists for. Not style, not taste. The line number, the column, and the caret under the offending expression are the whole review comment, delivered before anyone had to volunteer to read the diff.

## Two commands, and a warning that counts as a failure

The module vocabulary is the same in every directory of this repository, which is the point:

```bash
cd agents/go
mise run format
mise run check
```

`format` writes; `check` only reads. Review what the formatter changed before you keep it, then let `check` fan out in parallel:

```text
[check:env-example] $ go run ./cmd/agent config:example --check ../../.env.example
[check:tidy] $ go mod tidy -diff
[check:lint] $ golangci-lint run ./...
[check:format] $ golangci-lint fmt --diff
[check:tidy] Finished in 129.9ms
[check:env-example] Finished in 334.4ms
[check:lint] 0 issues.
[check:lint] Finished in 1.60s
[check:format] Finished in 2.74s
Finished in 2.78s
```

Four checks, under three seconds, no model and no network. Treat the result as binary: a warning here is a failed correctness gate, not polish you will get to later. The moment one warning is allowed to survive, the next one has cover.

Three tools own Go source between them. `goimports` groups imports and applies base formatting; `gofumpt` adds a stricter, deterministic style on top; `golangci-lint` v2 checks that same formatter policy without writing, then runs the analyzers. Its configuration is deliberately explicit rather than clever: `version: "2"` selects the current schema, `formatters` enables `goimports` and `gofumpt` with this module's import prefix and extra rules, `linters` adds security, error-handling, SQL resource, structured-logging, spelling, performance, and unused-code checks, and `govet.enable-all: true` turns on every applicable `go vet` analyzer through the aggregate. Drop to raw `go vet ./...` while you are diagnosing one analyzer's opinion, but keep `mise run check` as the gate that decides.

Known-vulnerability analysis is a different kind of question and lives on a different boundary. `mise run check:vuln` runs `govulncheck` across the `agents/go`, `evals`, and `tools` modules, and it needs the network, so it stays out of the per-commit gate. An offline commit must remain possible, and a stale or unreachable advisory database is not evidence that your dependencies are clean.

## Which checker owns which file

Go is the loudest surface, not the only one. Each of the others has exactly one owner, so a failure always names a tool you can run by hand:

| Surface                       | Primary checker                            |
| ----------------------------- | ------------------------------------------ |
| Go source and imports         | `gofumpt`, `goimports`, `golangci-lint` v2 |
| Markdown, JSON, TOML, YAML    | dprint                                     |
| Course structure and includes | Repository convention checker              |
| Shell                         | ShellCheck plus repository contract checks |
| Workflows                     | actionlint, offline Zizmor, pinned actions |
| Kubernetes and OpenTofu       | Renderers plus configuration scanners      |

An aggregate of analyzers is only worth its noise if every finding is actionable, which is why each enabled linter here answers a failure class that exists in this codebase: an ignored error, a leaked response body, an SQL handle left open, a malformed structured log, an accidental copy. Adding an analyzer that fires on nothing real teaches the team to skim.

When one of them is wrong, prefer changing the code. When it is wrong at exactly one site, scope the exception to that one rule and leave the reason beside it: there are four `//nolint` lines in this tree, and each names its rule and its reason on the line it protects.

Then open `.golangci.yml` and notice that the repository also carries two exclusions considerably wider than that. Test files are exempt from `gosec`, because fixtures deliberately construct the hostile inputs production code has to reject. And eight `gosec` rules — G304 file paths, G204 subprocesses, and six more — are switched off for every package in the module, production included. Read that second list the way you should read any list like it in a repository you inherit: as a debt you can see, not as a policy to copy. What is never acceptable is adding a suppression to force a green run, because the guardrail you disable to ship on Friday is the one that was about to catch Monday's incident.

Course pages are checked the same way, because they are executable interface documentation. The convention gate reads front matter, headings, navigation, source includes, link labels, diagrams, and closing contracts, and Hugo then renders with warnings treated as errors — so a page that quotes a source region which no longer exists fails before the site can ship misleading code.

None of this is duplicated between your machine and CI. Git hooks delegate to mise instead of copying flags, and hosted CI invokes the same repository tasks on a clean runner: the validation job installs the account-free tier with `install:validation` and then runs the base doctor, the checks, and the tests, while the documentation workflow installs only its pinned documentation and browser toolchains before rendering and the browser checks. Those are two jobs in one `ci.yml`, not two pipelines you have to keep in step, and neither starts a model, a platform service, or a cloud tool. What that alignment proves is command equivalence. A green run here is evidence about the tree in front of you, not about a future commit on a hosted runner — see [0.2. Evidence]({{< relref "/0. Overview/0.2. Evidence.md" >}}).

## Your turn: make the linter catch you

Reproduce the opening capture on your own machine, so that the next time you see an `errcheck` line you already know what it costs.

- **Mode**: `temporary experiment`.
- **Goal**: drop the commit error check in the guarded-write transaction, watch static analysis catch what the compiler waved through, then restore the file.
- **Files to touch**: `agents/go/data/write.go` only. Do not edit any test.
- **Preflight**: require `git diff --quiet -- agents/go/data/write.go`, then run `cd agents/go && go build ./...` and `mise run check` green so a later red result is your edit and nothing else.
- **Steps**: in `inWriteTransaction`, replace the block that checks the result of committing with a bare `tx.Commit()` followed by `return nil`. Predict first: will the compiler complain? Will `cd agents/go && go test ./data ./tools -count=1` go red?
- **Gate that proves completion**: `cd agents/go && go build ./...` succeeds, and `golangci-lint run ./data/...` reports an unchecked error return value from `tx.Commit` under `errcheck` and exits non-zero.
- **Final state**: run `git restore -- agents/go/data/write.go`, then `cd agents/go && mise run check` is green again.

Both predictions resolve the same way, and that is the lesson. The build succeeds, and the focused test run reports `ok` for both packages, because nothing in the suite arranges for a commit to fail. Compilation answers "can this run" and the tests answer "does it do what the cases describe"; only the analyzer had an opinion about an error nobody read.

## What you can do now

- You made a real correctness bug appear and be caught by a machine, and you saw the compiler stay silent about it.
- You can run `mise run format` and `mise run check` from any module and read a warning as a failed gate rather than a suggestion.
- You can name the tool that owns a `.go`, `.md`, `.sh`, and workflow file, and say why `check:vuln` is not on the commit hook.
- You can find every suppression this repository carries — four `//nolint` lines with their reasons, and one module-wide `gosec` exclusion list — and say what each one costs.

A second reviewer now reads every line you write, has no opinions about your naming, and cannot be talked into approving a dropped error because the sprint ends tomorrow. Keeping its findings at zero is what makes the next page's red tests mean something: when the only noise is deliberate, a failure is information.
