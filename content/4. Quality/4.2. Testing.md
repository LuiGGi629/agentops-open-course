- **You will:** Run the offline suite and inspect how it controls state, model output, time, concurrency, and import boundaries.
- **You need:** `mise run install` done; no model, key, container, or network is required.
- **Time:** about 24 minutes, hands-on. {{% /admonition %}}

## How do you run focused and complete tests?

Use `go test` for a package while developing and `gotestsum` for the complete module gate:

```bash
cd agents/go
go test ./tools -run Test -count=1
mise run test
mise run coverage
```

The full task runs every package with `-race` and writes `coverage.out`. The coverage report is measured evidence only.

No Go coverage threshold is enforced because the owner has not selected one. Do not infer a pass policy from the current percentage or copy a measurement into governance prose.

## What should an agent prove offline?

Deterministic tests should cover:

- Configuration parsing and cross-field failures.
- Domain normalization and strict protocol decoding.
- Read tools, guarded writes, audit transactions, and idempotent replay.
- Policy ordering, redaction, injection handling, budget, and compaction.
- Sessions, A2A tasks, MCP filtering, cancellation, and drain behavior.
- Telemetry field shape and content-capture defaults.
- Static binary configuration and executable startup boundaries.

These properties do not need a generative model. Keeping them offline makes failure diagnosis fast and exact.

## How is state isolated?

Tests copy immutable seed data into a temporary directory and point every writable store there. The real SQLite implementation stays in the path, so transactions, constraints, locks, and migrations are exercised.

The committed `agents/data/incidents.db` must remain unchanged:

```bash
test -z "$(git status --porcelain agents/data/incidents.db)"
```

If that command prints a path, stop. A test or manual run crossed the seed/state boundary.

## Why use a scripted model instead of a real one?

A scripted implementation of ADK's `model.LLM` returns known sequences of text, tool calls, tool results, and usage metadata.

Only the stochastic boundary is replaced. The ADK runner, plugins, confirmation flow, sessions, tools, SQLite state, and telemetry remain real.

That shape proves composition and callback behavior without making the test suite depend on model availability, latency, or sampling.

## How does `testing/synctest` improve clock tests?

Retries, circuit resets, and concurrent waits are risky when tests depend on wall-clock sleeps. `testing/synctest` runs goroutines inside a virtual-time bubble.

The resilience tests advance timers deterministically and call `synctest.Wait` when they need every runnable goroutine to become durably blocked. Long cooldowns then complete quickly without a fake clock threaded through production APIs.

Use it for behavior driven by timers and goroutine scheduling. Keep ordinary pure functions as ordinary table tests.

## When is Rapid worth adding?

Rapid is a property-based testing library for generating many structured inputs and shrinking a failure to a small counterexample. It is useful for invariants such as parser round trips, identifier normalization, pagination tokens, and event folding.

The current module does not carry Rapid as a dependency; its reviewed table and concurrency tests already cover the committed invariants. Add Rapid only with a concrete property that ordinary examples do not express, then pin it in `go.mod` and keep the seed reproducible.

This is a dependency decision, not a reason to write random tests whose failures cannot be replayed.

## What does the race detector add?

`-race` instruments memory access and reports unsynchronized reads or writes exercised by the suite. It is particularly valuable for session serialization, index creation, circuit state, restore locks, and graceful shutdown.

A green race run does not prove all interleavings. It proves that the exercised concurrent paths produced no detected race on this run.

## Why keep real transactions in tests?

The guarded-action test must prove that operational state and the audit row commit together, and that a failure rolls both back.

A mocked repository can assert which methods were called but cannot prove SQLite locking, trigger behavior, atomicity, or crash-recovery journal semantics. Use a temporary real database for those claims.

## How do black-box tests prevent accidental coupling?

The `evals` module drives REST and A2A as a client. It deliberately does not require or import `agents/go`.

Its import-boundary test resolves the Go package graph and fails if an agent package appears. This mechanical rule prevents the evaluator from sharing producer types or implementation shortcuts.

## What can offline tests never prove?

They cannot prove that a live model chooses the right tool, that two stochastic runs are stable, that an OTLP collector stored evidence, that a browser works with a real gateway, or that a deployed cluster drains correctly.

Chapter 4.4 owns model-backed evaluation. Chapters 5–7 own gateway, platform, and observability evidence. Hosted CI, runtime, and release proof remain distinct from local tests.
