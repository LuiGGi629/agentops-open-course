## What can you prove offline first?

Run the deterministic policy, action, and webhook tests:

```bash
cd agents/go

```

These tests use fixed inputs, scripted model output, and local HTTP fixtures. They do not call a live model or gateway.

## What is a guardrail?

A guardrail is a boundary that constrains what data or action may continue. It can reject, mask, require confirmation, roll back, or emit evidence.

No single guardrail makes an agent safe. The course composes types, domain validation, least-privilege tools, PII handling, injection controls, deadlines, human confirmation, transactions, and audit evidence.

## How is policy attached to every agent?

One ADK plugin is registered at the application boundary:

{{< include path="agents/go/policy/policy.go" region="policy-plugin" lang="go" >}}

Its hooks cover the conversational agent, sub-agents, workflow nodes, and coordinator. Adding another agent therefore does not silently lose budget, redaction, injection, or error handling.

Before-model order is budget, compaction, then redaction. The first non-nil result short-circuits the remaining guards; tests pin this order.

## What does PII Layer 1 cover?

Layer 1 runs in process, on every agent path, with no network or model. It masks:

- Email, phone, US SSN, and Canadian SIN shapes.
- Luhn-valid payment cards and checksum-valid IBANs.
- IPv4, IPv6, and MAC addresses where the boundary policy permits them.
- Common credential assignments, bearer values, and provider token shapes.

It recursively redacts outbound model requests, inbound model responses, tool results, saved notes, and audit rationales at their owning boundaries.

Layer 1 is always required because it sees local logs, SQLite writes, and direct-model paths that a gateway cannot see.

## What can Layer 1 not detect?

It does not recognize arbitrary natural-person names, geographic locations, or organizations. Deterministic patterns cannot reliably decide whether “Jordan,” “Paris,” or “Apple” is sensitive in context.

It also does not certify that every future identifier shape is covered. False negatives and false positives remain possible, so raw content capture stays disabled by default.

This boundary is explicit: Layer 1 is strong for known shapes and checksum-backed values, not semantic named entities.

## What does gateway Layer 2 add?

agentgateway applies central request and response guards to every client of the model route:

1. Built-in rules mask SSN, payment card, phone, email, and Canadian SIN patterns.
1. A private Go webhook asks the already-required local Ollama model for `PERSON`, `LOCATION`, and `ORGANIZATION` spans.
1. The webhook validates byte ranges and exact substrings before masking them.

The detector calls Ollama directly through `/v1/responses`; calling back through agentgateway would recurse into the same guard.

Layer 2 is slower and non-deterministic. It is defense in depth at the gateway, not a replacement for in-process policy.

## How does the webhook fail closed?

The handler bounds body size, item count, text size, model response size, entity count, and deadline. It rejects malformed gateway payloads.

If the configured model times out, fails, or returns invalid spans, every non-empty inspected value becomes `<REDACTED>`. A reachable webhook never turns detector failure into pass-through.

agentgateway also configures the webhook with `failureMode: failClosed`, so an unreachable endpoint stops the guarded request rather than silently bypassing it.

`AGENT_PII_MODEL`, `AGENT_PII_MODEL_BASE_URL`, `AGENT_PII_MODEL_ENABLED`, and `AGENT_PII_MODEL_TIMEOUT_S` own this optional model boundary. The defaults select the local account-free model path.

## How are tool arguments constrained?

ADK decodes a declared JSON shape, then tools parse model-controlled identifiers into domain types and check target existence.

Reads return stable not-found or invalid-input results. Writes add a stricter sequence: supported action, valid target, configuration permits writes, ADK confirmation is present, approver/session/invocation identity is present, rationale is non-empty and bounded, and rationale is redacted.

An approval request is not an approval, and a model sentence claiming an action is not a tool call.

## Why are writes never retried automatically?

Read tools are idempotent and may use bounded retries. A write can change state and append audit evidence, so retrying after an ambiguous timeout risks duplication.

The retry type retains its final dependency error for Go error classification, but that chain is not safe model output. The policy extracts a separate first-party summary containing only the tool, attempt count, and `AGENT_MAX_RETRIES`; provider bodies, endpoints, paths, and driver details stay opaque.

Confirmed actions use an invocation identity as an idempotency key. A replay returns the original audit result without applying the mutation again.

## What makes state and audit atomic?

The action mutation and append-only audit insert share one SQLite transaction. Either both commit or both roll back.

Schema triggers block ordinary row update and delete, and every row carries its schema version. This is append-only application evidence, not immutable storage; an administrator with file or schema authority can still alter it.

## How does write freeze work?

`AGENT_WRITES_DISABLED=true` refuses every guarded action before state changes. Use it during an incident, investigation, or degraded approval path.

The flag is a process configuration control. It does not replace database permissions, gateway identity, or an external change-management policy.

## How is prompt injection handled?

Model prompts, tool results, MCP output, logs, and runbooks cross different trust boundaries. Every ordinary tool result is treated as data and wrapped or neutralized before the model reads it.

The locally constructed skill-loading tool is the narrow exception because its repository-reviewed body is instruction. The exception follows the concrete Go tool type, not a name a remote server could impersonate, and secret/PII redaction still applies.

## Which live exercise is optional?

The gateway exercise starts local model and gateway processes and therefore sits outside the offline gate:

```bash
mise run doctor:model
mise run doctor:gateway
mise run gateway:host:start
mise run smoke:host
mise run gateway:host:stop
```

Run it only when those dependencies materially validate the guard boundary. Keep every listener on loopback and stop the temporary gateway afterward.

Expected evidence distinguishes request rejection, request masking, response masking, and fail-closed detector failure. A passing offline test does not substitute for that live path.
