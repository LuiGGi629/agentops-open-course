## What does the compiler prove for an agent?

Go checks that values, methods, interfaces, and returns fit together before the binary runs. That removes broad classes of missing-method and wrong-shape failures.

Run the proof over every package:

```bash
cd agents/go
go build ./...
go test ./config ./domain ./tools -count=1
```

Compilation cannot prove that a model supplied a real incident id or that a database row obeys the domain. External data becomes trusted only after parsing.

## Why does type safety matter more around models?

A model produces probabilistic text and tool arguments. Treating decoded JSON as trusted merely moves uncertainty into the runtime.

The safe sequence is:

```text
untrusted bytes -> strict decode -> normalize -> typed domain value -> operation
```

This is “parse, do not validate”: perform validation while constructing a narrower type, then pass that type through internal code. Do not keep rechecking a raw string in every function.

## Where are the trust boundaries?

| Boundary            | Untrusted input            | Trusted result                                     |
| ------------------- | -------------------------- | -------------------------------------------------- |
| Environment         | Strings and missing values | `config.Config` with typed providers and durations |
| Model tool call     | JSON arguments             | Typed argument struct plus normalized domain ids   |
| A2A and REST        | Protocol JSON and metadata | Validated messages, tasks, and turns               |
| SQLite              | Rows and nullable columns  | Domain records or an explicit error                |
| Evaluation artifact | Captured protocol events   | Typed `evals.Turn` and sanitized result schema     |

Each parser fails at its own edge with a message that names the field or invariant.

## Which invariants deserve named types?

Use a typed enum when the valid set is closed, such as provider, entrypoint, severity, incident status, or A2A transport.

Use a parsing constructor when a string must satisfy structure, such as an `INC-123` incident id or kebab-case service slug. Internal functions then accept the normalized type.

Use a struct when fields belong together and partial construction would be ambiguous. Keep secrets in a wrapper whose normal formatting is masked.

## What happens when a model violates a tool schema?

ADK decodes the JSON shape into the declared argument struct. The tool still normalizes identifiers and checks domain existence before any operation.

For a read, an invalid model-controlled value returns a stable, user-facing result rather than a raw database error. For a guarded write, malformed arguments, missing confirmation, missing approver identity, or an invalid rationale fail before the transaction.

Generated JSON Schema improves the model's chance of proposing a valid call; it is not an authorization boundary.

## How are structured answers checked?

The evaluation harness decodes a triage report with unknown fields refused, requires one JSON value, and validates incident, severity, service, runbook, evidence, and action fields.

That scorer operates on captured output at the wire boundary. It does not import the agent's report type, so a coordinated internal change cannot make both producer and grader accept the same regression silently.

## Where do types stop helping?

Types do not prove that an answer is truthful, a tool call is well timed, a reviewer approved the right action, or an operator configured a trusted gateway.

Those properties need deterministic tests, trajectory and groundedness evaluation, policy controls, runtime observability, and human review.
