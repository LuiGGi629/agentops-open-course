## Green dashboards, wrong answers

At 09:40 the agent's dashboards are perfect. Availability 100%, p99 latency 900 ms, error ratio flat at zero, no alerts. At 09:41 Ana notices that every triage answer since the morning deploy has recommended a runbook for a service that does not exist in the seed. Nothing in the service metrics moved, because nothing in the service failed. The agent returned HTTP 200 as fast as ever, and it was wrong.

This is the whole reason an agent needs a scorecard rather than a dashboard. Availability and latency describe the pipe; they say nothing about what went through it. Agent quality needs five different classes of signal, and no single number summarizes all five honestly: deterministic software correctness, model behavior over fixed cases, cost and call usage, runtime RED signals and guardrail counters, and human review of the residue.

Some of those five have a command behind them:

```bash
mise run --cd agents/go coverage
```

```text
github.com/MLOps-Courses/agentops-open-course-go/agents/go/tools/tools.go:294:			newTool				80.0%
github.com/MLOps-Courses/agentops-open-course-go/agents/go/tools/tools.go:327:			describeProperties		100.0%
total:												(statements)			87.2%
```

Two function lines out of several hundred, plus the total the report ends with. Every part of that can be reproduced by anyone holding this repository. The number in the 09:41 story cannot, because nobody measured it. That gap — between a number with a command and a number with a memory — is what the rest of this page organizes.

## Gates, evidence, and where a threshold actually lives {#what-is-a-gate-and-what-is-evidence}

A **gate** is deterministic enough to block a change and to name the defect it found. **Evidence** informs a decision but varies between runs or needs infrastructure that may simply be absent. [0.2. Evidence]({{< relref "/0. Overview/0.2. Evidence.md" >}}) owns that distinction; this page only assigns each of the agent's signals to one side of it.

| Signal                                           | Default role           |
| ------------------------------------------------ | ---------------------- |
| Format, lint, compile, race-enabled tests        | Merge gate             |
| Eval asset and import-boundary validation        | Merge gate             |
| Model trajectory, grounding, schema, judge, cost | Commit-scoped evidence |
| Tempo, Loki, Prometheus, Grafana observations    | Runtime evidence       |
| Human review                                     | Decision evidence      |

Two mistakes cross that line in opposite directions, and both are common. The first turns stochastic output into an unexplained merge blocker, so the team learns to re-run the job until it is green. The second reads a missing runtime observation as a code failure, so someone "fixes" an agent that was never broken and only unobserved.

<a id="which-thresholds-are-policy"></a>Which leaves the question of where a threshold lives. In this repository the answer is deliberately boring: **only a threshold encoded in a task, a manifest, or an alert rule is policy.** Every evaluation threshold sits on the `eval` task's command line in `evals/mise.toml`, which means you can read the policy without opening a policy document:

```bash
cd evals
mise tasks info eval
```

```text
Run:
  go run ./cmd/agentops-eval run --evalset ops.evalset.json --entrypoint agent --transport rest --repeat 3 --min-pass-rate 0.33 --required-cases investigation-recalls-context,remediation-loads-skill,restart-needs-approval,resolve-needs-approval --judge --output results.json
```

Trimmed to the `Run:` block; the same command also prints the task's description, the file it came from, and its usage spec. There is the entire release policy for this agent's behavior on one line — three samples per case, a third of all samples must pass, and four named cases must pass in every single sample. Changing any of it is a diff someone reviews. The Go coverage floor qualifies the same way: the `80` sits on the `test` task's command line in `agents/go/mise.toml` and `evals/mise.toml`, which is why `mise run test` fails any package under it.

Two numbers are deliberately measured and not enforced. `mise run eval:judge-calibration` prints how often the judge agreed with a human label and exits zero either way, and a run whose token total moves more than 25% from the previous run prints a warning without failing. A number that gates is a number someone eventually tunes until it passes.

Keep the two roles of coverage apart when you write it down: the enforced 80% floor belongs in the policy column, and the measured 87.2% belongs in the scorecard with its command and its date.

## Which application metrics ship?

The Go agent emits a small, bounded set of custom signals — small because every one of them has to stay cheap to store and query:

| Name                                         | Meaning                                        |
| -------------------------------------------- | ---------------------------------------------- |
| `agentops.tokens`                            | Input and output tokens by direction           |
| `agentops.guardrails.injections_neutralized` | Untrusted-output injection markers neutralized |
| `agentops.triage_report.schema_failures`     | Structured reports rejected after validation   |
| `agentops.circuit.opened_total`              | Circuit transitions to open                    |
| `agentops.kagent.client.calls`               | Optional kagent calls by operation and outcome |

Session token totals and an estimated cost also travel as span attributes, with prices supplied by configuration and defaulting to zero for local models. Request rate, errors, and duration are derived by the collector from spans, so do not re-implement them in application code and then wonder which of the two to believe.

## The rules that keep a signal readable

The evaluator emits its own family — `agentops.eval.score`, `agentops.eval.case.passed`, `agentops.eval.tokens`, `agentops.eval.model_calls`, and `agentops.eval.run.passed` — attributed by run, commit, model, evalset, transport, case, sample, score, and pass state. Keep that family separate from the application one above. One describes a service answering live traffic; the other describes an experiment scoring a fixed set on whatever day somebody last ran it. Merge them into a single "agent quality" panel and the panel reads 99.4% on a Monday morning — a service success ratio, wearing a quality label, on an evalset nobody has run since Thursday, in front of a room deciding whether to release.

What never becomes a metric dimension is just as deliberate: prompt text, answer text, user, session, tool arguments, and trace id. Unbounded label values multiply series, wreck query performance, and quietly turn your metrics backend into an unsanctioned copy of your users' data. Segment on bounded operational dimensions — operation, model, error type, transport, score name, deployment — and reach for traces when you need to investigate one specific turn.

<a id="how-do-you-define-a-useful-slo"></a>A useful SLO needs four things and nothing else: one user-visible outcome, an indicator, a target window, and a named owner. "Successful read-only A2A requests under a stated latency objective over a stated window" is a contract; "the agent is fast" is a mood. This course ships demonstration alerts and budgets rather than a production SLO contract, because a real target has to come from your traffic and your capacity. Resist the temptation to make a quality score do an availability objective's job: page someone at 03:00 because last week's evalset scored 0.62 and they will spend an hour finding nothing wrong, because nothing is wrong right now. Release evidence and runtime objectives answer different questions on different clocks.

Finally, pair each metric with the one that punishes gaming it. Lower model calls against trajectory and groundedness. Higher pass rate against required-case status and a stable evalset digest. Lower cost against answer and schema quality. Lower latency against error ratio and cancellations. Fewer guardrail rejections against adversarial regression cases. If changing only the measurement can improve the score, the scorecard is not finished.

## Your turn: fill one scorecard row from a real command

A scorecard is worthless as a template and useful the moment one row is real. Build one row properly, and the shape of the rest becomes obvious.

- **Mode**: `inspect` — you run read-only commands and write down what they printed.
- **Goal**: produce three scorecard rows where each number names its command, its candidate, and its proof class, and mark every row you cannot measure as `unknown`.
- **Files to touch**: none. Keep your notes outside the repository.
- **Preflight**: `mise run --cd agents/go test` and `mise run --cd evals eval:validate` both exit zero.
- **Steps**: predict the agent module's measured coverage total before you look, then run `mise run --cd agents/go coverage` and record what it actually says; run `mise run --cd evals test` and record pass or fail; then try to fill the runtime latency row without starting anything, and notice what you are tempted to write.
- **Gate that proves completion**: your three rows each carry a command and a proof class, the coverage row shows the enforced floor and the measured percentage as two different things, and the latency row says `unknown` rather than a remembered number.
- **Final state**: no files changed in the repository; you keep the scorecard.

A finished scorecard usually carries these rows, and the right-hand column is the one people skip:

| Field                                       | Example source                                           |
| ------------------------------------------- | -------------------------------------------------------- |
| Candidate source tuple and clean-tree state | `tools/bin/source-identity --root . --mode release` JSON |
| Offline tests and race result               | `mise run test` in each Go module                        |
| Measured coverage                           | `mise run coverage` in the agent module                  |
| Evalset id and digest                       | `mise run eval` run artifact                             |
| Pass rate, minimum, required cases          | Run artifact `summary`                                   |
| Tokens and model calls                      | Run artifact per-case `usage`                            |
| Judge agreement                             | Calibration artifact                                     |
| Runtime rate, errors, latency               | Prometheus over a stated window                          |
| Trace or log observation                    | Tempo or Loki query with time window                     |

Write `unknown` when a value was not measured. A blank filled from prose is the 09:41 story starting again.

## What you can do now

- You can put any of this agent's signals on the correct side of the gate-versus-evidence line, and say what goes wrong when it lands on the other one.
- You can point at the exact command line where every enforced threshold in this repository lives, and name the two numbers that are measured instead.
- You built scorecard rows that each carry a command, a candidate, and a proof class, and you wrote `unknown` at least once.
- You can name a metric that improves when the agent gets worse, and the counterweight that catches it.

Take one finished row to whoever asks you next whether the agent is any good. The row will not answer yes. It will say what was measured, when, by which command, and against which candidate — and where nothing was measured it will say `unknown` rather than repeat a number somebody remembers. That is a smaller claim than a dashboard makes at 09:40, and it is the only kind that survives being checked at 09:41.
