## Why are ordinary service metrics insufficient?

Availability and latency can be healthy while an agent chooses the wrong tool, invents an entity, violates a schema, or doubles model calls.

Agent quality needs several signal classes:

- Deterministic software correctness.
- Model behavior over fixed cases.
- Cost and call usage.
- Runtime RED signals and guardrail counters.
- Human review of residual semantic quality.

No single number summarizes all five honestly.

## What is a gate and what is evidence?

A gate is deterministic enough to block a change with an actionable failure. Evidence informs a decision but can vary or require runtime infrastructure.

| Signal                                           | Default role           |
| ------------------------------------------------ | ---------------------- |
| Format, lint, compile, race-enabled tests        | Merge gate             |
| Eval asset and import-boundary validation        | Merge gate             |
| Model trajectory, grounding, schema, judge, cost | Commit-scoped evidence |
| Tempo, Loki, Prometheus, Grafana observations    | Runtime evidence       |
| Human review                                     | Decision evidence      |

Do not turn stochastic output into an unexplained merge blocker or treat runtime absence as a local code failure.

## Which thresholds are policy?

Only thresholds encoded in tasks, manifests, or alerts are policy.

Every evaluation threshold sits on the `eval` task's command line in `evals/mise.toml`: `--repeat 3`, `--min-pass-rate 0.33`, and the `--required-cases` list, whose four names must pass in every sample. Reading the policy is reading the task, and changing it is a diff someone reviews. Judge agreement and token cost are measured instead: `mise run eval:judge-calibration` prints an agreement number and exits zero, and a run whose token total moves more than 25% from the previous run prints a warning without failing.

The Go coverage floor qualifies by the same rule: the `80` sits on the `test` task's command line in `agents/go/mise.toml` and `evals/mise.toml`, so `mise run test` fails any package under 80% line coverage and moving that number is a diff someone reviews. The floor is the policy; the measured percentage is evidence, and it belongs in the scorecard with its command and date.

## Which application metrics ship?

The Go agent emits bounded custom signals:

| Name                                         | Meaning                                        |
| -------------------------------------------- | ---------------------------------------------- |
| `agentops.tokens`                            | Input and output tokens by direction           |
| `agentops.guardrails.injections_neutralized` | Untrusted-output injection markers neutralized |
| `agentops.triage_report.schema_failures`     | Structured reports rejected after validation   |
| `agentops.circuit.opened_total`              | Circuit transitions to open                    |
| `agentops.kagent.client.calls`               | Optional kagent calls by operation and outcome |

Session token totals and estimated cost also appear as span attributes. Prices are configuration, defaulting to zero for local models.

The collector derives request rate, error, and duration metrics from spans. Do not duplicate those in application code.

## Which evaluation metrics ship?

The evaluator emits:

- `agentops.eval.score`.
- `agentops.eval.case.passed`.
- `agentops.eval.tokens`.
- `agentops.eval.model_calls`.
- `agentops.eval.run.passed`.

Attributes include run, commit, model, evalset, transport, case, sample, score, and pass state. Prompt, answer, user, session, and trace id never become metric dimensions.

## How should metrics be segmented?

Use bounded operational dimensions such as operation, model, error type, transport, score name, and deployment.

Never label by prompt text, answer, user, session, tool arguments, or trace id. Unbounded values increase cost, harm query performance, and can leak sensitive data.

Use traces for individual high-cardinality investigations and metrics for aggregates.

## How do you define a useful SLO?

Choose one user-visible outcome, an indicator, a target window, and an owner. For example: successful read-only A2A requests under a latency objective over a stated window.

The course ships demonstration alerts and budgets, not a production SLO contract. A production owner must derive targets from real traffic and capacity evidence.

Quality scores over a fixed evalset are release evidence, not a runtime availability SLO.

## How do you prevent metric gaming?

Pair each metric with a counterweight:

- Lower model calls with trajectory and groundedness.
- Higher pass rate with required-case status and a stable evalset digest.
- Lower cost with answer and schema quality.
- Lower latency with error ratio and cancellations.
- Fewer guardrail rejections with adversarial regression cases.

If changing the measurement alone can improve the score, the scorecard is incomplete.

## What does a useful scorecard contain?

Record:

| Field                                       | Example source                          |
| ------------------------------------------- | --------------------------------------- |
| Candidate source tuple and clean-tree state | `source-identity --mode release` JSON   |
| Offline tests and race result               | `mise run test` in each Go module       |
| Measured coverage                           | `mise run coverage` in the agent module |
| Evalset id and digest                       | `mise run eval` run artifact            |
| Pass rate, minimum, required cases          | Run artifact `summary`                  |
| Tokens and model calls                      | Run artifact per-case `usage`           |
| Judge agreement                             | Calibration artifact                    |
| Runtime rate, errors, latency               | Prometheus over a stated window         |
| Trace or log observation                    | Tempo or Loki query with time window    |

Write `unknown` when a value was not measured. Never fill a blank from prose.

## What proves this page worked?

Collect the offline half:

```bash
mise run --cd agents/go test
mise run --cd agents/go coverage
mise run --cd evals eval:validate
mise run --cd evals test
```

**You are done when:**

- Every scorecard row names its command, candidate, and proof boundary.
- Coverage appears as both: the enforced 80% per-package floor in the policy column, the measured percentage in the scorecard as evidence.
- You can distinguish application metrics from evaluation metrics.
- No high-cardinality or content-bearing value appears as a metric label.
- A missing runtime or model-backed value is marked unknown instead of estimated.
