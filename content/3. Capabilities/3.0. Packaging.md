## The second binary is the one nobody validated

The second binary is always the one nobody validated. It starts as a convenience — a small MCP server here, a workflow runner there, each one obviously too simple to need its own review — and it ends at 02:14 with Ana holding two configuration paths, two build pipelines, and no idea which of them the failing process actually read.

This chapter hands the agent four new ways to be reached, and every one of them is a plausible excuse for that second executable. There is one binary. Build it and look:

```bash
cd agents/go
mise run build
./bin/agent version
```

```json
{
  "build_timestamp": "2026-08-10T20:12:50+02:00",
  "mode": "development",
  "version": "development",
  "source_identity": "f72b98b025ae35f644c865cd097b66155b3b0d04",
  "revision": "f72b98b025ae35f644c865cd097b66155b3b0d04",
  "tree_digest": "sha256:7c103f338448acc491d90f73de4908d76cb1e16d45614842a97353c7dd66ebe4",
  "dirty": false
}
```

Your hashes will differ — they are this checkout's revision and a digest of its whole tree, stamped in at link time so a running process can say exactly which source it came from. `mode` and `version` read `development` because `AGENT_BUILD_MODE` is unset; a release build reads the `VERSION` file instead.

The build sets `CGO_ENABLED=0`, which is a course invariant rather than an optimization. It is what lets the same file run inside a distroless image in Chapter 6, and what keeps one pure-Go SQLite implementation in the binary instead of a C library that has to be present on every host that runs it.

**You just built the whole agent — every composition, every transport, every tool — as a single self-contained file with no runtime dependencies.**

## The composition is one environment variable

That one file has to be told which agent to be, and it parses its environment and refuses bad settings before it constructs a runtime. Ask it what it resolved:

```bash
cd agents/go
./bin/agent config:check
```

```text
Agent configuration is valid. Resolved settings (secrets masked):
- AGENT_A2A_MAX_LLM_CALLS = 12
- AGENT_A2A_PORT = 8080
- AGENT_DATA_DIR = ../data
- AGENT_ENTRYPOINT = agent
- AGENT_MCP_URL = (unset)
- AGENT_MODEL = qwen3:4b-instruct
- AGENT_STATE_DIR = .state
- AGENT_WRITES_DISABLED = false
- OPENAI_API_KEY = **********
```

That is nine lines out of about forty-five; the real listing names every setting the runtime read, sorted, with secrets replaced by asterisks. It is the fastest way to answer "which value is this process actually using", and it never prints a credential.

Now predict what happens if you ask for a composition that does not exist. A typo in `AGENT_ENTRYPOINT` could plausibly fall back to the default, or fail somewhere deep in the first turn:

```bash
cd agents/go
AGENT_ENTRYPOINT=supervisor ./bin/agent console
```

```text
agent: loading the configuration (run `config:check` for the resolved settings): agent configuration is invalid (1 problems)
  - AGENT_ENTRYPOINT: must be one of agent, workflow, coordinator; got "supervisor"
```

Those are the first two of eighty-one lines: the binary exits non-zero before a model client exists, names the three legal values, and then — because the subcommand never parsed — ADK dumps its whole argument reference underneath. Read the top two lines and ignore the rest. Validation that reports every problem it found at once, at startup, is the difference between a five-second fix and a debugging session inside a half-built agent.

`cmd/agent` parses a subcommand, loads configuration once, and composes the requested surface. Every task below runs that same file:

| Task                   | Exact task expansion                                                                                                                             | Composition or transport                                           |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------ |
| `mise run run`         | `AGENT_ENTRYPOINT=agent go run ./cmd/agent console`                                                                                              | Conversational agent in the terminal                               |
| `mise run workflow`    | `AGENT_ENTRYPOINT=workflow go run ./cmd/agent console`                                                                                           | Bounded read-only workflow                                         |
| `mise run coordinator` | `AGENT_ENTRYPOINT=coordinator go run ./cmd/agent console`                                                                                        | Least-privilege coordinator                                        |
| `mise run web`         | `AGENT_ENTRYPOINT=agent go run ./cmd/agent web -port 8002 webui -api_server_address http://localhost:8002/api api -webui_address localhost:8002` | ADK development web and REST surface                               |
| `mise run mcp`         | `go run ./cmd/agent mcp`                                                                                                                         | MCP over standard input/output                                     |
| `mise run mcp:http`    | `MCP_HOST=127.0.0.1 MCP_PORT=8000 MCP_TRANSPORT=streamable-http go run ./cmd/agent mcp`                                                          | MCP over loopback HTTP                                             |
| `mise run a2a`         | `AGENT_ENTRYPOINT=agent go run ./cmd/agent a2a`                                                                                                  | Persistent A2A server                                              |
| `mise run data:reset`  | `rm -rf .state`                                                                                                                                  | Delete disposable runtime state; the next A2A start republishes it |

The expansions above show each task's own environment. Five of them — `run`, `workflow`, `coordinator`, `web`, and `a2a` — additionally load the repository-root `.env` through mise's redacted dotenv loader, because those five build a model client and a model client needs credentials. The two MCP tasks deliberately do not: that process reads a database and holds no credential. Step outside mise and the loader goes with it, which is why [3.4. Memory]({{< relref "/3. Capabilities/3.4. Memory.md" >}}) writes `set -a && . ../.env && set +a` by hand before running the retrieval command from `evals`.

Read the first three rows together: they differ by one environment variable. The composition is data, not a build target, which is why a behavior you see in `mise run workflow` is reproducible in a container that only ever ships one binary.

Two directories complete the picture, and confusing them is the packaging mistake that hurts most. `agents/data` is committed, immutable seed: incidents, service logs, runbooks, and skills. Runtime writes go to `agents/go/.state` on a host, or a shared volume in Kubernetes. Startup copies or migrates a runtime generation at the write-owning boundary; read tools and probes never touch the seed. Both locations are explicit settings — `AGENT_DATA_DIR` and `AGENT_STATE_DIR` — so nothing depends on which directory you happened to be standing in.

The container follows the same rule. The multi-stage `agents/go/Dockerfile` compiles this exact package with `CGO_ENABLED=0`, then copies the binary and the seed into a distroless runtime with no compiler and no module cache. Chapter 6 verifies the non-root user, read-only filesystem, probes, scan, and artifact identity.

{{% collapsible note "Deeper: the packaging mistakes that break the course contract" %}}

Each of these has a specific failure behind it, not a style preference:

- Adding agent dependencies to the root theme module, which makes the documentation build resolve the agent's graph.
- Reading ambient credentials inside a package instead of passing validated configuration, which makes `config:check` a lie.
- Hiding runtime state beside immutable seed data, which makes `mise run data:reset` destructive.
- Building a second executable per composition, which lets two of them drift and only one get tested.
- Importing `agents/go` from the black-box `evals` module, which turns protocol observation into unit tests of your own implementation.
- Relying on cgo, which breaks the static distroless image contract and forces a second SQLite engine into the build. {{% /collapsible %}}

## The package map you will be editing all chapter

The module is deliberately flat. Packages are grouped by responsibility, not by framework layer, so a capability has one obvious home:

```text
agents/go/
├── cmd/agent/       executable and subcommands
├── compose/         conversational, workflow, and coordinator wiring
├── config/          typed environment boundary
├── data/            immutable seed and the runtime generation published from it
├── domain/          normalized ids, enums, and shared records
├── tools/           incident reads and guarded actions
├── memory/          runbooks, notes, and semantic retrieval
├── policy/          budget, compaction, redaction, and injection controls
├── resilience/      deadlines, retries, and circuit breaking
├── a2aserver/       persistent A2A transport and task store
├── mcpserver/       least-privilege MCP server
├── telemetry/       logs, traces, and metrics
├── go.mod           direct, indirect, and tool dependencies
└── go.sum           resolved module checksums
```

`go list ./...` prints twenty-two packages: the twelve above plus `buildinfo`, `kagentinterop`, `model`, `piiwebhook`, `platformdrill`, `principal`, `state`, a second small command, and two `internal/` helpers. The twelve are the ones this chapter touches. Dependencies point inward toward typed domain values and outward only at explicit adapters, which is why `compose` can swap a local tool for a remote one without `domain` noticing.

`go.mod` gives the module its import path, its language version, and its direct requirements; `go.sum` authenticates what was downloaded. Here is the requirement block itself, quoted from the file the build actually reads:

{{< include path="agents/go/go.mod" region="runtime-dependencies" lang="go" >}}

Read it for two things rather than for the version numbers. Three of those module names — `glebarez/go-sqlite`, `glebarez/sqlite`, and the `modernc.org/sqlite` the comment names — are one SQLite engine seen from three angles, all pure Go, which is the requirement behind the `CGO_ENABLED=0` invariant above. And four entries carry a `// compatibility hold:` marker naming ADK as their owner: `openai-go`, `otel`, `otel/log`, and `genai` are pinned to whatever the installed ADK compiles against, so nobody bumps one of them alone and discovers at runtime that the adapter no longer matches.

Two commands confirm the graph resolves and matches its checksums:

```bash
cd agents/go
go mod verify
go list -deps ./... >/dev/null
```

```text
all modules verified
```

Be precise about what that answers. It says the bytes you compiled are the bytes the module authors published. It says nothing about licences, known vulnerabilities, or whether the code is any good — separate checks own each of those claims, and [0.2. Evidence]({{< relref "/0. Overview/0.2. Evidence.md" >}}) explains why the course keeps them apart.

`go.mod` also carries a `tool` directive listing `goimports`, `govulncheck`, and `gofumpt`. That makes each one part of the module graph — versioned and checksummed like any dependency, runnable as `go tool gofumpt` — without importing a single line of it into the production binary. Tools that span modules, such as `golangci-lint` and `gotestsum`, are pinned in the root `mise.toml` instead, so there is exactly one authority per tool and no hidden global install.

{{% collapsible note "Deeper: when vendoring is worth its cost" %}}

The learner path uses the module cache and committed checksums. Vendoring writes a large derived tree into the repository, and it earns that only when a release or restricted build environment forbids fetching modules at build time:

```bash
cd agents/go
go mod vendor
go build -mod=vendor ./cmd/agent
```

If you do it, review `vendor/modules.txt` and make the module mode explicit in CI and release builds, because a vendored tree that silently disagrees with `go.mod` is worse than none. This course commits no vendor tree: reproducibility comes from versioned requirements, checksums, pinned build tools, and a digest-pinned container. {{% /collapsible %}}

## Your turn: prove the composition is configuration, not a build target

The claim above is easy to state and easy to get wrong later, so check it by hand once, now, while nothing else is moving.

- **Mode**: `inspect` — every step is a read or a refusal, so there is nothing to revert.
- **Goal**: show that the composition is configuration rather than a build target, and that an unknown composition never reaches a runtime.
- **Files to touch**: none.
- **Preflight**: `cd agents/go && mise run build`, then confirm `./bin/agent version` reports `"mode": "development"`.
- **Steps**: record `sha256sum bin/agent`. Run `./bin/agent config:check`, then `AGENT_ENTRYPOINT=workflow ./bin/agent config:check`, then `AGENT_ENTRYPOINT=coordinator ./bin/agent config:check`, and read the `AGENT_ENTRYPOINT` line each time. Finish with `AGENT_ENTRYPOINT=supervisor ./bin/agent console`, and read only its first two lines — the eighty that follow are ADK's argument reference, as above.
- **Gate that proves completion**: the three valid runs report three different entrypoints, `sha256sum bin/agent` is identical after all of them, and the fourth exits non-zero naming `agent, workflow, coordinator`.
- **Final state**: no files changed. Write down which of the eight tasks in the table above you would reach for to reproduce a colleague's bug report about the workflow.
