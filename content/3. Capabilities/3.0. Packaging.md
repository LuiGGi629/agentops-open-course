## Why package the agent before adding capabilities?

A package boundary tells you which code owns configuration, state, tools, policy, protocols, and composition. Without it, every new capability becomes another route around the same invariants.

Start with the executable proof:

```bash
cd agents/go
mise run build
./bin/agent config:check
```

The build produces one cgo-free binary. The configuration check parses the same settings the runtime uses and masks secrets in its output.

## How is the module organized?

The module is intentionally flat:

```text
agents/go/
├── cmd/agent/       executable and subcommands
├── compose/         conversational, workflow, and coordinator wiring
├── config/          typed environment boundary
├── domain/          normalized ids, enums, and shared records
├── tools/           incident reads and guarded actions
├── memory/          runbooks, notes, and semantic retrieval
├── policy/          budget, compaction, redaction, and injection controls
├── resilience/      deadlines, retries, and circuit breaking
├── a2aserver/       persistent A2A transport and task store
├── mcpserver/       least-privilege MCP server
├── telemetry/       logs, traces, and metrics
├── go.mod           direct, indirect, and tool dependencies
└── go.sum           resolved module checksums
```

Packages are grouped by responsibility, not framework layer. Dependencies point inward toward typed domain values and outward only at explicit adapters.

## What does a Go module guarantee?

`go.mod` gives the module an import path, a language version, direct requirements, and tracked development tools. `go.sum` authenticates downloaded module content.

```bash
cd agents/go
go mod verify
go list -m all >/dev/null
go list -deps ./... >/dev/null
```

These commands prove the graph resolves and downloaded modules match their checksums. They do not prove licence compatibility, vulnerability status, or runtime behavior; separate gates own those claims.

## Why track developer commands with the `tool` directive?

The `tool` directive makes a Go command part of the module graph without importing it into production code. The formatter and vulnerability checker can then run as `go tool gofumpt`, `go tool goimports`, and `go tool govulncheck`.

Root mise pins tools used across modules, including `golangci-lint` and `gotestsum`. This split avoids a hidden global install while keeping the production binary free of development commands.

## When should you vendor dependencies?

The normal learner path uses the module cache and committed checksums. Vendoring is useful only when a release or restricted build environment requires a repository-local dependency tree.

```bash
cd agents/go
go mod vendor
go build -mod=vendor ./cmd/agent
```

`go mod vendor` writes a large derived tree. Run it only when your delivery contract requires it, review `vendor/modules.txt`, and keep the chosen module mode explicit in CI and release builds.

The course does not commit a vendor tree today. Reproducibility comes from versioned requirements, checksums, pinned build tools, and a digest-pinned container build.

## How does one binary expose several surfaces?

The `cmd/agent` package parses a subcommand, loads configuration once, and composes the requested surface:

| Task                   | Exact task expansion                                                                                                                             | Composition or transport                                |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------- |
| `mise run run`         | `AGENT_ENTRYPOINT=agent go run ./cmd/agent console`                                                                                              | Conversational agent in the terminal                    |
| `mise run workflow`    | `AGENT_ENTRYPOINT=workflow go run ./cmd/agent console`                                                                                           | Bounded read-only workflow                              |
| `mise run coordinator` | `AGENT_ENTRYPOINT=coordinator go run ./cmd/agent console`                                                                                        | Least-privilege coordinator                             |
| `mise run web`         | `AGENT_ENTRYPOINT=agent go run ./cmd/agent web -port 8002 webui -api_server_address http://localhost:8002/api api -webui_address localhost:8002` | ADK development web and REST surface                    |
| `mise run mcp`         | `go run ./cmd/agent mcp`                                                                                                                         | MCP over standard input/output                          |
| `mise run mcp:http`    | `MCP_HOST=127.0.0.1 MCP_PORT=8000 MCP_TRANSPORT=streamable-http go run ./cmd/agent mcp`                                                          | MCP over loopback HTTP                                  |
| `mise run a2a`         | `AGENT_ENTRYPOINT=agent go run ./cmd/agent a2a`                                                                                                  | Persistent A2A server                                   |
| `mise run data:reset`  | `rm -rf .state`                                                                                                                                  | Reset disposable runtime state from immutable seed data |

`AGENT_ENTRYPOINT=agent|workflow|coordinator` selects the composition behind the conversational launchers. Invalid values fail during configuration parsing.

## How do data and state paths stay portable?

Committed seed data lives under `agents/data`; runtime writes belong under `agents/go/.state` on the host or the shared state volume in Kubernetes.

The binary accepts explicit `AGENT_DATA_DIR` and `AGENT_STATE_DIR` values. It never relies on a maintainer's current directory or private home path.

The seed database is immutable. Startup copies or migrates the runtime generation at the write-owning boundary, while probes and read tools remain read-only.

## What does the container package?

The multi-stage Dockerfile compiles the same `cmd/agent` package with `CGO_ENABLED=0`, then copies the binary and seed data into a distroless runtime.

```bash
docker build -f agents/go/Dockerfile -t agentops-agent:dev .
docker image inspect agentops-agent:dev --format '{{json .Config.Entrypoint}}'
```

The image does not contain the compiler or module cache. Chapter 6 verifies the non-root user, read-only filesystem, revision label, probes, scan, and exact artifact identity.

## Which packaging mistakes break the course contract?

Avoid these failures:

- Adding agent dependencies to the root theme module.
- Reading ambient credentials inside a package instead of passing validated configuration.
- Hiding runtime state beside immutable seed data.
- Building a second executable for each composition and letting behavior drift.
- Importing `agents/go` from the black-box `evals` module.
- Relying on cgo, which breaks the static distroless image contract.
