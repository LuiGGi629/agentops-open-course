{{% admonition abstract "In one glance" %}}

- **You will:** Serve the agent's reads over MCP, list them from the wire, watch a write tool be refused, and then try to add one on purpose.
- **You need:** The tool tests passing, a second terminal, and `curl` and `jq` on your path. No model is required.
- **Time:** about 40 minutes, hands-on. {{% /admonition %}}

## Six tools, one process boundary {#what-problem-does-mcp-solve}

Ana's team already runs an incident database. So does the platform team, and the security team, and each of them will eventually want an agent that can read it. Linking that read implementation into every agent that needs it is how you end up with four copies of the same query, three of which are out of date and one of which has a subtly different definition of "open".

The Model Context Protocol separates a tool's consumer from the process that owns the capability. Start the server in one terminal:

```bash
cd agents/go
mise run mcp:http
```

```text
time=2026-08-10T20:19:31.579+02:00 level=INFO msg="serving MCP over HTTP" address=<IP_ADDRESS>:8000 transport=streamable-http tools=6
```

Six tools, and a bind address the process redacted in its own log — every log record passes through the sanitizing handler from [4.5. Guardrails]({{< relref "/4. Quality/4.5. Guardrails.md" >}}), and `127.0.0.1` matches its IP-address rule. Now ask the server, from a second terminal, what it will actually serve:

```bash
curl -sN -X POST http://127.0.0.1:8000/mcp \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}' \
  | sed -n 's/^data: //p' | jq -r '.result.tools[].name'
```

```text
get_incident
get_runbook
get_service_status
list_incidents
search_runbooks
search_service_logs
```

There is the whole surface: the same six reads from [3.1. Tools]({{< relref "/3. Capabilities/3.1. Tools.md#which-read-tools-does-the-agent-expose" >}}), carrying the same names, descriptions, and JSON schemas the model sees in process — they are the same tool values, re-exposed, not a parallel implementation. The `sed` is not decoration: streamable HTTP answers as server-sent events, so each JSON-RPC reply arrives on a `data:` line.

Before you run the next command, predict the failure mode. `restart_service` is a real tool in this binary. What should a server that is only supposed to serve reads do when a client asks for it by name?

```bash
curl -sN -X POST http://127.0.0.1:8000/mcp \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"restart_service","arguments":{"name":"inventory"}}}' \
  | sed -n 's/^data: //p' | jq -c .
```

```json
{ "jsonrpc": "2.0", "id": 3, "error": { "code": -32602, "message": "unknown tool \"restart_service\"" } }
```

Not "unauthorized". Not "confirmation required". _Unknown._ The tool was never registered on this server, so there is nothing here to authorize, rate-limit, or forget to check.

**You just moved a tool surface across a process boundary without changing a single thing the model sees.**

## The probes disagree, and they are both right

Leave the server running and ask it how it is:

```bash
curl -s http://127.0.0.1:8000/livez
curl -s http://127.0.0.1:8000/healthz
```

```text
{"status":"alive"}
{"status":"unready","problems":["dataset unavailable: *fmt.wrapErrors"]}
```

On a fresh checkout that second line is not a bug, and reading it correctly is worth more than any amount of prose about health checks. `/livez` reports only that the process loop is running, because liveness restarts a container and restarting never fixes a missing database — wiring liveness to storage turns an outage into a restart loop that deepens it. `/healthz` additionally opens the configured runtime store and checks that it is readable and correctly shaped, and on a checkout where nothing has published runtime state yet, it is not.

The reason it is not is the design, not an oversight: this process is a reader, always. It never prepares, migrates, or publishes writable state, because a replica that migrated state under a running agent would be a data race across processes. Publication belongs to the A2A startup path, which is the single writer. Run `mise run a2a` once — Chapter [3.6. A2A]({{< relref "/3. Capabilities/3.6. A2A.md" >}}) is where that server earns its own page — and `/healthz` returns `{"status":"ready"}` from then on.

Notice also what the unready body does not say. It reports the error's Go type, never its message, because a message can name a filesystem path or a driver detail and a readiness body is served to anyone who can reach the port.

## Transports, allowlists, and the pinned SDK {#which-transports-are-supported}

Four roles make up the picture. The Go MCP **server** registers the six reads. ADK's Go MCP **toolset** is the client adapter inside the agent. A **transport** carries JSON-RPC. And agentgateway is an optional **policy point** between the two, which Chapter 5 gives its own treatment. MCP governs tool discovery and invocation; [3.6. A2A]({{< relref "/3. Capabilities/3.6. A2A.md" >}}) governs agent discovery and task exchange, and neither replaces the other.

The server supports three transports, chosen by one switch:

{{< include path="agents/go/mcpserver/transport.go" region="mcp-server-transport" lang="go" >}}

`Serve` dispatches on the configured transport and folds both HTTP flavors into one path, and its `default` branch returns an error even though `New` already validated the value — because "unreachable" is a claim about today's code. <a id="what-does-the-stdio-transport-actually-launch"></a>**stdio** is the default local path: the client launches this same agent binary with the `mcp` subcommand as a child process, which inherits only the environment its parent deliberately gave it, talks over standard input and output, needs no shell or second runtime, and publishes no port at all. **Streamable HTTP** serves `/mcp` and is what the gateway and the Kubernetes deployment use. **SSE** exists for older clients; new deployments should not choose it.

The HTTP surface defaults to loopback and applies Host and Origin allowlists, a header timeout, and a bounded drain on shutdown. The Host allowlist is DNS-rebinding protection rather than paperwork: a browser page on an attacker's site can be made to resolve a name it controls to `127.0.0.1` and then talk to a local server as though it were same-origin, and a closed list of authorities is what stops it. Setting it to `*` is refused outright.

<a id="why-does-mcp-matter-beyond-this-repository"></a>Which protocol revision are you speaking? Whatever the pinned `github.com/modelcontextprotocol/go-sdk` negotiates with the peer. Do not copy a revision number into configuration; `agents/go/go.mod`, `go.sum`, the installed SDK source, and the handshake tests are the authority, and an SDK upgrade has to re-run both the stdio and HTTP protocol tests plus the gateway smoke. That negotiation is the whole portability argument: independently deployed clients and servers evolve behind an agreed protocol instead of a shared package tree. It is also the risk, because tool names, descriptions, and schemas are model input. A server you connect to writes prose into your prompt.

Which is why the client side pins its own list:

{{< include path="agents/go/compose/mcp.go" region="ops-mcp-toolset" lang="go" >}}

`NewMCPToolset` builds the toolset with `tool.AllowedToolsPredicate(MCPReadToolNames())` inside the config, so filtering happens before a tool is wrapped and a rejected declaration never reaches a request. An HTTP endpoint gets a bounded `http.Client` and an optional bearer credential; a child command gets the SDK's command transport and no network credential; supplying neither is a configuration error rather than a silent no-op.

<a id="when-does-the-root-agent-use-mcp"></a>Only the conversational entrypoint switches to MCP, and only when `AGENT_MCP_URL` is set. The workflow and coordinator specialists keep their local restricted sets, and the guarded writes stay in this process in every composition, so a remote server cannot acquire action authority merely because the read path moved behind a protocol.

<a id="what-changes-when-you-flip-agent_mcp_url"></a>And what changes when you flip it? The implementation location, and nothing the model can see. Names and schemas are identical, the client discovers declarations at connect time, keeps only the allowlisted names, and applies the tool timeout. What the agent gives up is the local resilience wrapping — deadline, retries, and circuit breaker then belong to the gateway in front of the server, which is the trade Chapter 5 makes explicit.

## Your turn: add a tool to the MCP server

The claim above is that the read-only surface is enforced at three independent points, and that any one of them alone would hold. Test it. Try to get a write tool onto this server and see how far you get before something stops you.

- **Mode**: `temporary experiment` — you are deliberately weakening a security boundary to watch it fail, and you will put it back.
- **Goal**: defeat the server-side surface check, then the client allowlist, and find out what is still standing behind them.
- **Files to touch**: `agents/go/cmd/agent/servers.go` and `agents/go/compose/mcp.go` only.
- **Preflight**: `git diff --quiet -- agents/go/cmd/agent/servers.go agents/go/compose/mcp.go`, and `cd agents/go && go test ./mcpserver ./compose` green.
- **Step one — the server refuses.** In `servers.go`, append `surface.ActionTools()` to the `Tools` list the MCP server is built with, then run `mise run mcp:http`. Predict the message before you read it:

```text
agent: incomplete MCP server configuration: tool "restart_service" is not in the read allowlist (list_incidents, get_incident, get_service_status, search_service_logs, get_runbook, search_runbooks); the MCP surface is read-only and a server cannot widen it
incomplete MCP server configuration: tool "resolve_incident" is not in the read allowlist (list_incidents, get_incident, get_service_status, search_service_logs, get_runbook, search_runbooks); the MCP surface is read-only and a server cannot widen it
```

Two problems, not one — `ActionTools()` returns both guarded writes, and the check reports every offending tool at once rather than dying on the first.

- **Step two — widen the allowlist.** Add `tools.RestartServiceToolName` to `MCPReadToolNames()` in `compose/mcp.go`, keep just that one action tool on the server, and start it again. Now the startup log says `tools=7` and the listing request from the top of this page returns seven names including `restart_service`. Two of the three enforcement points are gone.
- **Step three — call it.** Send the `tools/call` request from the top of this page again, and read what comes back:

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "result": {
    "content": [
      {
        "type": "text",
        "text": "this tool requires human confirmation, which the MCP server cannot request: call it through the agent instead"
      }
    ],
    "isError": true
  }
}
```

- **Gate that proves completion**: you can state, from your own three runs, which check produced each of the three outcomes — startup refusal, seven advertised tools, and a call that fails closed — and why the third one cannot be configured away.
- **Final state**: `git restore -- agents/go/cmd/agent/servers.go agents/go/compose/mcp.go`, then `cd agents/go && go test ./mcpserver ./compose` green again and `mise run mcp:http` back to `tools=6`.

The third check is structural rather than configured. This process has no session to pause, no event stream to publish a confirmation request on, and no human listening, so a tool that requires approval cannot execute here at all — which is the correct answer, because an MCP server that could run an approval-gated action would have made approval optional.

{{% collapsible note "Deeper: adding a third-party MCP server safely" %}}

Treat someone else's server as untrusted code _and_ untrusted instruction data, because it is both.

1. Review provenance, licence, transport, authentication, and every tool schema before you connect.
1. Create a closed client-side name allowlist, exactly as `MCPReadToolNames` is.
1. Give the server only the data and network access its tools need.
1. Apply deadlines, size bounds, redaction, and audit records on your side of the wire.
1. Add a test where the server advertises an extra tool, and confirm it never reaches the model. {{% /collapsible %}}

## What you can do now

- You served the agent's six reads from their own process and listed them from the wire, unchanged in name and schema.
- You can explain why `/livez` says alive while `/healthz` says unready on a fresh checkout, and which process is allowed to fix it.
- You defeated two of the three read-only enforcement points and watched the third refuse the call anyway.
- `cd agents/go && go test ./mcpserver ./compose` passes, covering the transports, probes, drain, and the exact accepted tool names.

A capability that lives behind a protocol is a capability another team can consume and you can put a gateway in front of — and you now know, from having tried, that moving it there did not move its authority with it.
