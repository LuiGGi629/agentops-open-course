## What does memory mean in this course?

Memory is six stores with different owners and lifetimes:

| Store             | Scope                           | Implementation               |
| ----------------- | ------------------------------- | ---------------------------- |
| Conversation      | One user and session            | ADK database session service |
| A2A task          | One network task                | Persistent A2A task store    |
| Operational state | Services, incidents, audit      | Writable SQLite generation   |
| Long-term notes   | One stable user across sessions | `.state/memory.db`           |
| Knowledge         | Shared remediation procedures   | Immutable Markdown runbooks  |
| Session state     | One session or invocation       | ADK callback state           |

A note for one caller is not shared knowledge. An A2A task is not a conversation, and an incident row is not a prompt message.

Choose the store from the required lifetime and authority before writing code.

## What should survive across sessions?

Persist facts the next investigation needs and cannot safely recompute: attempted remediation, observed outcomes, and explicit decisions.

The `save_incident_note` and `recall_incident_context` tools make those writes and reads visible in traces. Notes are keyed by the stable caller identity, referentially checked against known incidents, length-bounded, and redacted before persistence.

The unauthenticated A2A path derives a synthetic user from its context id. A new context is therefore a new logical user. Human-level memory requires an authenticated, durable subject propagated by a trusted gateway.

## Why are memory operations explicit tools?

An explicit tool call is observable, testable, and policy-controlled. Silent context injection hides what was read, while automatic history ingestion hides what was persisted.

The trade-off is behavioral: the model must decide to recall or save. The instruction requires recall at the start of an investigation, and trajectory evaluation checks that ordering.

## How does deterministic keyword retrieval work?

The default scorer tokenizes every runbook, rewards terms that are rare across the corpus, boosts slug matches, and sorts ties by slug.

It is fast, inspectable, account-free, and deterministic. It also misses paraphrases: “checkout is slow” may not match a procedure that says “high latency.”

That limitation is why semantic retrieval is an evaluated option, not why it becomes the default automatically.

## Why does semantic retrieval use a brute-force cosine scan?

The runbook corpus is well under one hundred vectors at a few hundred dimensions. Scanning every vector takes microseconds and the index is only a few hundred kilobytes.

At that scale, a vector extension adds deployment and cgo cost without useful latency. The static distroless binary also rules out the available cgo binding.

The Go implementation stores vectors as SQLite blobs and computes cosine distance in process. Add an approximate index only after measurements show that a larger corpus makes the simple scan material.

## What keeps a semantic index reproducible?

An index is a cache whose typed `Provenance` record includes `CorpusSHA256`, `EmbeddingModel`, `ModelDigest`, `ChunkerVersion`, `BuiltAt`, `FormatVersion`, `Dimensions`, and `ChunkCount`. Together those fields bind corpus content, embedding artifact, build time, vector shape, chunker, and index format.

The first caller takes a SQLite write lock and builds a complete replacement generation in one transaction. A failed rebuild rolls back; concurrent readers never observe a half-built index.

If provenance changes during query or build, the semantic result is refused and the agent falls back to deterministic keyword retrieval with a warning.

## When do embeddings earn their cost?

They earn it only when a reviewed retrieval set shows better hit rate on real paraphrases without unacceptable latency or outage behavior.

Run both retrievers against seed-derived incident queries through separate read-only MCP runtimes:

```bash
cd evals
mise run eval:retrieval
```

The task writes `retrieval-results.json` with keyword and semantic hit-rate at 1 and 3, source/model identity, and a corpus digest. It stores no queries or retrieved text. Its semantic runtime needs the configured local embedding endpoint; the keyword runtime does not.

Historical checkpoint (superseded): any retrieval result captured before the current corpus hash, model digest, chunker version, or evalset is context only. Rebuild and remeasure before using it as candidate evidence.

Never present a nearest neighbor as truth. Cosine distance always ranks something, even when every candidate is wrong.

## What occupies the model context?

The request can contain the root instruction, tool declarations, conversation history, tool calls and results, retrieved runbooks, long-term notes, and the current prompt.

These stores do not compete for disk, but their selected contents compete for the model's context window. Observe token usage before increasing the limit or choosing a larger model.

## How is long history bounded?

The policy can replace older messages with one deterministic marker while retaining the newest messages and tool result:

{{< include path="agents/go/policy/compaction.go" region="compact-history" lang="go" >}}

Compaction rewrites only the outgoing request. Stored session events remain complete, and the marker does not accumulate across turns.

Set `AGENT_MAX_HISTORY_MESSAGES` with headroom because one user turn can create several messages. A low value can remove evidence the model still needs.

## What should you drop first when context is tight?

Remove duplicated instructions and irrelevant retrieved text before removing recent tool evidence. Prefer exact runbook sections over entire documents, and bound catalog descriptions before truncating the current task.

Compaction is a cost and availability control, not a replacement for evidence selection.

## How do you defend against retrieval injection?

Runbooks and logs are data, even when committed locally. Tool outputs are wrapped as untrusted content and screened for instructions before they return to the model.

The locally constructed skill loader is the narrow exception: reviewed repository skill instructions bypass injection neutralization but still receive recursive secret and PII redaction. The exception is keyed by the concrete tool type, not a name an MCP server could spoof.

## How do you add a runbook safely?

Add the Markdown source under `agents/data/runbooks`, add or update incidents that refer to its normalized slug, and extend retrieval cases with realistic queries.

Then run:

```bash
cd agents/go
go test ./memory ./policy -count=1
cd ../../evals
mise run eval:validate
```

If semantic retrieval is enabled later, rebuild and remeasure rather than trusting vectors from the previous corpus hash.
