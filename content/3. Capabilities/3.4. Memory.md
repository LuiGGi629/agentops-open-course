## The runbook nobody typed the name of

Ana's incident record carries a `runbook` field, so the agent can fetch the right procedure by slug. That covers the easy half of the night. The other half is the page that arrives as a sentence — "checkout is slow", "the queue will not drain", "we are seeing 503s from stock lookups" — with no slug attached and no incident open yet.

Ask the knowledge base directly, using the MCP server you started in [3.3. MCP]({{< relref "/3. Capabilities/3.3. MCP.md" >}}) so no model is involved and the ranking is entirely the retrieval code's doing. Predict first: of the seven runbooks in the corpus, which one should come back for a sentence about crash-looping pods and 503s, and does the word "service" — which appears in nearly all of them — help or hurt?

```bash
curl -sN -X POST http://127.0.0.1:8000/mcp \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"search_runbooks","arguments":{"query":"inventory pods are crash-looping and stock lookups return 503"}}}' \
  | sed -n 's/^data: //p' | jq '.result.structuredContent | {count, retrieval, slugs: [.runbooks[].slug]}'
```

```json
{
  "count": 3,
  "retrieval": "keyword",
  "slugs": ["service-down", "disk-full", "cascade-failure"]
}
```

`service-down` first, which is the procedure `INC-002` actually links to — arrived at from Ana's words rather than from her incident record. Note the `retrieval` field: the answer says how it was ranked, in the payload the model reads, not only in a log line. That field will matter twice more on this page.

**You just watched the agent find the right procedure from a sentence Ana could have typed at 02:14, with no slug, no model call, and no service to sign up for.**

## Six stores, one window

"Memory" is the word that makes agent architectures go wrong, because it flattens six different things with six different owners and lifetimes into one bucket:

| Store             | Scope                           | Implementation               |
| ----------------- | ------------------------------- | ---------------------------- |
| Conversation      | One user and session            | ADK database session service |
| A2A task          | One network task                | Persistent A2A task store    |
| Operational state | Services, incidents, audit      | Writable SQLite generation   |
| Long-term notes   | One stable user across sessions | `.state/memory.db`           |
| Knowledge         | Shared remediation procedures   | Immutable Markdown runbooks  |
| Session state     | One session or invocation       | ADK callback state           |

A note one caller wrote is not shared knowledge. An A2A task is not a conversation. An incident row is not a prompt message. Choose the store from the lifetime and the authority the fact needs before you write any code, because moving a fact between these later means moving its access rules with it.

<a id="what-should-survive-across-sessions"></a>What deserves to survive a session is narrow: facts the next investigation needs and cannot safely recompute — an attempted remediation, an observed outcome, an explicit decision. The `save_incident_note` and `recall_incident_context` tools make those writes and reads visible in traces, and notes are keyed by the stable caller identity, checked against known incidents, length-bounded, and redacted before they persist.

Making them explicit tools is a deliberate trade. Silent context injection hides what was read; automatic history ingestion hides what was persisted; an explicit call is observable, testable, and policy-controlled. The cost is behavioral: the model has to decide to recall or save. The instruction requires a recall at the start of an investigation, and trajectory evaluation checks that ordering rather than assuming it.

One sharp edge belongs here rather than in a footnote. The unauthenticated A2A path derives a synthetic user from its context id, so a new context is a new logical user with no memory of the last one. Human-level memory needs an authenticated, durable subject propagated by a trusted gateway — which is [5.5. Gateway Security]({{< relref "/5. Gateway/5.5. Gateway Security.md" >}})'s job, not this page's.

<a id="what-occupies-the-model-context"></a>Those six stores do not compete for disk. Their selected contents compete for one thing: the model's context window, which on any given request can hold the root instruction, every tool declaration, conversation history, tool calls and their results, retrieved runbooks, long-term notes, and the current prompt.

<a id="how-is-long-history-bounded"></a>The policy plane's answer is compaction — replacing older messages with one deterministic marker while keeping the newest messages and tool result:

{{< include path="agents/go/policy/compaction.go" region="compact-history" lang="go" >}}

Two details there repay attention. The loop that advances `cut` past function responses exists because a request can end mid-tool-loop: stopping one short keeps at least the newest tool result rather than replacing the very thing the model just asked for with a marker. And the rewrite touches only the outgoing request — ADK rebuilds contents from stored session events every turn, so nothing is deleted from the session and the marker never accumulates. Set `AGENT_MAX_HISTORY_MESSAGES` with headroom, because one user turn can create several messages and a tight value removes context the model still needs.

<a id="what-should-you-drop-first-when-context-is-tight"></a>When the window is tight, drop in this order: duplicated instructions first, then irrelevant retrieved text, then whole documents in favor of the exact runbook sections you need, then catalog descriptions — and only ever last, recent tool results. Compaction is a cost and availability control. It is not a substitute for choosing better sources in the first place.

One rule survives all of this compression. Runbooks and logs are data even when they are committed locally: tool outputs are wrapped as untrusted content and screened for embedded instructions before they return to the model. The single exception is the locally constructed skill loader from [3.2. Skills]({{< relref "/3. Capabilities/3.2. Skills.md" >}}), whose reviewed body bypasses injection neutralization but still gets recursive secret and PII redaction — and that exception is keyed on the concrete tool value, not a name an MCP server could choose for itself.

## Two retrievers, and the field that says which one answered

<a id="how-is-a-known-runbook-fetched"></a>When an incident already supplies a slug, use it. The exact read is the whole tool:

{{< include path="agents/go/memory/knowledge.go" region="get-runbook" lang="go" >}}

`runGetRunbook` runs `readRunbook` inside the same guard the other reads use, and the inner reader normalizes the model-controlled slug into a validated domain value before any filesystem access. A traversal string cannot be expressed as that type, so it never becomes a path — the same parse-at-the-boundary rule from [3.1. Tools]({{< relref "/3. Capabilities/3.1. Tools.md#what-makes-a-function-a-good-agent-tool" >}}), applied where it protects a filesystem instead of a database.

<a id="how-does-deterministic-keyword-retrieval-work"></a>Free-text search is the fallback for when no trusted slug exists, and the default scorer is a TF-IDF-style ranker: it tokenizes every runbook, weights a term higher when it is rare across the corpus so ubiquitous words cannot dominate, adds a large flat boost when a term appears in a runbook's slug, and breaks score ties by slug so equal scores always order the same way. It is fast, inspectable, account-free, and reproducible — which is exactly what an evaluation needs.

It also misses paraphrases. "Checkout is slow" does not contain the word "latency", and no amount of tuning the boost changes that. That limitation is the entire argument for embeddings — so here is what taking the argument seriously costs.

Turn semantic retrieval on with `AGENT_SEMANTIC_RETRIEVAL=true` and the same query is answered by cosine distance over locally computed embeddings instead. A brute-force scan, deliberately: the runbook corpus is well under a hundred vectors at a few hundred dimensions, scanning every one takes microseconds, and the whole index is a few hundred kilobytes. At that size a vector extension buys no useful latency and costs deployment complexity and cgo — and cgo is exactly what the static distroless binary from [3.0. Packaging]({{< relref "/3. Capabilities/3.0. Packaging.md" >}}) rules out. Vectors are SQLite blobs; cosine distance is computed in process. Add an approximate index when a measurement says the simple scan has become material, not before.

An index is a cache, so it carries a typed `Provenance` record binding it to everything that could invalidate it: `CorpusSHA256` for the content, `EmbeddingModel` and `ModelDigest` for the artifact that produced the vectors, `ChunkerVersion` for how the text was split, `BuiltAt` for when, `FormatVersion` for the table shape, and `Dimensions` and `ChunkCount` for the vectors themselves. The first caller takes a SQLite write lock and builds a complete replacement generation in one transaction, so a failed rebuild rolls back and concurrent readers never see a half-built index. If provenance changes during a query or a build, the semantic result is refused.

Refused, but not fatal — and the fallback is visible. Here is what a first semantic query looked like on a CPU-only laptop where building the index exceeded `AGENT_EMBEDDING_TIMEOUT_S`:

```text
level=WARN msg="semantic retrieval unavailable, falling back to keywords" error="Embeddings unavailable at http://<IP_ADDRESS>:11434 with model \"nomic-embed-text\"; start Ollama and `ollama pull nomic-embed-text`, or unset AGENT_SEMANTIC_RETRIEVAL."
```

The tool still answered, with `"retrieval": "keyword"` in the result. That is the field from the first section doing its real job: the transcript itself records that the answer came from the deterministic scorer, so nobody later reads a keyword result as a sign that the embedding path works. A silent degradation would have been indistinguishable from success.

So when do embeddings earn their cost? Only when a reviewed retrieval set shows a better hit rate on real paraphrases without unacceptable latency or outage behavior. Retrieval quality is a separate pipeline rather than an evalset, so it stays a direct command on the evaluation CLI, running both retrievers against seed-derived incident queries through separate read-only MCP runtimes:

```bash
mise run --cd agents/go build
cd evals
set -a && . ../.env && set +a
go run ./cmd/agentops-eval retrieval
```

It writes `retrieval-results.json` with keyword and semantic hit-rate at 1 and 3, source and model identity, and a corpus digest — and it stores no queries and no retrieved text. Its semantic runtime needs the configured local embedding endpoint; the keyword runtime does not.

Before you quote a hit rate out of that file, check its four identity fields against the ones you have now. A run taken before the current corpus hash, model digest, chunker version, or evalset is a **Historical checkpoint (superseded)**: the moment any one of the four changes, the number describes a system that no longer exists. Rerun it rather than carrying the old figure forward — the exercise below changes the corpus in exactly that way. A hit rate is an observation about one run rather than a gate, which is the distinction [0.2. Evidence]({{< relref "/0. Overview/0.2. Evidence.md" >}}) makes once for the whole course.

And whichever retriever answers, never present a nearest neighbor as truth. Cosine distance always ranks something, even when every candidate is wrong.

## Your turn: add a runbook and watch retrieval rank it

Your own domain's knowledge is the thing you will actually want in here. Add one procedure, then watch the ranker put it first for a symptom that never mentions its name.

- **Mode**: `temporary experiment` — the committed corpus is what other pages measure against, so this one goes back.
- **Goal**: add a runbook and observe it move from absent to first place for a paraphrased query.
- **Files to touch**: one new file under `agents/data/runbooks/` only.
- **Preflight**: pick a slug that does not exist yet and require `test ! -e agents/data/runbooks/<your-slug>.md`; have the MCP server from 3.3 running.
- **Steps**: run the `search_runbooks` call from the top of this page with a query describing your symptom in a sentence, and record the three slugs it returns _before_ you add anything. Write the runbook as Markdown with the same H2 shape as the shipped ones — Symptoms, Diagnosis, Remediation, Related — using your symptom's own vocabulary. Run the identical query again.
- **Gate that proves completion**: the same query returns your slug first, and you can point at which words in it earned the ranking. Adding a queue-backlog runbook and asking "consumer lag keeps growing and the queue depth will not drain" gave these two answers, through the same projection as the command above:

```json
{ "count": 3, "retrieval": "keyword", "slugs": ["cascade-failure", "memory-leak", "disk-full"] }
```

```json
{ "count": 3, "retrieval": "keyword", "slugs": ["queue-backlog", "cascade-failure", "memory-leak"] }
```

Before the file existed the ranker had to answer with something, and it did — three procedures about failures that are not this one. That is the point about nearest neighbors, made by the keyword scorer instead of by embeddings.

- **Final state**: `rm -- agents/data/runbooks/<your-slug>.md`, then confirm the query returns the original three slugs again. If you had semantic retrieval enabled, rebuild and remeasure rather than trusting vectors built against the previous corpus hash.

Keeping a runbook for real is a bigger commitment than deleting one: add or update the incidents that refer to its normalized slug, extend the retrieval cases with realistic queries, and run `cd agents/go && go test ./memory ./policy -count=1` plus `cd evals && mise run eval:validate` before you rely on it.

## What you can do now

- You watched deterministic retrieval rank the right runbook for a sentence, and watched a runbook you wrote take first place for a symptom that never named it.
- You can map any fact to one of six stores by lifetime and authority, and say why an A2A context is not a durable user.
- You can read a `retrieval` field and know whether an answer came from embeddings or the keyword fallback, and name the provenance that would invalidate an index.
- `cd agents/go && go test ./memory ./policy -count=1` passes with no model and no network, and `test -z "$(git status --porcelain ../data/runbooks)"` confirms the runbook you added and deleted left the committed corpus exactly as you cloned it.

The agent can now be handed knowledge it was not born with, and you can point at the words that made it choose. Continue to [3.5. Workflows]({{< relref "/3. Capabilities/3.5. Workflows.md" >}}), where the order of the investigation stops being the model's decision.
