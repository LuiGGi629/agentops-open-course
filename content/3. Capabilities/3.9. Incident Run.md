{{% admonition abstract "In one glance" %}}

- **You will:** Put the agent you built through one incident, then read the turn back call by call and say, for each, whether the model decided it or the code did.
- **You need:** Chapter 3 finished with your own tool and skill in place, Ollama running, and `cd agents/go && mise run test` green.
- **Time:** about 15 minutes, hands-on. {{% /admonition %}}

## Nine pages ended at a unit test, and nobody has asked the agent a question

Every page in this chapter ended at a unit test. That was the right gate for each one — a tool contract, a skill loader, a delegation boundary, and a streaming window are all decidable offline, and offline is where they belong. But the agent you actually built has never been asked a question.

INC-002 has been the promise since [2.1. First Agent]({{< relref "/2. Agents/2.1. First Agent.md" >}}): the inventory service is crash-looping and Ana is triaging it at 02:14. Back then the agent could read the incident and stop. Now it can retrieve a runbook nobody typed as a slug, remember what last night's engineer tried, and refuse a restart without a named human. One session is the difference between having built those and having used them.

Be exact about which session, because it is not the whole chapter. `mise run web` pins `AGENT_ENTRYPOINT` to `agent`, and that composition is one agent holding the read and action tools, the memory tools, and the skill toolset — so this run reaches [3.1. Tools]({{< relref "/3. Capabilities/3.1. Tools.md" >}}), [3.2. Skills]({{< relref "/3. Capabilities/3.2. Skills.md" >}}) and [3.4. Memory]({{< relref "/3. Capabilities/3.4. Memory.md" >}}), and no further. The rest are separate entrypoints and separate switches, each one command away: `mise run workflow` builds the bounded investigation from [3.5. Workflows]({{< relref "/3. Capabilities/3.5. Workflows.md" >}}), `mise run coordinator` builds the delegating specialists from [3.7. Multi-Agent]({{< relref "/3. Capabilities/3.7. Multi-Agent.md" >}}), `mise run a2a` serves the network agent from [3.6. A2A]({{< relref "/3. Capabilities/3.6. A2A.md" >}}) and carries the token stream from [3.8. Streaming]({{< relref "/3. Capabilities/3.8. Streaming.md" >}}) when `AGENT_A2A_STREAMING=true`, and setting `AGENT_MCP_URL` moves the six reads to the server from [3.3. MCP]({{< relref "/3. Capabilities/3.3. MCP.md" >}}). Run the single agent first: every one of those traces is easier to read once you know what an undelegated one looks like.

Start the developer UI, which is the only surface that shows the calls behind an answer:

```bash
cd agents/go
mise run web
```

Open `http://localhost:8002`, select `agentops_agent`, and work the incident the way Ana would — one question at a time, not one paragraph containing all of them:

1. Ask what is open right now.
1. Ask what is wrong with the inventory service specifically.
1. Ask what has already been tried.
1. Ask what to do about it.
1. Ask it to do that thing.

Give each turn room. On a CPU-only host a grounded turn runs several multiples of the `inference` line `mise run doctor:model` printed, and [1.4. Providers]({{< relref "/1. Setup/1.4. Providers.md" >}}) owns the budget that governs it.

## The Events view is the only place the decisions are visible

The chat pane shows prose. The Events pane shows the turn: one row per `functionCall`, one per `functionResponse`, and the final model message that was built from them. That distinction is the whole point of this page, because a good answer and a fabricated answer read identically in the chat pane and differently in Events.

Two kinds of row will be there, and telling them apart is the skill worth leaving the chapter with:

- **A call the model chose.** `list_incidents` with a status filter, `get_incident` with an identifier, `search_runbooks` with words from the symptom, `load_skill` with a name — every one of these is the model reading the situation and picking. Nothing in the code says to call them, and a different model would pick differently.
- **A call the code forced, or refused.** The pause before `restart_service` is not a decision the model made and is not one it can skip: [3.1. Tools]({{< relref "/3. Capabilities/3.1. Tools.md" >}}) makes confirmation, a named approver, and a bounded rationale structural preconditions of the write. The model can ask for the write. It cannot perform one.

The last request is therefore where this page stops, one step short of the write. Read the confirmation card instead of clicking through it: it names `restart_service` and the exact target the model proposed, and that proposal is the entire thing an approver would be signing.

Do not expect to complete the approval here. The dev UI's card answers with `{confirmed, payload}`, where the payload is the tool arguments the model already sent and the card offers no field to change or add to them — so no rationale can reach `agents/go/tools/action.go`, and the guard refuses the execution with `the approval carried no rationale`. That refusal is the same one [3.1. Tools]({{< relref "/3. Capabilities/3.1. Tools.md" >}}) built: an attributable approval is a precondition of the write, and a click is not attribution.

So check the other half of the contract — that the request alone wrote nothing:

```bash
sqlite3 -header -column .state/incidents.db \
  'SELECT schema_version, actor, approved_by, action, target FROM audit_log ORDER BY id DESC LIMIT 5;'
```

No rows is the correct result, and it is the receipt: the agent asked for a restart, you never supplied a rationale, and the audit table records exactly the writes that happened. [5.3. A2A Gateway]({{< relref "/5. Gateway/5.3. A2A Gateway.md" >}}) is where this same action gets approved for real, through the browser client in `clients/web/index.html` — the one shipped surface that sends a rationale with the confirmation — and that is where this query returns a row with your name on it.

## Your turn: run INC-002 end to end and name every call

Predict first, before you open the browser: across those five requests, how many rows in Events will be calls the model chose, and how many will be things the code required? Write both numbers down, then count.

- **Mode**: `inspect` — the session writes runtime state under `agents/go/.state`, which is already gitignored, and touches no tracked file.
- **Goal**: drive one incident through the agent you built, and account for every call in the event log by who decided it.
- **Files to touch**: none.
- **Preflight**: `cd agents/go && mise run test` green, and `mise run doctor:model` reporting a measured inference line.
- **Steps**: start `mise run web`, work the five requests above in order, stop at the confirmation card without approving it, then open the Events pane and list every `functionCall` in the order it fired. Beside each one write **model** or **code**, and for the ones you marked **model**, name the words in your question that made it pick that tool.
- **Gate that proves completion**: your list accounts for every `functionCall` row; `load_skill` appears exactly where your skill's "Use when…" clause said it would; the confirmation card names `restart_service` with the exact target the model proposed; and the `sqlite3` query above returns no rows, because you never supplied the rationale the write requires.
- **Final state**: stop the server. Runtime state stays under `agents/go/.state`; `git status --short` reports nothing. `mise run data:reset` returns the simulated service to its seeded state when you want a clean run.

The disagreement between your prediction and your count is the lesson. Most people over-count what the model decides, because the answer reads like one continuous act of reasoning — and under-count the constraints, because a constraint that works is invisible.

## What you can do now

- You ran one incident through the typed tools, the skills and the memory of the default composition in a single session, and watched the model reach for each of them.
- You can name the five capabilities that session never touched — MCP, the workflow, A2A, streaming, and delegation — and the command or variable that reaches each one.
- For every call in the event log, you can say whether the model chose it or the code required it, and point at the file that decides.
- You have an empty audit table after a write request, which is the proof that asking for a restart and performing one are different events.
- You can tell a colleague, accurately, that you built an agent that triaged a real incident — and say exactly which part of that sentence the machine did.
