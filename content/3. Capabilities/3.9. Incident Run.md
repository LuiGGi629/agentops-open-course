{{% admonition abstract "In one glance" %}}

- **You will:** Put the agent you built through one incident, then read the turn back call by call and say, for each, whether the model decided it or the code did.
- **You need:** A model served and configured in the root `.env`, and `cd agents/go && mise run test` green. If you did the [3.1. Tools]({{< relref "/3. Capabilities/3.1. Tools.md" >}}) and [3.2. Skills]({{< relref "/3. Capabilities/3.2. Skills.md" >}}) exercises, your own tool and skill ride along here; if you skipped them, the six shipped reads and the two shipped skills carry all five requests.
- **Time:** about 45 minutes, hands-on — the reading is fifteen, and five grounded turns are the rest. {{% /admonition %}}

## What one live session shows that the offline gates cannot

The **default composition** is what the `agent` entrypoint builds: one agent holding the read and action tools, the memory tools, and the skill toolset. `mise run web` starts it with `AGENT_ENTRYPOINT=agent`, so this session reaches [3.1. Tools]({{< relref "/3. Capabilities/3.1. Tools.md" >}}), [3.2. Skills]({{< relref "/3. Capabilities/3.2. Skills.md" >}}) and [3.4. Memory]({{< relref "/3. Capabilities/3.4. Memory.md" >}}), and no further.

Every gate in this chapter so far was decidable without a model, and offline is where those belong. But no offline check shows which tools a model reaches for. A call the model chose and a constraint the code imposed read identically in the answer; in the event log they are separate rows.

So this page runs five requests, reads the event log call by call, stops at the confirmation card, and ends at an empty audit table. The run is INC-002, open since [2.1. First Agent]({{< relref "/2. Agents/2.1. First Agent.md" >}}) — the inventory service crash-looping, and back then an incident the agent could only read.

The rest of the chapter lives behind other entrypoints and switches, each one command away: `mise run workflow` builds the bounded investigation from [3.5. Workflows]({{< relref "/3. Capabilities/3.5. Workflows.md" >}}), `mise run coordinator` builds the delegating specialists from [3.7. Multi-Agent]({{< relref "/3. Capabilities/3.7. Multi-Agent.md" >}}), `mise run a2a` serves the network agent from [3.6. A2A]({{< relref "/3. Capabilities/3.6. A2A.md" >}}) and carries the token stream from [3.8. Streaming]({{< relref "/3. Capabilities/3.8. Streaming.md" >}}) when `AGENT_A2A_STREAMING=true`, and setting `AGENT_MCP_URL` moves the six reads to the server from [3.3. MCP]({{< relref "/3. Capabilities/3.3. MCP.md" >}}). Run the single agent first: an undelegated trace reads easiest.

Start the developer UI. The console prints only the final answer; the UI shows each tool call as a row:

```bash
cd agents/go
mise run web
```

Open `http://localhost:8002`, select `agentops_agent`, and ask one request at a time, not one paragraph holding all five, so each gets its own turn to read. Each elicits a different kind of call:

1. Ask what is open right now — a list read.
1. Ask what is wrong with the inventory service specifically — one exact record read.
1. Ask what has already been tried — a memory recall, not a database read.
1. Ask what to do about it — a runbook search, then a skill load: your own "Use when…" clause if you wrote one, otherwise the shipped `remediation` skill, whose clause covers asking how to fix a known incident.
1. Ask it to do that thing — a write proposal, which is not a write.

Give each turn room. On a CPU-only host a grounded turn runs several multiples of the `inference` line `mise run doctor:model` printed, and [1.4. Providers]({{< relref "/1. Setup/1.4. Providers.md" >}}) owns the budget — `AGENT_MODEL_TIMEOUT_S`, which names itself in the failure when a turn never returns.

## How the Events view separates model choices from code constraints

The chat pane shows prose. The Events pane shows the turn as rows: a `functionCall` is the model's request for a named tool, a `functionResponse` is what the Go handler returned, and the final model message is built from both. Telling the two call kinds apart is the skill worth leaving the chapter with:

- **A call the model chose.** `list_incidents` with a status filter, `get_incident` with an identifier, `search_runbooks` with words from the symptom, `load_skill` with a name — each is the model reading the situation and picking. Nothing in the code says to call them, and a different model would pick differently.
- **A call the code forced, or refused.** The pause before `restart_service` is no decision of the model's, and not one it can skip: confirmation, a named approver, and a bounded rationale are structural preconditions of the write. The model can ask for the write. It cannot perform one.

The page stops here, one step short of the write. Read the confirmation card instead of clicking through it: it names `restart_service` and the exact target the model proposed — the entire thing an approver would be signing.

Do not expect to complete the approval here. [3.1. Tools]({{< relref "/3. Capabilities/3.1. Tools.md" >}}) requires a rationale from the approver, bounded and redacted, before the guard will run anything. The dev UI's card answers with `{confirmed, payload}` — the payload being the arguments the model already sent, with no field to add to them — so no rationale reaches `agents/go/tools/action.go`, and the guard refuses the execution with `the approval carried no rationale`. A click is not attribution.

Check the other half of the contract — that the request alone wrote nothing:

```bash
sqlite3 -header -column .state/incidents.db \
  'SELECT schema_version, actor, approved_by, action, target FROM audit_log ORDER BY id DESC LIMIT 5;'
```

Those five columns are what a completed write leaves behind: row format, executing agent, approver identity, action, and target. No rows is the correct result, and the receipt: the agent asked for a restart, you never supplied a rationale, and the table records exactly the writes that happened. [5.3. A2A Gateway]({{< relref "/5. Gateway/5.3. A2A Gateway.md" >}}) is where this same action gets approved for real, through the browser client in `clients/web/index.html` — the one shipped surface that sends a rationale — and where this query returns a row with your name in `approved_by`.

## Your turn: run INC-002 end to end and name every call

Predict first, before you open the browser. Across those five requests, how many Events rows will be calls the model chose, and how many things the code required? Write both down, then count.

- **Mode**: `inspect` — the session writes runtime state under `agents/go/.state`, which is already gitignored, and touches no tracked file.
- **Goal**: drive one incident through the default composition, and account for every call in the event log by who decided it.
- **Files to touch**: none.
- **Preflight**: `cd agents/go && mise run test` green, and `mise run doctor:model` reporting a measured inference line.
- **Steps**: start `mise run web`, work the five requests above in order, stop at the confirmation card without approving, then open the Events pane and list every `functionCall` in the order it fired. Beside each one write **model** or **code**, and for the ones you marked **model**, name the words in your question that made it pick that tool.
- **Gate that proves completion**: your list accounts for every `functionCall` row; `load_skill` appears on the fourth request, and you can point at the "Use when…" clause explaining the name it carried — your own if you wrote one, otherwise the shipped `remediation` description; the confirmation card names `restart_service` with the exact target the model proposed; and the `sqlite3` query above returns no rows, because you never supplied the rationale the write requires.
- **Final state**: stop the server. Runtime state stays under `agents/go/.state`; `git status --short` reports nothing. `mise run data:reset` drops that state back to the committed seed for a clean run.

Where your prediction and your count disagree, the gap usually runs one way: people over-count what the model decides, because the answer reads like one act of reasoning, and under-count the constraints, because a working constraint is invisible.

## What you can do now

- You can list what `AGENT_ENTRYPOINT=agent` composes — read and action tools, memory tools, the skill toolset — and which request reaches each.
- You can name the five capabilities that session never touched — MCP, the workflow, A2A, streaming, and delegation — and the command or variable that reaches each one.
- For every call in the event log, you can say whether the model chose it or the code required it, and point at the file that decides.
- You can predict an empty `audit_log` after a write request, because a dev-UI click carries no rationale — asking and performing stay different events.
