## One line stands between a paragraph and a restarted service

Ana's runbook allows a restart "once the cause is understood". The agent is about to get `restart_service`. Everything comfortable about the last chapter — that the worst outcome was a confidently wrong sentence — stops being true at that moment, and what replaces it had better not be a rule written in the instruction, because the instruction is advice to a 4B model at two in the morning.

Start where the answers are cheapest. These tests need no model and no network:

```bash
cd agents/go
go test ./tools
```

```text
ok  	github.com/MLOps-Courses/agentops-open-course-go/agents/go/tools	2.496s
```

Green is not very interesting on its own. Predict what happens if the guard were slightly weaker: open `agents/go/tools/action.go`, find the approval check, and delete the confirmation half of it so it only refuses when the confirmation object is missing entirely, not when it is present and unconfirmed:

```go
// simplified — the weakened check, for one test run only
confirmation := ctx.ToolConfirmation()
if confirmation == nil {
	return approval{}, errors.New("the action has not been confirmed")
}
```

```text
--- FAIL: TestTheHandlerRechecksConfirmationItself (0.68s)
    action_test.go:678: Error = "", want it to contain "has not been confirmed"
    action_test.go:680: service status = "operational", want the refused action to have changed nothing
FAIL
FAIL	github.com/MLOps-Courses/agentops-open-course-go/agents/go/tools	1.793s
FAIL
```

Read the second reported line again. The service is `operational`. A call that nobody approved restarted it, and the only reason that is a test failure rather than an incident is that one boolean was still being checked a minute ago. Put it back with `git restore -- agents/go/tools/action.go`, watch the suite go green again, and keep that failure in mind for the rest of this page. Everything below is either a way to make a read cheap and bounded, or a way to keep that boolean from ever being the only thing in the way.

## A read tool is a parser with a deadline {#what-makes-a-function-a-good-agent-tool}

A good agent tool has one purpose, typed arguments, bounded work, a stable JSON result, explicit failure, and the least authority its job needs. In Go the first four come almost free, because the struct _is_ the schema — ADK derives the JSON declaration the model sees from the argument and result types, so there is no second copy to drift.

Here is the whole `get_incident` handler:

{{< include path="agents/go/tools/read.go" region="get-incident" lang="go" >}}

Almost nothing happens here, which is the point. `guard` wraps the call in its deadline, retry budget, and circuit breaker; `readIncident` does the work; the result is a typed value. External input is normalized into a validated domain type once, at this boundary, and trusted afterwards — `domain.NormalizeIncidentID` either produces an incident id or an error, so no code further in has to wonder whether its string is a real one.

<a id="which-read-tools-does-the-agent-expose"></a>The public read surface is six tools: `list_incidents`, `get_incident`, `get_service_status`, `search_service_logs`, `get_runbook`, and `search_runbooks`. `agents/go/tools` constructs the incident, service, and log reads plus the two guarded actions; `agents/go/memory` constructs the runbook and long-term-memory tools; `agents/go/compose` chooses the exact set each entrypoint gets. The long-term memory helpers are separate capabilities and are deliberately not part of that six, which is why widening the remote allowlist in [3.3. MCP]({{< relref "/3. Capabilities/3.3. MCP.md" >}}) cannot pull them along by accident.

<a id="what-happens-when-a-tool-hangs"></a>Every blocking read runs under a configured context deadline (`AGENT_TOOL_TIMEOUT_S`, 30 seconds by default). When it expires the call returns a stable failure instead of eating the rest of the turn, and because cancellation travels through `context.Context`, the database query or HTTP request underneath is genuinely canceled rather than abandoned on a thread nobody can reach.

<a id="how-does-the-agent-shed-load-when-a-dependency-stays-down"></a>Deadlines and retries fix a blip. They make a sustained outage worse: if a dependency is down and every read pays the full retry budget before failing, the agent turns one broken service into a turn that takes minutes. The circuit breaker is the answer to that — after a run of consecutive failures it opens, calls fail fast, and after a cooldown exactly one probe is admitted to test whether the dependency came back. It is off by default; turn it on with `AGENT_CIRCUIT_BREAKER_ENABLED=true`, and tune it with `AGENT_CIRCUIT_FAILURE_THRESHOLD` and `AGENT_CIRCUIT_RESET_TIMEOUT_S`. Writes never go through any of this, and the next section explains why.

Two more properties of a read matter once the results reach a model.

**Failures are classified, not flattened.** An expected domain failure — no such incident, unknown service, a `limit` of zero — comes back as a stable `error` field the model can explain to Ana. An infrastructure or programming failure comes back as a wrapped Go error, so database corruption, cancellation, and violated invariants stay visible in logs and traces instead of being smoothed into "I couldn't find that". Nothing is silently repaired in memory: a seed row that fails validation returns an error rather than a plausible guess.

**Results are treated as data, all the way to the prompt.** Before a tool result reaches the model, app-wide policy recursively redacts concrete PII and credentials, and untrusted tool output is neutralized and spotlighted so an instruction hiding inside a log line stays marked as content. The one narrow carve-out is locally constructed skill content, which [3.2. Skills]({{< relref "/3. Capabilities/3.2. Skills.md" >}}) explains and [4.5. Guardrails]({{< relref "/4. Quality/4.5. Guardrails.md" >}}) enforces.

All of which is an argument against the tool everyone reaches for first. One generic `query_database` would give the model a bigger schema, broader authority, and far more ways to construct something unsafe — and it would make every audit event say "ran SQL". Small domain tools produce small schemas, legible audit rows, deterministic tests, and an allowlist you can read out loud.

## A write tool is a parser with a witness {#how-does-human-confirmation-work}

`restart_service` and `resolve_incident` change state. ADK marks both as requiring confirmation, so calling one does not run it — it creates an approval request and pauses. That is the framework's half. The handler's half is to distrust the framework and check everything again in the last instruction before the write:

{{< include path="agents/go/tools/action.go" region="validated-approval" lang="go" >}}

Every requirement is re-verified here rather than assumed: the confirmation exists and is confirmed, an approver identity, a session id, and an invocation id are all present, a network action additionally carries an authenticated principal that owns that invocation, and a rationale exists, fits the audit bound, and is redacted before it can reach an append-only row. Any missing piece returns a refusal a human can read. This is the function whose one deleted line let an unapproved call restart a service at the top of this page, and it is why a forged context or a direct Go call cannot walk around the rule the model-facing tool advertises. A synthetic A2A session id is fine for scoping reads; it is not an approver.

What a human sees before approving is part of the contract: the action, the validated target, the reason, and the verified actor — no credentials, no unrelated conversation. Approval is specific to one invocation. A blanket "allow writes" switch would be a different feature, and it is not implemented.

<a id="how-does-one-safe-simulated-action-complete"></a>Follow a guarded `INC-002` inventory restart through the whole path, which mutates only the disposable SQLite simulation under `agents/go/.state` and restarts no Kubernetes workload anywhere:

1. After reading `INC-002`, its logs, and the `service-down` runbook, the model **proposes** `restart_service(name="inventory")`. Prose cannot create an action; only the tool call does.
1. The typed Go entry point parses the service slug, checks the target exists, and refuses immediately if `AGENT_WRITES_DISABLED=true`.
1. ADK pauses before the handler runs and presents the exact proposed action for confirmation.
1. Confirmed execution still requires the approver, session id, invocation id, and bounded redacted rationale above; a network action also requires the matching authenticated principal.
1. One SQLite transaction changes the simulated service state and appends its audit row — or rolls both back together.
1. Replaying the same invocation, action, and target returns the original audit row instead of mutating twice.
1. The agent re-reads the service and the incident. Only those fresh observations can support a recovery claim.
1. During an incident of the agent's own, the write freeze preserves read access, and backup and restore stop writers and use the journaled path rather than copying live SQLite files.

<a id="why-are-mutation-and-audit-one-transaction"></a>Step five is the one worth arguing about. The state change and the audit row commit or roll back together, so there is no such thing here as a successful action nobody wrote down, or an audit claim for an action that never landed. SQLite triggers reject updates and deletes on that table, which is why the course calls the log append-only rather than immutable: an administrator with file access can still alter the database, and pretending otherwise would be the kind of claim this course exists to avoid.

Step six is why idempotency is not permission to retry. The audit key makes a re-delivered write safe, but the client still never retries automatically, because after a transport failure the caller cannot know which side of the commit the first attempt fell on.

And the disposable copy under `.state` is what makes all of this practicable: the committed dataset stays immutable, a runtime generation is published at the write-owning boundary, and `mise run data:reset` puts you back to a known start.

**You now have a write path that cannot fire on model output alone — it needs a named approver, a session, an invocation, and a readable reason, and it records all four in the same transaction as the change it makes.**

Four focused suites cover that deterministic lifecycle, still without a model:

```bash
cd agents/go
go test ./tools ./memory ./resilience ./data
```

A green run says something about this simulation and nothing about a production service — see [0.2. Evidence]({{< relref "/0. Overview/0.2. Evidence.md" >}}).

## Your turn: prototype a `get_oncall_schedule` read tool {#your-turn-how-do-you-prototype-a-get_oncall_schedule-read-tool}

You have read two contracts. Now write one. Keep it inside the Go module and offline, and let the test suite tell you when the contract is real rather than intended.

- **Mode**: `keep` — this is the tool you carry into the rest of the chapter.
- **Goal**: add one bounded typed read without widening database or filesystem authority.
- **Files to touch**: a focused source file and its tests under `agents/go/tools`; composition only after the tool contract passes.
- **Preflight**: a clean focused diff, and `cd agents/go && go test ./tools` green before you start.
- **Steps**: define typed argument and result structs in a focused file. Parse the external service string into a validated domain value once, at the boundary, instead of passing a raw string inward and re-checking it everywhere. Bound the returned schedule. Use a fake or temporary fixture rather than committed runtime state. Add table-driven success, missing, invalid, and cancellation cases. Then decide, explicitly, whether the tool belongs in the local and remote read allowlists.
- **Gate that proves completion**: `cd agents/go && go test -race ./tools ./compose` passes, and your cancellation case fails if you remove the guard wrapper. Then watch a model reach for it: run `cd agents/go && mise run web`, open `http://localhost:8002`, select `agentops_agent`, ask a question only your tool can answer, and confirm the Events view shows a `functionCall` naming it before the answer arrives. About 5 minutes. Use `mise run web` rather than `mise run run` — as 2.5's own table says, the console prints the answer without the tool calls behind it.
- **Final state**: the diff contains only the intended tool, its tests, and any reviewed allowlist change — no generated runtime state, no generic file or database escape hatch.
