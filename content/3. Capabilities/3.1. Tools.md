## What makes a function a good agent tool?

A good tool has one purpose, typed arguments, bounded work, a stable JSON result, explicit failure, and the least authority needed for its job.

```bash
cd agents/go
go test ./tools
```

The Go structs are the schema. External input is parsed and validated at the boundary before trusted domain code runs.

## Which read tools does the agent expose?

The public read surface contains six tools.

- `list_incidents`
- `get_incident`
- `get_service_status`
- `search_service_logs`
- `get_runbook`
- `search_runbooks`

Long-term memory helpers are separate capabilities and are never widened into the remote MCP allowlist by accident.

## Where do the tool lists live, and who composes them?

`agents/go/tools` constructs incident, service, log, and guarded action tools. `agents/go/memory` constructs runbook and memory tools. `agents/go/compose` chooses the exact set for each entrypoint.

The conversational agent can replace its six local reads with a filtered MCP toolset. Workflow and coordinator specialists keep structurally restricted local sets. Guarded writes remain local in every composition.

## What happens when a tool hangs?

Every external or blocking read runs under a configured context deadline.

When the deadline expires, the call returns a stable failure instead of consuming the rest of a turn. Cancellation reaches Go code through `context.Context`; callers do not need an abandoned worker thread.

## How does the agent shed load when a dependency stays down?

The resilience guard combines bounded retries for idempotent reads with a circuit breaker.

Repeated dependency failures open the circuit. Calls fail fast until the reset interval permits a probe. Writes are never retried because a caller cannot know whether the first attempt committed before a transport failure.

## How are database rows trusted?

SQLite rows are parsed into typed domain records and validated before they cross the tool boundary.

Incident identifiers, service slugs, runbook paths, enum values, timestamps, and optional fields have explicit rules. Invalid seed or runtime data returns a visible error; it is never repaired silently in memory.

## Why does the seed get copied?

The committed dataset is immutable evidence, while exercises need disposable writes.

A2A startup or the direct write boundary publishes a runtime copy under `.state`. Reads stay read-only. State actions, audit rows, session events, and A2A tasks then use runtime stores without mutating the seed.

## How does a tool result reach the model?

ADK serializes the typed result as function-response content and presents it to the model on the next generation step.

Before that happens, app-wide policy recursively redacts concrete PII and credentials. Untrusted tool output is neutralized and spotlighted so instructions embedded in retrieved data remain marked as data. Only locally constructed skill content gets the narrow reviewed-instruction carve-out.

## How are tool failures reported?

Expected domain failures use stable error fields; infrastructure or programming failures return wrapped Go errors.

The distinction lets the model explain a missing incident without hiding database corruption, cancellation, or a violated invariant. Logs and traces receive sanitized error evidence, never a swallowed exception.

## Which tools change state, and why are they never retried?

`restart_service` and `resolve_incident` change the disposable runtime database.

They require validated targets, ADK confirmation, and attributable identity. A network write additionally requires a gateway-authenticated principal that owns the invocation. Replays with the same invocation, action, and target return the original audit row instead of mutating state twice. The client still never retries a write automatically.

## How does human confirmation work?

ADK marks both action tools as requiring confirmation, and the handler validates confirmation again at the execution boundary.

{{< include path="agents/go/tools/action.go" region="validated-approval" lang="go" >}}

Direct calls and forged contexts therefore cannot bypass the same rule the model-facing tool advertises. A synthetic A2A session id is useful for reads, but it is not an authenticated approver.

## What should a human see before approving?

The approval view must name the action, validated target, reason, and verified actor without exposing credentials or unrelated conversation content.

Approval is specific to one invocation. For A2A, the verified gateway subject must also own that invocation. A broad “allow writes” switch is not equivalent and is not implemented.

## Why are mutation and audit one transaction?

The state change and append-only audit row commit or roll back together.

This prevents a successful action with no evidence and an audit claim for an action that never committed. SQLite triggers reject row update or delete; administrators can still alter the file or schema, so the course calls the log append-only, not immutable.

## Why not expose one generic database tool?

A generic query or update tool would give the model a larger schema, broader authority, and more ways to construct unsafe work.

Small domain tools produce smaller schemas, clearer audit events, deterministic tests, and a narrow MCP allowlist.

## How does one safe simulated action complete?

`restart_service` and `resolve_incident` mutate only the disposable SQLite simulation under `agents/go/.state`.

They do not restart Kubernetes workloads or touch production services. Follow a guarded `INC-002` inventory restart through the complete boundary:

1. After reading `INC-002`, its logs, and the `service-down` runbook, the model **proposes** `restart_service(name="inventory")`; prose alone cannot create an action.
1. The typed Go boundary parses the service slug, checks that the target exists, and refuses immediately if `AGENT_WRITES_DISABLED=true`.
1. ADK pauses before the handler executes and presents the exact proposed action for human confirmation.
1. Confirmed execution still requires an approver, session ID, invocation ID, and bounded redacted rationale; a network action also requires the matching authenticated principal.
1. One SQLite transaction changes the simulated service state and appends its audit row, or rolls both back.
1. Replaying the same invocation, action, and target returns the original audit result without another mutation or row.
1. The agent rereads the service and incident; only those fresh observations can support a recovery claim.
1. During an agent incident, the write-freeze flag preserves read access. Backup and restore stop writers, hold the process lock, and use the journaled recovery path rather than copying live SQLite files.

The focused action and state tests prove the deterministic lifecycle. A successful mock action is evidence about this simulation, never evidence that a Kubernetes or production service changed.

## Your turn: how do you prototype a `get_oncall_schedule` read tool?

Keep the prototype inside the Go module and offline.

- **Mode**: `keep`.
- **Goal**: add one bounded typed read without widening database or filesystem authority.
- **Files to touch**: a focused file and tests under `agents/go/tools`; composition only after the tool contract passes.
- **Preflight**: require a clean focused diff and run `cd agents/go && go test ./tools`.
- **Gate that proves completion**: `cd agents/go && go test -race ./tools ./compose`.
- **Final state**: tests are green and the diff contains only the intended tool, tests, and reviewed allowlist change.

1. Define typed arguments and a result in a focused package.
1. Parse the external service string into a validated domain value once; do not pass a raw string inward and revalidate it throughout the implementation.
1. Bound the returned schedule.
1. Use a fake or temporary fixture, not committed runtime state.
1. Add table-driven success, missing, invalid, and cancellation tests.
1. Decide explicitly whether the tool belongs in the local and remote read allowlists.

Run `cd agents/go && go test ./tools` before changing composition. Do not add a generic file or database escape hatch.
