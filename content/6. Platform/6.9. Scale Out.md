## The two-word command that quietly breaks a conversation

The agent is on the cluster. It answers, it traces, it refuses writes it should refuse. Then a colleague reads the dashboard, sees one pod serving every request, and types the obvious thing:

```bash
kubectl scale deployment/agentops-agent --replicas=2
```

Nothing fails. No pod crashes, no alert fires, no error reaches a log. What happens instead is that Ana asks a follow-up question, gets routed to the other replica, and is answered by an agent that has never heard of her incident. She reports it as "the agent forgot," which is not a phrase you can grep for.

The cause is one line in `agents/go/cmd/agent/session_store.go`: ADK's sessions live in a SQLite file inside `AGENT_STATE_DIR`, opened with a pool of exactly one connection. That is the correct design for one process — [2.4. Sessions]({{< relref "/2. Agents/2.4. Sessions.md" >}}) explains why the single connection is load-bearing rather than lazy — and it is a conversation-shredder for two. A file is not a shared database just because two pods can both open it.

## One conversation, two processes, one PostgreSQL

Watch it work before reading how. Start a PostgreSQL server, then start two agents that share nothing except that server — different ports, different state directories, different processes:

```bash
docker run -d --name agentops-sessions \
  -e POSTGRES_USER=agentops -e POSTGRES_PASSWORD=local-postgres -e POSTGRES_DB=sessions \
  -p 55432:5432 \
  postgres:18.3-alpine@sha256:54451ecb8ab38c24c3ec123f2fd501303a3a1856a5c66e98cecf2460d5e1e9d7
```

In two terminals, each exporting the same two settings and nothing else in common:

```bash
export AGENT_SESSION_BACKEND=postgres
export AGENT_SESSION_DSN='postgres://agentops:local-postgres@127.0.0.1:55432/sessions?sslmode=disable'
cd agents/go
AGENT_A2A_PORT=8090 AGENT_STATE_DIR=.state-a go run ./cmd/agent a2a
AGENT_A2A_PORT=8091 AGENT_STATE_DIR=.state-b go run ./cmd/agent a2a
```

`go run` rather than `mise run a2a` here on purpose: the task loads the repository `.env`, and this experiment is about the two variables you just exported rather than the ones your workspace already had.

Send a message to the first replica carrying a `contextId` you choose, then send the follow-up to the second replica with the same one. Predict the answer before you read it: replica B has its own empty state directory and has never seen the first message, so either the conversation lives somewhere both processes can reach, or B answers with nothing.

Here is the run from this machine. The first turn's model call actually failed — Ollama was busy with another job — which turns out to make the demonstration stronger rather than weaker:

```json
{
  "contextId": "scaleout-proof-001",
  "state": "failed",
  "text": "llm error response (code MODEL_UNAVAILABLE): \"Model request failed safely.\""

```

The second turn, sent to the other process, asked what phrase it had been told to remember:

```json
{ "contextId": "scaleout-proof-001", "state": "completed", "text": "SCALEOUT-CANARY-42" }
```

Replica B answered with a phrase that was only ever typed at replica A, during a turn that failed. Look at what the two of them left behind:

## What moved, and what deliberately did not

Three settings do all of this, and the [1.4. Providers]({{< relref "/1. Setup/1.4. Providers.md" >}}) rules apply to them exactly as they do to everything else — parse at the boundary, fail at startup, never at the first turn:

```bash
AGENT_SESSION_BACKEND=postgres    # sqlite (default) or postgres
AGENT_SESSION_DSN=postgres://...  # required by postgres, refused beside sqlite
AGENT_SESSION_MAX_CONNS=10        # connections one replica may hold
```

`AGENT_SESSION_DSN` is a `Secret`, so `mise run config:check` prints `**********` and every error this store raises names the variable rather than the value. That is not politeness. A connection URL carries a password, and a container log carries forever; the tests in `agents/go/cmd/agent/session_store_test.go` assert that a refused connection, an unreachable server, and a DSN the driver rejects all fail without the credential in the message.

The third setting is the one people skip and then page each other about. The connection ceiling that matters is not this replica's, it is the server's: PostgreSQL defaults to 100 connections, so ten replicas holding ten each is exactly the budget, and the eleventh replica — the one the autoscaler adds during the incident — gets `sorry, too many clients already`, as does every healthy replica's next connection. Multiply before you scale.

Setting `AGENT_SESSION_BACKEND=sqlite` while `AGENT_SESSION_DSN` is set is refused rather than ignored, because a DSN that looks configured while every session still lands on local disk is the same outage as before with a more convincing dashboard.

Sessions are the only state that moves. These stay exactly where they were, and each has a reason:

| State                               | Where it lives            | Why it stays                                                    |
| ----------------------------------- | ------------------------- | --------------------------------------------------------------- |
| A2A tasks (`tasks.db`)              | `AGENT_STATE_DIR`, SQLite | The task store is per-process; two replicas keep two task lists |
| Incident seed (`incidents.db`)      | `AGENT_STATE_DIR`, SQLite | Published and migrated by one writer at startup, by design      |
| Memory and vectors                  | `AGENT_STATE_DIR`, SQLite | Derived from the seed; rebuilt, not replicated                  |
| The audit seed under `agents/data/` | The repository, read-only | It is committed input. A dataset you can write to is not a seed |

The audit seed is the one to be loudest about: it is not moving to PostgreSQL, not now and not in a production port of this design. It is immutable committed input that every evaluation and every test measures against, and the moment it becomes a writable shared table, the thing your evidence is anchored to can drift underneath it.

That same single-writer logic used to keep the agent itself at one replica, and the first thing in its way was readiness rather than sessions. `a2aserver/probe.go` opened `runtime.db` in `AGENT_STATE_DIR` unconditionally, so an agent configured for PostgreSQL served turns correctly and reported unready forever — a pod that works and never joins the load balancer. That is fixed: the probe now asks the backend it is actually using, resolving ADK's four tables through `information_schema` on the PostgreSQL side and keeping the dedicated read-only file handle on the SQLite side. Point an A2A server at PostgreSQL now and it answers:

```bash
curl -s localhost:8090/healthz
```

```json
{ "status": "ready" }
```

Drop a column ADK needs — `ALTER TABLE events DROP COLUMN content` — and the same route returns `503` with the cause in the log rather than on the wire. Readiness stayed a real question; it just stopped asking it about a file.

Two bindings remain, and they are the honest reason the agent is not yet a fleet:

1. `a2aserver/taskstore.go` — the A2A task store is a per-replica SQLite file, so a `tasks/get` that lands on the replica which did not create the task finds nothing. Sessions are shared; tasks are not.
1. The `a2aserver` package documentation names the A2A process the single writer of runtime state: it recovers an interrupted restore, publishes and migrates the incident database at startup, and two of those against one claim is two writers.

So the state of it is: sessions are shared and proved, readiness follows the backend, and the task store is next. Which half is measured and which is projected is the distinction [0.2. Evidence]({{< relref "/0. Overview/0.2. Evidence.md" >}}) owns.

## Two replicas of the read plane, and what they actually bought

The MCP server is the workload replication was invented for. It opens the state volume read-only, publishes nothing, migrates nothing, and answers six read tools — so two of them are two identical readers rather than two writers racing. `infra/k8s/overlays/scale` is that change, layered on the local overlay rather than folded into it:

```bash
kubectl kustomize infra/k8s/overlays/scale | \
  yq 'select(.kind == "Deployment" and .metadata.name == "agentops-mcp") | .spec.replicas'
```

```text
2
```

A fourth overlay instead of an edit to `base` is a deliberate call. The local overlay is the taught path and its `ResourceQuota` is sized to exactly what Chapter 6 runs; doubling a workload there changes the pod budget for every learner who never opens this page. Keeping it separate also makes the whole scale-out a diff you can read: `diff <(kubectl kustomize infra/k8s/overlays/local) <(kubectl kustomize infra/k8s/overlays/scale)` is the lesson, in one command.

The overlay adds a `HorizontalPodAutoscaler` with `minReplicas: 2` — an autoscaler whose floor is one is a restart policy wearing a costume — and a ceiling of four, because the state claim is `ReadWriteOnce` and every replica therefore lands on the node that already holds the volume. Scaling past what one node can serve buys pending pods, not throughput. The anti-affinity rule is `preferred`, never `required`, for the same reason: the provisioner pins the volume's node as a hard filter, so a required rule would make the second pod unschedulable while a preferred one costs nothing today and spreads correctly the day the claim becomes `ReadWriteMany`.

CPU is the autoscaler's signal for this workload and must not be for the agent. The MCP server's cost really is processor time. The agent's latency is dominated by model inference happening in another process entirely, so its CPU sits low exactly when it is slowest — an HPA reading that would remove replicas under load.

Now measure it, because a replica count is a claim and a percentile is evidence. Run the existing MCP scenario against one replica at the shipped default rate, then look at the number before drawing a conclusion:

```bash
MCP_URL=http://localhost:8000/mcp mise run load:mcp
```

```text
✓ 'p(95)<250' p(95)=15.6ms
✓ 'rate<0.01'  rate=0.00%
checks_succeeded...: 100.00% 188 out of 188
```

Sixty tool calls per minute against a 250 ms budget, answered in 15.6 ms at the 95th percentile. Predict what happens at a hundred times that rate before you run it — most people expect the SQLite reader to be the wall:

```bash
MCP_URL=http://localhost:8000/mcp DURATION=30s RATE=6000 mise run load:mcp
```

```text
✓ 'p(95)<250' p(95)=15ms
http_req_failed....: 0.00%  0 out of 3014
iterations.........: 2998   99.896087/s
```

One replica served a hundred read-tool calls per second inside the same budget. Two replicas, driven concurrently at that rate each, came in at `p(95)=4.39ms` and `p(95)=4.58ms` across 18,013 successful checks and zero failures — two hundred calls per second, comfortably.

So the honest reading of this harness is not the one the word "scale" advertises. The shipped gateway rate-limits this listener to 120 requests per minute, which is one fiftieth of what a single replica already handles on a laptop. **At the rates this course teaches, replication buys availability, not throughput** — a rolling update with no gap, and a node drain that costs latency instead of an outage. If you want a throughput story from this stack, the honest place to look for it is the model, which is where every second of an agent turn actually goes.

Two claims above are unproved and must not be repeated as if they were measured: no run on this page happened on a Kubernetes cluster, so the autoscaler has never been observed adding a replica, and the Service's round-robin across two pods was never exercised — two processes were driven directly, one k6 run each. The overlay's rendering, schema validation, and lint are proved; its behavior on a live cluster is yours to confirm.

## Your turn: lose the disk, keep the conversation

Prove the session store is genuinely shared by taking away the only thing the two processes could have been sharing: their disks.

Predict first. If you delete replica A's entire state directory between the two turns, will replica B still know the phrase? The answer tells you exactly which store the conversation lives in, and the wrong prediction here is the one worth having.

- **Mode**: `temporary experiment`.
- **Goal**: run one conversation across two agent processes with PostgreSQL sessions, destroy one replica's local state mid-conversation, and confirm the other replica still answers from the shared store.
- **Files to touch**: none tracked. Working from `agents/go`, the experiment creates the two disposable state directories `.state-a` and `.state-b` plus a container named `agentops-sessions`; all three are removed at the end.
- **Preflight**: from `agents/go`, confirm each target is absent rather than inherited — `test ! -e .state-a`, `test ! -e .state-b`, and `docker ps -a --filter name=agentops-sessions` listing no container. Stop rather than reusing a container or a state directory you did not create here.
- **Steps**: start the container and both agents as shown above. Send the canary message to `:8090`. Then delete the first replica's disk with `rm --recursive --force -- .state-a` and send the follow-up to `:8091`.
- **Gate that proves completion**: the second turn returns the canary phrase, and `psql` shows exactly one row in `sessions` with four rows in `events`. Then set `AGENT_SESSION_BACKEND=sqlite` on both agents, repeat the same two turns, and watch the second replica answer without the phrase — that contrast, not the first result alone, is the proof.
- **Final state**: `docker rm --force agentops-sessions` and `rm --recursive --force -- .state-a .state-b`, then `mise run check` and `mise run test` from `agents/go` pass with no tracked file changed.

## What you can do now

- You ran one conversation across two agent processes that shared nothing but a PostgreSQL server, and read the single session row both of them wrote to.
- You can size a connection pool against a server's `max_connections` before adding a replica, instead of after.
- You can name the two bindings that still keep the agent at one replica, and show the readiness route answering `ready` against a PostgreSQL session store.
- You measured the read plane at 100 and 200 calls per second and can say what replication bought — and what it did not.

An hour ago, "runs at scale" was a property you would have had to take on faith. You can now demonstrate the half of it that is real, point at the exact file that blocks the other half, and tell the difference apart in someone else's architecture diagram.
