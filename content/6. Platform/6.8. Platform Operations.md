- **You will:** Fix the four things that actually go wrong on a laptop cluster: an unreachable model, a machine out of memory, a session you want to pause, and a control plane you want gone.
- **You need:** The k3d cluster from [6.2. Platform Install]({{< relref "/6. Platform/6.2. Platform Install.md" >}}), or a memory of it going wrong.
- **Time:** about 12 minutes, reference. {{% /admonition %}}

## The first command of the chapter that refuses to run

You get to the point in [6.2. Platform Install]({{< relref "/6. Platform/6.2. Platform Install.md" >}}) where the model has to become reachable from inside the cluster, you export the bridge address, you run `ollama serve`, and:

```text
Error: listen tcp 127.0.0.1:11434: bind: address already in use
```

Something already owns that port. On Linux it is almost always the systemd unit the Ollama installer shipped, which has been quietly serving your loopback since [1.4. Providers]({{< relref "/1. Setup/1.4. Providers.md" >}}). Occasionally it is `mise run model:fake`, the deterministic stand-in for load tests, which binds the same port on purpose so a k6 run can exercise the platform without spending tokens — if you started it earlier and forgot, stop it before reading further.

This page collects the four operational problems of running a Kubernetes cluster on the machine you also use for everything else. None of them is a bug in the agent.

## Make the model reachable from inside the cluster

Pods cannot reach a loopback listener on your host. k3d puts the cluster on its own Docker bridge network, so the model has to listen on the bridge's gateway address, which you read rather than guess:

```bash
docker network inspect k3d-local --format '{{(index .IPAM.Config 0).Gateway}}'
```

That address changes whenever Docker recreates the network, so re-read it each session instead of writing it down. On **Linux**, pick one of two ways to hand the port over, and undo it when the lab ends:

1. **Borrow the port for the session.** `sudo systemctl stop ollama`, run `ollama serve` in its own terminal with `OLLAMA_HOST` exported to `<bridge address>:11434`, then `sudo systemctl start ollama` when you are done. Nothing on disk changes.
1. **Rebind the unit itself**, if you want systemd to keep managing Ollama. Run `sudo systemctl edit ollama`, add `Environment="OLLAMA_HOST=<bridge address>:11434"` under `[Service]`, then `sudo systemctl restart ollama`. Undo it with `sudo systemctl revert ollama && sudo systemctl restart ollama`, which deletes the drop-in and restores the vendor unit.

On **macOS** the container engine runs inside a VM, so the Linux bridge address is not a valid macOS bind address at all. Follow [Ollama's macOS bind configuration](https://docs.ollama.com/faq#how-do-i-configure-ollama-server), quit and reopen Ollama.app, then prove it from a short-lived pod outside the restricted `agentops` namespace:

```bash
launchctl setenv OLLAMA_HOST "0.0.0.0:11434"
kubectl run ollama-check --rm -i --restart=Never \
  --image=docker.io/library/busybox:1.37.0@sha256:9532d8c39891ca2ecde4d30d7710e01fb739c87a8b9299685c63704296b16028 -- \
  wget -qO- http://host.k3d.internal:11434/api/tags
launchctl unsetenv OLLAMA_HOST
```

k3d injects `host.k3d.internal` for pod-to-host access, which is why that URL works from a pod and the bridge IP is what the host itself must bind.

{{% admonition danger "A rebound Ollama has no authentication" %}}

Every path above moves Ollama off loopback, and Ollama does not authenticate callers on that listener. Once it is bound to the bridge, every container on the `k3d-local` network — and anything that can route to that address — can use your model, read whatever you send it, and spend your GPU. Do this on a trusted machine, on a trusted network, and undo it when the lab ends. {{% /admonition %}}

If neither path is appealing on your machine, stopping here is a legitimate outcome rather than a failure. The Chapter 5 host profile is a supported checkpoint: it exercises the same agent, the same gateway, and the same protocols, and only the Kubernetes packaging is missing. The validated cluster path is Linux with Docker Engine; GKE stays plan-only unless an approved deployment is explicitly requested.

## When pods stay Pending, the machine ran out of room

This is the most common cold-laptop failure of the chapter, and it never announces itself as "out of memory". It arrives as a pod stuck `Pending`, a container in `CrashLoopBackOff`, a Skaffold build that stops moving, or a `kubectl` that suddenly cannot reach the API server. Three different failures look alike and have different fixes, so diagnose in this order — and before you read the table below, predict which of the three means your manifests are at fault. Exactly one of them does, and it is not the one people reach for first:

```bash
kubectl -n agentops get pods
kubectl -n agentops describe pod <pod> | grep -A6 "Last State"
kubectl get events -A --sort-by=.lastTimestamp | tail -20
docker stats --no-stream
```

| What you observe                                                              | What it actually is                                                                        | What to do                                                                                                                   |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| `Pending`, with `Insufficient memory` or `Insufficient cpu` in the events     | the node has no room left to schedule; nothing is broken or misconfigured                  | free the host first — stop the Chapter 5 and 7 host Compose stacks and any unrelated containers, then re-check               |
| `OOMKilled`, or exit code `137` under `Last State`                            | that one container exceeded **its own** limit; the rest of the cluster is fine             | read the limit in the owning manifest and raise it deliberately, or give that pod less work                                  |
| `kubectl` stops answering, or the k3d node container is gone from `docker ps` | the engine (or the Docker Desktop/Colima VM) hit the machine's ceiling and killed the node | raise the VM's memory allocation, or run fewer tenants: the model, the cluster, and a browser do not share 8 GiB comfortably |

Two structural savings come before tuning any limit. Never run the host Compose observability stack and the in-cluster stack at the same time: they duplicate every component and contend for the same local ports, which is also why dashboards go flat and port-forwards return nothing when both are up. And stop the cluster when you are not using it. The model is the other large tenant — Ollama keeps `qwen3:4b-instruct` resident for as long as it is serving.

## Stopping is not deleting

`k3d cluster stop` stops the node containers and leaves the cluster, its images, its volumes, and every deployed workload exactly as they are:

```bash
k3d cluster stop local
```

Make that the normal end of a working session. It returns the memory k3s and the course workloads were holding while keeping every byte of state, and `mise run cluster:start` resumes the same cluster in seconds. Deleting the cluster instead destroys its volumes, which is why that command sits behind the teardown review in [6.6. Platform Delivery]({{< relref "/6. Platform/6.6. Platform Delivery.md" >}}).

Removing kagent is a separate, later decision, and the order matters: remove the course workloads with Skaffold first, then the Helm releases. Deleting the controller and its CRDs first would leave a BYO Deployment nothing owns and nothing can clean up. The kagent control plane is also cluster-wide, so on a shared `local` cluster the right move is usually to remove the course workloads and leave the controller available to other namespaces. When you genuinely own the cluster, `helmfile --file infra/helmfile.yaml destroy` removes both releases — and [6.6. Platform Delivery]({{< relref "/6. Platform/6.6. Platform Delivery.md" >}}) owns that sequence, including how to prove nobody else is using it.

## What you can do now

- You can read the k3d bridge address and bind the model to it, on Linux or macOS, and undo the change afterwards.
- You can tell an unschedulable pod, an `OOMKilled` container, and a dead node apart from the same three commands.
- `k3d cluster stop local` ends a session without losing a single volume, and `mise run cluster:start` brings the same cluster back.
- You can say why the controller has to be removed after the workloads it manages, not before.

The cluster stops being a demo you ran once and becomes a tenant on your machine that you can feed, pause, and evict on purpose.
