{{% admonition abstract "In one glance" %}}

- **You will:** Build the agent image, inspect its binary contract, and distinguish local image proof from release provenance.
- **You need:** Docker running and `mise run doctor:gateway` passing; no cluster is required.
- **Time:** about 32 minutes, hands-on. {{% /admonition %}}

## How do you build the local image?

The root task resolves an honest development source identity, then passes the complete tuple to the Dockerfile:

```bash
mise run build:agent-image
docker image inspect agentops-agent:dev \
  --format '{{.Size}} {{json .Config.Entrypoint}} {{json .Config.Cmd}} {{.Config.User}}'
docker run --rm --read-only agentops-agent:dev version | jq
```

On the current reference build, the compressed runtime is about 16 MB and reports `[/app/agent]`, `[a2a]`, and `10001:10001`. Treat size as a measurement, not a frozen limit; remeasure after dependency or base-image changes.

## Why use two stages?

The build stage contains the pinned Go toolchain and module cache. It compiles one static executable:

The runtime stage contains only the distroless base, compiled binary, seed data, and prepared state directory:

{{< include path="agents/go/Dockerfile" region="runtime-base" lang="dockerfile" >}}

No shell, compiler, package manager, module cache, or development tool reaches the final image.

## Why is `CGO_ENABLED=0` load-bearing?

The cgo-free build runs on a static base with no libc and keeps one pure-Go SQLite implementation. Reintroducing cgo would change the runtime, scanner findings, and portability contract.

`-trimpath` removes builder paths, while `-s -w` removes debug tables the runtime does not need. The binary still exposes Go build information for dependency and version inspection.

## Why pin both base images by digest?

A tag can move while a digest identifies exact content. Both builder and runtime are digest-pinned:

{{< include path="agents/go/Dockerfile" region="base-images" lang="dockerfile" >}}

The Go version remains coordinated across root `mise.toml`, `agents/go/go.mod`, and the builder stage. Update them together and rerun compile, test, scan, and image checks.

## How does the traceability guard work?

Every image build supplies a validated source mode, identity, revision, tree digest, dirty bit, version, and timestamp.

{{< include path="agents/go/Dockerfile" region="traceability-guard" lang="dockerfile" >}}

The Dockerfile rejects missing, malformed, and templated-but-unset values before the distroless stage. A dirty development build receives a visible `unknown+dirty.<digest>` identity and no revision claim.

Build a clean release candidate with:

```bash
AGENT_BUILD_MODE=release mise run build:agent-image
```

Release mode fails if tracked or untracked source differs from the candidate revision. The task changes only the local image store; it does not publish the image.

## Why does one image serve several roles?

`ENTRYPOINT ["/app/agent"]` fixes the executable and `CMD ["a2a"]` selects the default surface. Kubernetes changes `args` to run MCP or state operations without repeating the executable path.

| Role             | Arguments                    | Owner                                 |
| ---------------- | ---------------------------- | ------------------------------------- |
| A2A agent        | `a2a`                        | Agent deployment and kagent BYO Agent |
| MCP server       | `mcp` plus transport options | MCP deployment                        |
| State operations | `state …`                    | Backup and restore jobs               |

One artifact keeps policy, configuration, telemetry, data parsing, and source identity aligned.

## How are seed and writable state separated?

`/app/data` contains the committed seed. `/app/state` is owned by UID/GID `10001` and is the only persistent write target. `/tmp` can be provided as a temporary filesystem.

Run with a read-only root filesystem and mount only the intended state path. The container must never mutate `/app/data`.

## How do you exercise probes locally?

Start a disposable container on loopback:

```bash
docker run --rm --name agentops-agent-check \
  --user 10001:10001 --read-only \
  --tmpfs /tmp:rw,noexec,nosuid,size=16m \
  -p 127.0.0.1:8080:8080 agentops-agent:dev
```

From a second terminal:

```bash
curl --fail http://127.0.0.1:8080/livez
curl --fail http://127.0.0.1:8080/healthz
docker stop agentops-agent-check
```

This starts a model-backed A2A process and may require the configured local model for readiness. Stop it after the check; an offline image inspection alone does not prove startup.

## How do you scan the exact artifact?

Scan the local tag you just built:

```bash
trivy image --severity HIGH,CRITICAL --exit-code 1 agentops-agent:dev
```

Record the image digest after the scan. A tag rebuilt later can identify different content, so release evidence must name the digest.

An SBOM inventories packages and modules; a signature binds an identity to an artifact digest. Neither proves the agent behaves correctly. Verification of a published signature, attestation, and immutable release evidence belongs to the owner-gated release workflow.

## What proves this page worked?

Inspect and scan the exact local image:

```bash
docker image inspect agentops-agent:dev \
  --format '{{.Id}} {{.Size}} {{json .Config.Entrypoint}} {{json .Config.Cmd}} {{.Config.User}}'
trivy image --severity HIGH,CRITICAL --exit-code 1 agentops-agent:dev
```

**You are done when:**

- The image reports `/app/agent`, default argument `a2a`, and user `10001:10001`.
- The current image size is recorded as measured evidence rather than an enforced budget.
- The high/critical scan exits successfully for that exact local artifact.
- You can explain why cgo is disabled, why both bases use digests, and why one binary serves three roles.
- A release build carries one clean revision and tree digest; a dirty local build uses `unknown+dirty.<digest>` without claiming that revision.
- Any temporary container is stopped.
