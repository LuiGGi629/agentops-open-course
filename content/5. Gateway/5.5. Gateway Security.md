## How does the prompt guard work?

The model listener parses `/v1/responses` and applies ordered request and response policy before forwarding or returning content.

```bash
cd agents/go
go test ./policy ./piiwebhook
```

The host and k3d OpenAI-compatible profiles use three controls:

1. A narrow injection pattern rejects obvious “ignore/override instructions” requests with status `400`.
1. Five built-ins mask SSN, credit-card, phone-number, email, and Canadian SIN patterns on requests and responses.
1. A Go webhook detects named entities such as people and locations through a bounded local Ollama call and returns masked content.

The reserved `reject-probe@example.invalid` value is a deterministic smoke canary: requests containing it return `400`, and a fake-model response containing it returns `502`. It preserves rejection evidence without changing the ordinary email policy, which is masking.

The application redactor remains the deterministic floor even when no gateway runs.

## Why is regex not enough?

Attackers paraphrase, encode, split, translate, or move instructions into retrieved data, while real text can match a simplistic pattern accidentally.

The regex is one visible rejection, not a claim of prompt-injection prevention. Tool allowlists, typed arguments, reviewed-skill provenance, spotlighting, action confirmation, call budgets, adversarial tests, and monitoring remain necessary.

Pattern-based PII similarly misses context-dependent names and places. That limitation is why the optional local model webhook exists.

## Which controls are active in every profile?

Every profile keeps separate MCP, A2A, and model listeners with bounded local rate limits and structured telemetry.

All MCP routes restrict tool targets. Kubernetes uses ClusterIP services and explicit network policy. Caller authentication, PII action shape, and backend identity vary by profile:

- Host/k3d OpenAI-compatible model routes use built-in masks plus the fail-closed Go webhook.
- The GKE Vertex route keeps its tested reject-only guard because it has no local Ollama webhook dependency.
- The default host profile is loopback-only and unauthenticated for local learning.
- The secured host profile adds TLS, JWT identity for MCP/A2A, tool authorization, and model API-key policy.
- The shipped k3d and GKE A2A routes have no caller identity provider, so their application pods refuse every guarded operational write.

## Could an optional managed classifier screen prompts here instead?

Yes, but it would be a proprietary, networked policy dependency with its own privacy, latency, availability, residency, and cost contract.

The required path remains account-free and local. A managed classifier must be opt-in, fail according to an explicit risk decision, receive only reviewed data, and carry separate evaluation and operational evidence.

## How is cloud authentication separated?

Caller identity and backend cloud identity are different trust boundaries.

The shipped GKE gateway does not authenticate callers. Adding that boundary requires an owner-selected issuer, audience, JWKS lifecycle, and verified-subject transformation.

Separately, `backendAuth.gcp` uses Workload Identity Federation to reach Vertex. No caller token becomes a Google credential, and no service-account key is mounted into the Pod. Backend identity neither authenticates an A2A caller nor makes guarded writes safe to enable.

## How do callers authenticate to the gateway?

The default host profile relies on loopback reachability. The opt-in secured profile uses TLS and listener-specific authentication.

- MCP and A2A validate JWTs from the locally generated lab issuer.
- MCP authorization maps verified subjects to closed tool-name sets.
- A2A forwards a verified subject header only after JWT validation.
- The model listener uses a configured API-key marker.

These are lab credentials committed or generated for demonstration. Rotate and replace them before any real exposure.

## How does the gateway-verified identity reach the audit row?

The secured A2A route validates a JWT, then writes the verified subject into the configured trusted header.

{{< include path="agents/go/a2aserver/identity.go" region="verified-identity" lang="go" >}}

The Go server accepts that header only when its trusted-identity setting is enabled. The value becomes request-scoped identity; guarded action handlers require it before committing state and audit. A direct caller cannot claim the same header on an untrusted boundary and receive verified status.

## Whose identity does the agent use downstream?

Each downstream call uses the minimum identity required by that hop.

The A2A actor identifies the human or service requesting work. MCP bearer credentials identify the agent as a tool client. The model API-key marker identifies the application route. Workload Identity identifies the gateway workload to Google Cloud. They are not interchangeable.

## In what order do the policies run?

Order matters because later policy must not parse or forward content rejected by an earlier control.

For the secured model route, caller authentication and rate policy precede AI route parsing; the request injection guard, built-in masks, and webhook run before the backend. Response masks and webhook run before the caller receives output.

Inside the application, the model-bound policy order is budget, compaction, then deterministic redaction. The first blocking result stops the remaining request path.

## How does the agent connect when authentication is on?

Use validated configuration rather than embedding tokens in commands or source.

- `AGENT_MCP_URL` selects the secured MCP endpoint.
- `AGENT_MCP_TOKEN` supplies the bearer token through ADK's credential provider.
- `OPENAI_BASE_URL` selects the HTTPS model endpoint.
- `OPENAI_API_KEY` carries the configured model-listener marker.
- The client's trust store or explicit CA path must trust the lab CA.

Do not print generated tokens or store them in tracked files.

## How do I turn on TLS locally?

Generate the gitignored lab CA and certificate, then start the standalone A2A upstream in one terminal. The trusted-header setting makes protocol requests fail unless the secured gateway supplies its JWT-verified subject:

```bash
infra/scripts/gateway-tls.sh

cd agents/go
AGENT_TRUSTED_IDENTITY_HEADER=x-verified-subject mise run a2a
```

Leave the upstream running. From a second terminal at the repository root, start the secured gateway:

```bash
mise run gateway:host:auth
```

From a third terminal, verify the certificate and JWT on a read-only A2A card request using a freshly generated token held only in the shell:

```bash
AGENTOPS_CA=infra/agentgateway/host/auth/ca-cert.pem
AGENTOPS_TOKEN="$(infra/scripts/gateway-jwt.sh ops-viewer)"
curl --fail --cacert "$AGENTOPS_CA" \
  -H "Authorization: Bearer $AGENTOPS_TOKEN" \
  https://localhost:3001/.well-known/agent-card.json \
  | jq -e '.name != null'
unset AGENTOPS_CA AGENTOPS_TOKEN
```

The card request makes no model call. A full model-backed turn must also configure the secured model and MCP endpoints, bearer token, and lab CA described above.

Never enable `AGENT_TRUSTED_IDENTITY_HEADER` on a raw listener reachable by untrusted clients. The gateway must validate the JWT and overwrite any client-supplied copy before the application may trust it.

This is lab trust: localhost names, no public CA, and no automated rotation or revocation. It is not an internet-ready endpoint.

## What stays unauthenticated and why?

The default raw loopback route is an account-free, single-user capability surface because the required learning path exposes no routable listener. Opaque task and context identifiers do not provide tenant authentication or multi-user task confidentiality.

The shipped Kubernetes A2A routes are also unauthenticated. ClusterIP, NetworkPolicy, and temporary port-forwards restrict reachability, while `AGENT_WRITES_DISABLED=true` independently freezes guarded operational writes; none of those controls establishes a caller identity.

Kubernetes probes remain unauthenticated but are pod-local or cluster-internal and return only bounded health state. Public status, user login, internet ingress, and tenant identity are not implemented.

## Why is the local rate limit not a quota?

It is an in-memory token bucket per gateway instance.

It does not aggregate by customer, persist across restart, coordinate replicas, or cap concurrent in-flight requests. Application call and token budgets remain separate. A real quota needs durable identity-aware accounting.

## Which security controls are intentionally absent?

The course does not ship public ingress, managed certificates, mesh mTLS, tenant isolation, distributed authorization state, WAF policy, DDoS protection, automatic key rotation, or a managed classifier.

Those omissions are explicit so a local lab is not presented as production security.

## What proves this page worked?

Run the offline guard, identity, configuration, and infrastructure evidence:

```bash
cd agents/go
go test -race ./piiwebhook ./policy ./a2aserver ./config
cd ../..
mise run check:infra
```

Run the TLS exercise only if you intentionally start the secured host profile. Stop the gateway afterward with `mise run gateway:host:stop`, then stop the standalone A2A upstream with `Ctrl-C` in its terminal.

**You are done when:**

- Built-in and named-entity masking, timeout, and conservative fail-closed paths pass.
- Verified identity reaches action audit only through the trusted boundary.
- Infrastructure checks prove the profile-specific guard shapes, webhook targets, Kubernetes write freeze, and disabled ADK content tracing.
- You can explain why lab TLS and a per-instance rate limit are not production auth or quota.
