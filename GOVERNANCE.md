# Governance

The AgentOps Open Course uses a single-maintainer model. This keeps decisions fast while making the final authority explicit instead of implying a committee that does not exist.

## Who maintains the project?

Médéric Hurier (Fmind) is the lead maintainer and final decision-maker. The maintainer owns repository access, release decisions, moderation, and the interpretation of project scope.

The Code of Conduct and security policy still constrain that authority. Security reports remain private, and moderation decisions follow [CODE_OF_CONDUCT.md](./CODE_OF_CONDUCT.md).

## How are decisions made?

- Small corrections and dependency-safe maintenance can be decided in a pull request.
- A new dependency, public contract, architecture change, or substantial course rewrite starts with an issue so alternatives and learner impact are visible.
- Decisions prefer the smallest solution that preserves the account-free OSS learning path, source-backed documentation, and deterministic local gates.
- The maintainer makes the final call after considering technical evidence and contributor feedback. When feedback is not adopted, the issue or review should record the reason.

Direct maintainer pushes are allowed, but they follow the same formatting, checks, tests, scans, and exact-head CI evidence as reviewed pull requests.

## What does reviewed mean?

“Reviewed” means a responsible maintainer has inspected the request, relevant source, final diff, and validation evidence. It does not imply that two independent people approved a change.

Model-backed evaluation, cloud runtime proof, and publication checks remain separate evidence. A green offline suite cannot silently stand in for a live boundary the change affects.

## How does someone become a maintainer?

There is no contribution quota. A contributor may be invited after sustained work demonstrates:

- sound judgment about learner experience, security boundaries, and repository scope;
- accurate, focused reviews as well as code or course contributions;
- reliable follow-through on validation and maintenance;
- constructive participation under the Code of Conduct.

The lead maintainer opens a public nomination issue, records the proposed responsibility and repository permissions, and grants access only after the contributor accepts. Permissions start at the least privilege needed for that role.

Maintainer access may be reduced after prolonged inactivity, at the maintainer's request, or when security and conduct obligations require it. The reason should be recorded publicly unless privacy or security prevents disclosure.

## How is the stable project maintained?

The latest 1.x release and `main` are the supported lines described in [SUPPORT.md](./SUPPORT.md). Routine dependency updates are reviewed weekly. Critical exploitable dependency findings are triaged within three business days; other fixes are grouped into small patch releases, while backward-compatible capabilities use minor releases.

Release authority remains with the lead maintainer. A release needs the local gate, exact-head GitHub checks, reviewed notes, and any runtime evidence affected by the change. A draft generated by automation is not a published release decision.

If no maintainer can safely review releases for six months, the lead maintainer should publish an inactivity notice and seek a successor. If succession fails, the repository is archived, unsupported workflows and scheduled jobs are disabled, and the last verified release remains available without an implied maintenance promise.
